# ADR-007: Approvals and the tasks queue — one pending task, one human gate

- **Status:** active
- **Date:** 2026-08-05
- **Deciders:** Tommaso (human), grilling session with assisted analysis
- **Builds on:** [ADR-006](006-dual-declaration.md) (two activation paths), [ADR-002](002-postgres-work-graph.md) (work graph substrate)
- **Amended by:** [ADR-017](017-consultative-subagents-durable-root-work.md) — declared specialist consultations have no write/effect tools and therefore never park; all durable specialist work enters through claimed tasks
- **Amended by:** [ADR-018](018-one-shot-durable-agent-tasks.md) — agent tasks are terminal one-shot runs; only direct deterministic tasks retain the bounded lease/retry protocol below
- **Amended by:** [ADR-019](019-human-approved-external-commitments.md) — chat and autonomous work create the same pending direct task; every external commitment uses a human button and a one-shot deterministic executor

## Context

Two questions were left open by the ADR-006 grilling:

- **Q3 — Concurrency between the two activation paths**: the CMO delegates a specialist for brand X (interactive) while a schedule fires the same specialist for brand X (autonomous).
- **Q4 — Parked approvals vs queue lease**: an autonomous run parking for hours at an approval gate while its task lease expires, causing a second dispatcher to re-lease and double-execute the work.

Code analysis of [trycompai/crm at `2eea41b`](https://github.com/trycompai/crm/tree/2eea41bc4511b5888eb6199d5f6017c1ab83a336) (`apps/agent/agent/lib/{approval,tasks,dispatch,evidence,pool}.ts`) shows the production-shaped mechanism we are following:

- `approval.ts` — principal-aware gates: automated sessions get boundary writes **denied** with an "instead" instruction (`"Not something to do unattended."`); interactive sessions get `user-approval`. Automated turns never park on an approval, so leases remain bounded.
- `tasks.ts` — immediate `enqueue` observes an existing unfinished task without modifying it, while `scheduleTask` may update an existing future booking's `dueAt` and `reason` instead of creating another. Neither operation has a database uniqueness constraint. Recurring `recheck` work has a distinct kind even where dispatch shares its execution path with immediate profile work, preventing a future recheck booking from suppressing immediate work. The CRM rescheduler does not distinguish a future booking from the equivalent task currently running, so ADR-017 stages that self-recheck until completion rather than copying this edge case. `claimDue` leases atomically with `FOR UPDATE SKIP LOCKED`; agent work gets 30 minutes, direct work 2 minutes, and `MAX_ATTEMPTS = 3` with `retireExhausted` for poison tasks. There is no heartbeat, lease owner, attempt token, or write fence.
- `dispatch.ts` — **two lanes**: `DIRECT_KINDS` are executed deterministically inside the dispatcher (plain code, no LLM); research kinds become agent sessions through the CRM's machine channel. Retry briefs say *"carry on from what is already in this thread"*. This remains historical queue evidence rather than Branderize's current Eve call shape: in eve 0.31.3 the custom machine channel owns `/internal/dispatch`, and its drain starts a claimed agent row through the channel-address API described below.
- `evidence.ts` — writes are **weighted by evidence kind**; a `contradiction` caps the score and the fact degrades to a human-settled suggestion. The write path arbitrates conflicts, not locks.
- `pool.ts` — `collapsing()` prevents overlapping dispatcher runs.

> **Current agent-run precedent (ADR-018).** The queue observations above remain historical context for the deterministic direct lane and for dedup/scheduling. They no longer define autonomous eve execution. The current CRM `AgentRun` is one task-mode session with one terminal result and only pre-`session_id` delivery recovery; Branderize now follows that lifecycle for `execution_mode = agent`.

## Decision

> **Amended by ADR-017, ADR-018, and ADR-019.** Read-only consultation may still be immediate, but every durable specialist result starts from a task. External commitments no longer use two approval mechanisms: both interactive CMO chat and autonomous roots create the same direct task in `awaiting_approval`. No eve tool parks to own the later effect, and no separate Proposal Object or `execute-proposal` child task is created.

**External approval has one durable owner.** A registered preparation operation may create a safe external draft, but every schedule, publish, send, activation, spend, merge, pause, unpublish, cancellation, or close becomes a human-activation direct task. The human click appends the Approval Action and changes that same row to `queued`. Its responsible specialist deployment then runs the fixed plain-code handler without eve or an LLM. Chat and the console are two views and controls over the same task.

**The tasks queue** combines the current CRM one-shot agent-run boundary with the already accepted Branderize dedup and recheck mechanics:

- Immediate/recheck identity: every immediate kind that permits a follow-up declares one distinct, same-root `recheckKind` in the registry. They may share schema, core brief, and execution handler, but remain separate queue identities so a future active booking cannot make immediate work return `already_active`. A recurring recheck kind may map its next recheck to itself
- Immediate dedup: a partial unique index on `(kind, brand_id, subject_key) WHERE status IN ('awaiting_approval', 'queued', 'running')` makes observe-or-create atomic. Ordinary work uses a semantic subject; each commitment proposal uses its own stable subject so independent proposals do not coalesce. On conflict, `enqueueOrObserveTask` returns `already_active` without changing the accepted row's `due_at`, typed payload, or rationale. A unique creator key prevents replay of an ordinary request that created a task. V1 does not persist distinct keys from later requests that merely observed or rescheduled it; after the active task settles, retrying such a request may create new work. An ADR-014 D7 deterministic cadence task is separately keyed by exact `(schedule_id, scheduled_for)` and uses an occurrence-scoped subject, while partial uniqueness on active `schedule_id` permits at most one queued/running occurrence per schedule. A due slot behind that occurrence creates no task or alias: the materializer advances the schedule and updates only its coalescing counter and last slot. Separate from dedup, registry-declared non-commutative commitments derive a trusted target conflict key: at most one can be `queued | running` per brand and key, while any number of distinct proposals may remain `awaiting_approval`
- Intentional rescheduling: the root agent chooses a bounded due time, typed payload, and rationale through the authored `scheduleRecheck` tool; trusted eve session context and the registry relation supply the authorized recheck kind plus task and tenant identity. The model cannot select an arbitrary kind. `scheduleOrRescheduleTask` may move an equivalent scheduled booking, while a running recheck that books the same recheck identity stores `next_due_at`, `next_payload`, and `next_rationale` on itself. That self-target write is one atomic `UPDATE ... WHERE id = current_task_id AND status = 'running' RETURNING`; zero rows means `task_closed`, with no fallback insert. Concurrent authorized schedulers update the one target row or one `next_*` tuple atomically; Postgres row ordering makes the last valid database write win, with no earliest/immediate priority, merge, or additional successor
- Agent claim: `/internal/dispatch` is a route of the root's custom machine channel. It authenticates `DISPATCH_SECRET`, acknowledges the payload-free poke, and registers the drain with `waitUntil`. Inside that drain, an eligible sessionless `queued` row is atomically changed to `running` only after filtering `worker_key = SELF AND kind IN compiledSupportedKinds` and passing the agent-specific autonomous-credit check. At zero balance it remains queued and no eve session starts. The root reloads task and graph context, then calls ``from(`task:${taskId}`).send(brief, { auth, mode: "task", outputSchema })``. `task:<task_id>` is the raw channel-local address and eve adds the machine-channel namespace. The returned `session.id` is the authoritative `session_id`; claim does not increment `attempts` or create an agent execution lease, and `session.started` normally binds that id before the post-send path does
- Agent delivery recovery: only `running AND session_id IS NULL` older than five minutes may return to `queued`, clearing `started_at`, staged completion, and `next_*`. Once the authoritative `session_id` is stored, that task is never reclaimed or redispatched. If both bind paths missed an accepted session, recovery may send again after that unrecorded owner has released the address; a later product retry is a fresh task with a fresh id and creator key
- Agent settlement: `finishTask` validates and stages the canonical registered `TaskCompletion`; `result.completed` may mirror it for telemetry, but only `session.completed` with the staged value normally changes `running → succeeded`. `completed`, `partial`, and `blocked` are deliberate domain outcomes under `succeeded`. Delivery error, `turn.failed`, `session.failed`, application cancellation, or terminal completion without a valid staged value produces `failed` or `cancelled`. A cancellation's following `session.waiting` is ignored. Only successful settlement atomically creates or observes one equivalent staged successor; failure clears it. A swallowed terminal-handler error alerts for manual reconciliation and never triggers redispatch
- Direct lanes: retry-safe direct/automatic kinds may retain the two-minute bounded lease, but are limited to transaction-safe internal operations or side-effect-free idempotent external reads and never write externally. Neither direct lane reads the agent credit gate. A human-approved external commitment moves `awaiting_approval → queued → running` in its responsible root even at zero pool balance, makes at most one provider call, and settles `succeeded`, `failed`, or `outcome_unknown`; it has no execution lease, automatic reclaim, or three-attempt policy. Approval of a serialized target already owned by another `queued | running` commitment returns `target_busy`, commits no Approval Action, and creates no FIFO waiter
- Bounded drain order: after stale-human classification, the root offers batch capacity first to claimable approved commitments by `execute_before NULLS LAST`, Approval time, and id; remaining slots flow to retry-safe direct/automatic FIFO and then agent FIFO. This ordering lives in claim queries, not in a generic `priority` column, and does not preempt already-started work

**Concurrency on writes is optimistic, on the supersession chain.** `produceObject` declares the exact Object version it intends to supersede. In the same transaction that would append the Action and new Object, trusted code locks and compares the current head. If it no longer matches, the transaction writes neither grammar-layer row and returns `stale_head`; it does not invent an active, superseded, dismissed, candidate, or conflict Object. The caller reloads the current head and may deliberately recompute a new proposal from that state, but it must not replay the already-computed payload against the new head automatically. Single-owner Objects (brand context → product-marketer) plus enqueue dedup make this case rare by construction. Claim grading (`proven / plausible / assumption`) still plays the role of the CRM's evidence weighting, but concurrent stale writes fail closed rather than creating a second resolution lifecycle.

An accepted agent session relies on eve's durable Workflow run and is never replaced because an application lease expired. Its tools still require idempotency because an interrupted durable step may replay. Direct/automatic work may be at-least-once only where a transaction-safe internal operation or side-effect-free idempotent external read makes replay safe; it never performs an external write. A human external commitment is deliberately at-most-one automatic provider call: an ambiguous outcome stops as `outcome_unknown` and another attempt requires a new task and human approval.

## Consequences

- `packages/policy` derives the final effect signature and verdict from the registered kind and final task revision; external commitment has an absolute human-approval floor.
- `packages/brain`: a proposal is a direct task in `awaiting_approval`; the Approval Action is appended at the click and linked from that row.
- The console's approval inbox renders pending tasks and their derived preview. “Why am I being asked?” is answered by registry and final Policy data; “who authorized it?” is answered by the Approval Action.
- The current CRM has no equivalent provider-write inbox. Its closed, authored `AgentAction` surface is the precedent; Branderize's per-effect human gate and unknown-outcome behavior are explicit adaptations (ADR-019).
- The current CRM has no direct equivalent of `produceObject(expectedHead)`. Its AgentVersion builder can preserve alternatives because it models non-current `READY` versions and promotes one separately. Branderize does not add that candidate lifecycle in v1: a stale supersession writes nothing and must be recomputed from the new head.

## Alternatives considered

- **eve-native parking as the external execution owner** — rejected: autonomous roots cannot wait, and resuming a CMO tool would create a second executor beside the task dispatcher. Both paths create the same pending direct task instead.
- **Mutex per (specialist, brand)** — rejected: lock ownership across parked/long sessions is fragile; optimistic supersession + dedup achieves the same safety without lock lifetime questions.
- **Persist every stale write as a branch for human resolution** — rejected for v1: it requires a real non-current candidate state, lineage and a promotion/dismissal workflow. The current Object lifecycle has no truthful state for a candidate that was never canonical.
- **All consultations through the queue** — rejected: durable work belongs in tasks, while a read-only specialist consultation may answer synchronously without becoming a second execution lane (ADR-017).
