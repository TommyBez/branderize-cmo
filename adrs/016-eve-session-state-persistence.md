# ADR-016 — eve fixed-session persistence on the owning record

**Status:** Accepted — 2026-08-06
**Amends:** ADR-014 D2 (conversation and task session binding), ADR-008 §4 (continuation-token terminology)
**Amended by:** [ADR-018](018-one-shot-durable-agent-tasks.md) — task addressing now starts one task-mode session and never continues a failed run

## Context

Earlier drafts used Branderize strings such as `cmo:<conversation_id>` and `task:<task_id>` to find eve client state through a shared mapping table. That copied the CRM's deterministic task-channel token into the human-chat path and confused three different identities:

- the application conversation or task;
- eve's `sessionId`, which identifies a durable session and its stream;
- a custom channel's `continuationToken`, which addresses channel-owned sessions but is not part of the default HTTP client's public state.

The production CRM provides the useful product invariant for human conversations: `AgentConversation.id` is the application primary key and `sessionId` is a unique eve-generated integration key. The UI selects, authorizes, and deletes by the application id. Branderize keeps that identity split while implementing the current eve client contract rather than copying the CRM's older mutable continuation state.

The machine channel is deliberately different. The current CRM derives `run:<run_id>` and sends it once in task mode; Branderize derives the equivalent `task:<task_id>` because its task row is its run record. Eve 0.31.3's bundled custom-channel guide still lets that channel define its raw token format. ADR-018 fixes the send to `mode: "task"`; the token correlates and protects one autonomous run rather than addressing follow-up turns.

For human chat, eve 0.31.3 exposes one fixed, ID-addressed `ClientSession` and a deliberately small public cursor:

```ts
interface ClientSessionState {
  sessionId: string;
  streamIndex: number;
}
```

`sessionId` is the immutable target of follow-up, control, and stream routes. `streamIndex` is only the local read cursor. `client.sessions.attach()` performs no request, remains pinned to exactly that id, and never creates or follows a replacement. The cursor is neither a product identifier nor a transcript.

Eve 0.31.1 added transitional runtime-envelope compatibility for sessions accepted by 0.30.3–0.30.8 deployments, so an in-flight durable session may survive the deployment upgrade. That compatibility does not restore the removed TypeScript client API or public continuation-token fields: all Branderize application code and persisted client state use the fixed-ID 0.31.3 contract above.

## Decisions

### D1 — Product records own identity; each channel owns its runtime addressing

A brand may have many CMO conversations. Each conversation has one owning user, and only that owner may send or continue it. Each `cmo_conversations.id` is generated by Branderize and is the stable id used by URLs, ownership checks, titles, archival, and message projection. The default eve channel generates the conversation's fixed `sessionId`; Branderize never fabricates or replaces it.

Durable work is identified by `tasks.id`. The machine channel derives `task:<task_id>` and uses it as the actual channel-local `continuationToken`, not as a Branderize lookup key. There is no polymorphic `agent_session_states` table.

### D2 — Persist each surface's runtime binding on its owning record

The human-conversation fields are:

```text
cmo_conversations {
  id,
  brand_id,
  owner_user_id,
  session_id NULL UNIQUE,
  stream_index NOT NULL DEFAULT 0,
  ...conversation metadata
}

```

`session_id` is the stable stream, telemetry, and diagnostic join. `stream_index` is the next unread event index for the application handle and is zero before the first session is created. There is no `session_state` JSON, client `continuationToken`, or adapter-version column: the complete eve 0.31.3 public state maps directly and losslessly to these two columns.

Branderize creates the CMO conversation row before the first send and passes its id through verified application context. This is a cheap adaptation of the CRM pattern: our audit hook projects `message.*` directly to `chat_messages(conversation_id)`, so pre-creation avoids buffering or backfilling the first events while `sessionId` is not known yet. Once eve returns a `sessionId`, it is persisted with a uniqueness constraint and attached to exactly one application conversation.

The task row stores the one authoritative `session_id` bound by its one-shot channel delivery. It does not persist human-client state or a stream cursor: the custom channel does not use `ClientSession`, and its deterministic channel-local token is derived from `tasks.id`. A `session.started` hook normally binds the id before post-send; only an unbound handoff may be delivered again under ADR-018.

### D3 — Persist human state at the two useful boundaries

Branderize creates the application conversation before the first message, then starts exactly one eve session with that first turn:

```ts
const { session, response } = await client.sessions.create({ message });
```

As soon as `create()` returns, the adapter binds `session.state.sessionId` to the still-unbound conversation. After consuming the response, it persists `session.state.streamIndex`. A crash after eve accepted the turn but before the cursor update may replay already-seen stream events from the older index; the audit/message projections remain idempotent by event id.

For every follow-up, the adapter loads the owning conversation, verifies its owner, and targets only its saved id:

```ts
const session = client.sessions.attach(conversation.sessionId, {
  streamIndex: conversation.streamIndex,
});
const response = await session.send(message);
```

After consuming the response it persists the advanced `session.state.streamIndex`. Domain code passes a typed conversation id and message; only the human-chat adapter constructs the fixed eve handle.

The task dispatcher passes a typed `task_id` to the machine-channel adapter. That adapter alone formats or parses `task:<task_id>`, calls `send()` with `mode: "task"`, and coordinates the hook/post-send fill of the authoritative session id. The prefix is a channel protocol detail rather than a domain identifier.

### D4 — Human conversations and task dispatch have different continuation semantics

For a waiting session, `attach(session_id, { streamIndex })` can send the next input. A completed, failed, expired, reset, or otherwise unavailable human conversation remains readable from Branderize's permanent message projection but is no longer continued.

Sending through a terminal fixed handle fails; it does not create or discover another session. Reset also retires that exact id and leaves the handle pinned to it. Starting again therefore requires an explicit product action that creates a new `cmo_conversations` row and then calls `client.sessions.create({ message })`. The adapter never rebinds the old conversation and never follows a replacement automatically.

A durable agent task has no continuation lifecycle. Its single claim attempts one task-mode run with fresh history, state, and sandbox after reloading authoritative task and graph context. Only a stale `running` row without `session_id` may return to `queued` to recover an unproven delivery. If both binding paths missed an accepted session, that recovery may send again after the unrecorded owner releases the token. Once the authoritative id is stored, the same task is never sent again; an explicit product retry creates a new task and session.

The runtime events also have different application meanings. `finishTask` stages the canonical validated `TaskCompletion`, and `session.completed` is the normal success boundary. `result.completed` may mirror the structured output for telemetry. `turn.failed`, `session.failed`, and cancellation are terminal application outcomes. Eve follows `turn.cancelled` with `session.waiting`; the application ignores that one expected waiting boundary and never reuses the token. Other waiting is anomalous telemetry and never resumes, succeeds, or requeues the task. If an event-handler database write fails, the durable stream is reconciled manually without redispatch.

### D5 — The transport contract stays adapter-private

Application callers do not accept `sessionId`, `streamIndex`, or a channel token. They pass Branderize conversation or task ids to the relevant adapter. A future incompatible eve client shape requires an explicit schema migration, but it cannot change conversation ids, ownership, transcripts, or graph artifacts. The task channel's token builder remains private to that channel and can evolve independently.

## Consequences

- Human chat keeps the production CRM's useful product/runtime identity split while adopting eve 0.31.3's fixed-ID client contract.
- `cmo_conversations` stores the complete public client cursor as typed columns: `session_id` plus `stream_index`, with no opaque JSON or client continuation token.
- CMO conversations follow the CRM's single-owner writing model: only `owner_user_id` may send the next turn. Whether other brand members may read the transcript is a separate authorization decision and is not defined here.
- State ownership is enforced by ordinary row access: one fixed human session belongs to one conversation; one authoritative machine session id belongs to one task.
- `cmo:<conversation_id>` and `agent_session_states` are removed from the architecture.
- `task:<task_id>` remains only as the channel-local token of the custom machine channel; callers and domain code never use it as a lookup key or follow-up address.
- Agent tasks and human external commitments do not read or increment `tasks.attempts`; only registered retry-safe direct/automatic kinds may use it under ADR-018 as amended by ADR-019.
- A terminal/reset CMO session is never rebound or transparently replaced; starting again creates a new application conversation and a new eve session.
- Task delivery uses `mode: "task"`. The dispatcher recovers only a stale sessionless handoff and never replaces a run after authoritative session binding.
- `session_events` remain durable telemetry. `chat_messages`, scoped by both `brand_id` and `conversation_id`, remain the permanent human transcript.

## Out of scope

This ADR fixes the conversation ownership invariant (one owner and writer), but does not decide whether other brand members may read its transcript. Authentication, the broader tenant ACL, membership checks, and database query scoping require separate decisions.
