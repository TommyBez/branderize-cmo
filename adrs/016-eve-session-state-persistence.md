## Context

Earlier drafts used Branderize strings such as `cmo:<conversation_id>` and `task:<task_id>` to find eve client state through a shared mapping table. That copied the CRM's deterministic task-channel token into the human-chat path and confused three different identities:

- the application conversation or task;
- eve's `sessionId`, which identifies a durable session and its stream;
- a custom channel's `continuationToken`, which addresses channel-owned sessions but is not part of the default HTTP client's public state.

The current production CRM provides two useful invariants for human conversations. `AgentConversation.id` is the application primary key while `sessionId` is a unique eve-generated integration key, and the browser's `useEveAgent` instance—not the Next proxy—owns the live `ClientSession`, cursor, stream consumption, and reconnect loop. The proxy verifies the caller and forwards the response body without consuming its NDJSON. Branderize keeps that split while tightening the CRM's permissive first-session ownership check.

The machine channel is deliberately different. The current CRM derives `run:<run_id>` and sends it once in task mode; Branderize derives the equivalent `task:<task_id>` because its task row is its run record. Eve 0.31.3's bundled custom-channel guide still lets that channel define its raw token format. ADR-018 fixes the send to `mode: "task"`; the token correlates and protects one autonomous run rather than addressing follow-up turns.

For human chat, eve 0.31.3 exposes one fixed, ID-addressed `ClientSession` and a deliberately small public cursor:

```ts
interface ClientSessionState {
  sessionId: string;
  streamIndex: number;
}
```

`sessionId` is the immutable target of follow-up, control, and stream routes. `streamIndex` is only the local read cursor. `client.sessions.attach()` performs no request, remains pinned to exactly that id, and never creates or follows a replacement. The cursor is neither a product identifier nor a transcript.

Eve 0.31.1 added transitional runtime-envelope compatibility for sessions accepted by 0.30.3–0.30.8 deployments, so an in-flight durable session may survive the deployment upgrade. That compatibility does not restore the removed TypeScript client API or public continuation-token fields: all Branderize application code and persisted client state use the fixed-ID 0.31.3 contract above.

## Decisions

### D1 — Product records own identity; each channel owns its runtime addressing

A brand may have many CMO conversations. Each conversation has one owning user. Only that exact owner, while the Better Auth `Member(brand.organization_id, owner_user_id)` currently has role `owner | admin | member`, may create, send, continue, answer HITL, or mutate its session/product state. A current `viewer` owner may still read the already-authorized transcript/snapshot/stream and may stop only an already observed in-flight turn through the scoped cancel rule in D3; it cannot start or resume model work. Each `cmo_conversations.id` is generated by Branderize and is the stable id used by URLs, ownership checks, titles, archival, and selection of the bound root event log. The default eve channel generates the conversation's fixed `sessionId`; Branderize never fabricates or replaces it, and possession of either runtime id is not authorization.

Durable work is identified by `tasks.id`. The machine channel derives `task:<task_id>` and uses it as the actual channel-local `continuationToken`, not as a Branderize lookup key. There is no polymorphic `agent_session_states` table. Child sessions likewise create no ownership or mapping row: Eve supplies their exact `session.id` and `ctx.session.parent` lineage, which the audit projection denormalizes on `session_events`; only the existing conversation or task owns the top-level runtime binding.

### D2 — Persist each surface's runtime binding on its owning record

The human-conversation fields are:

```text
cmo_conversations {
  id,
  brand_id,
  owner_user_id,
  session_id NULL UNIQUE,
  stream_index NOT NULL DEFAULT 0,
  ...conversation metadata
}

```

`session_id` is the stable stream, telemetry, and diagnostic join. `stream_index` is the latest browser cursor checkpoint known to the application and is zero before the first session is created. It is monotonic but opportunistic: a crash can leave it behind the durable stream. There is no `session_state` JSON, client `continuationToken`, or adapter-version column; the only public eve 0.31.3 client state is this fixed id plus cursor.

Branderize creates the CMO conversation row before the first send through an `apps/app` mutation that requires current Member role `owner | admin | member`. The browser supplies that application id in a proxy-only request header when `useEveAgent` performs `POST /eve/v1/session`; the value selects a candidate row but grants no authority. Only the create handler reads it. Because Eve's browser client may repeat configured headers on follow-ups, streams, and reconnects, the proxy removes this selector from **every** forwarded `/eve/v1/*` request, not just the create request. The proxy verifies the current Better Auth user is its `owner_user_id`, loads the conversation's brand, rereads the exact `Member(brand.organization_id, user_id)`, requires its current role to remain `owner | admin | member`, and rejects a row that is already bound. A role from the row-creation request, a previous bridge JWT, or browser state is not reused. From that authorized row it constructs the typed billing context and projects `brand_id` and `conversation_id` as trusted scalar Eve auth attributes; the browser cannot provide or override either claim.

The CMO's top-level `session.started` hook and the proxy's post-create response path perform the same fill-or-match binding. The hook acts only when `ctx.session.parent` is absent and uses the trusted conversation/brand attributes; it binds before later root events run through their hooks, while the proxy remains the response-boundary fallback. Both accept null-to-their-exact-id or the same existing id and reject a different binding. A child session can never bind a conversation. This current-CRM-style dual path closes the first-session race without adding another state record: the conversation's authoritative `session_id` names the exact root emitter selected for every later transcript read.

The audit hook attempts to persist every root and child event in `session_events`; delivery is best effort and persistence failures alert, but no snapshot or recovery path reconciles a missed event. It does not write a second message projection. The permanent conversation transcript selects only raw events whose exact emitting `session_id` equals the bound top-level `cmo_conversations.session_id`, keyset-pages the full stored prefix in application ingestion order, and reconstructs `EveMessageData` with Eve 0.31.3's `defaultMessageReducer()`. A self-copy or declared specialist inherits the trusted `conversation_id` for attribution but has its own child id and parent relation, so its raw brief, narration, reasoning, actions, and messages are never selected into the transcript. Eve returns its result into the parent stream as `action.result` with `result.kind = subagent-result`; because that event belongs to the root stream, the default reducer produces one dynamic-tool result while the child's `subagent.completed` stays child control-plane telemetry. Any later CMO summary is a distinct root assistant part. The reconstruction follows raw event-stream semantics, may contain an alerted ingestion gap, and may include distinct outputs from an interrupted replay; it does not claim to reconstruct Eve's canonical durable history.

Eve answers the create request immediately with the generated id in `x-eve-session-id` and its JSON body. The proxy awaits only those upstream headers, validates the id, and performs a fill-or-match compare-and-swap before it exposes the successful create response to the browser: the row may move from null to that id or already contain that exact id, but a different binding is a conflict. It then preserves the upstream status, non-hop-by-hop headers, body, and streaming semantics; it never parses the create body, consumes the later NDJSON event stream, or owns a reconnect cursor. A conflicting compare-and-swap or database failure suppresses the successful response and fails closed. Because Eve may already have accepted the first turn, a concurrent duplicate create or post-acceptance database failure can still leave an unbound physical session; v1 accepts that same-owner first-send edge rather than adding a cross-tab creation lock. Only the one database binding is authoritative, and every later session route rejects the unbound id.

The task row stores the one authoritative `session_id` bound by its one-shot channel delivery. It does not persist human-client state or a stream cursor: the custom channel does not use `ClientSession`, and its deterministic channel-local token is derived from `tasks.id`. The machine adapter constructs the same typed billing context from the claimed task and projects its verified `brand_id` into `taskAuth`, never from the dispatcher poke or model payload. A `session.started` hook normally binds the id before post-send; only an unbound handoff may be delivered again under ADR-018.

### D3 — The browser owns the live client; the proxy owns authorization and first binding

The selected conversation has one browser-owned Eve read state. For an exact owner with current role `owner | admin | member`, its `useEveAgent` store owns the `ClientSession`, consumes the response stream, advances its in-memory cursor, reconnects interrupted streams, and rejects a second send while its local turn is submitted or streaming. A `viewer` owner may consume the authorized transcript, snapshot, and stream with the composer and HITL controls disabled, but that UI distinction is not the authorization boundary. The same-origin proxy is a streaming reverse proxy, not an Eve SDK relay: after its authorization and create-binding work it forwards allowed request and response bodies opaquely.

For a new conversation, an authorized writer's `useEveAgent.send(message)` performs the underlying create request with the proxy-only conversation header. The proxy binding described in D2 is committed before the browser receives the successful create response. The browser then observes the same fixed `{ sessionId, streamIndex }` through `onSessionChange`; `onFinish` observes the final cursor after the turn boundary. Those callbacks call a thin application mutation that verifies owner, exact stored session id, and an exact current organization Member whose role remains `owner | admin | member`, then writes `stream_index = GREATEST(stream_index, received_index)`. An exact owner downgraded to `viewer` may advance only its in-memory read cursor; its callback or forged request cannot persist the checkpoint. An undefined session, a different id, or a lower cursor never clears or rewinds the binding. Cursor persistence is recoverability metadata, not part of authorization and not a prerequisite for transcript correctness.

For a saved conversation, the browser is initialized with that same fixed session rather than asking the proxy to create a server-side client. Normal authorized follow-ups go through `useEveAgent`, whose internal client targets `/eve/v1/session/:sessionId` and streams from its cursor. Every current and future route below that path first resolves the bound conversation and brand at the proxy and requires the current user to equal its immutable `owner_user_id`, the exact current `Member(brand.organization_id, user_id)`, and stored session id. Transcript, snapshot, and stream are read classes and accept `viewer` only when that viewer is the conversation owner. Follow-up `message` or `inputResponses`, compact, clear, and reset are write classes and require the exact owner with role `owner | admin | member`. Conversation list and metadata queries use the same owner predicate; raw `session_events` are never an organization-wide product read surface and the persisted transcript fallback is reachable only after this conversation authorization. Another same-organization Member, including an owner/admin, has no read or control override in v1. Unknown subroutes are denied until classified. An unknown or mismatched id fails without reaching Eve. V1 has no brand-membership relation.

Cancel is a separate state-reducing class. An exact owner with role `owner | admin | member` may use the normal endpoint. The exact current owner who remains a Member but is now `viewer` may call it only with a non-empty `turnId` taken from the authorized stream/snapshot of the turn being stopped. Eve 0.31.3 scopes cancellation to that turn: a stale or different id is accepted as a no-op and cannot cancel a later unseen turn. Cancellation sends no input. Although Eve returns the session to `waiting`, the viewer still cannot send a follow-up or `inputResponses`; the next request rereads the current Member role. There is no persisted observation grant or new capability row.

This role split is enforced before the request reaches `agent-cmo` and again at each application mutation boundary. V1 does not create a viewer-specific model turn, read-only CMO agent, prompt rule, tool allowlist, or filtered specialist surface. A viewer who exactly owns the conversation gets data-plane reads and the scoped stop operation, not inference with fewer tools.

Manual `compact` and Eve's automatic compaction share one accounting rule. Eve 0.31.3 can satisfy a compaction with framework heuristics and zero provider calls or make one or more summary calls. It emits `compaction.requested`/`compaction.completed` (and the normal manual waiting boundary) but no billable `step.completed`; the compaction events carry no authoritative provider usage, cost, or Gateway `generationId`. The audit hook still stores those raw events under the exact emitting session. They never produce `model_charge` or consume credits: compaction is Branderize platform COGS. The active model's merged `providerOptions` and Gateway user/tags remain, so Custom Reporting observes attributed overhead even though the application ledger intentionally does not itemize it.

Reload correctness does not trust the possibly stale database cursor. Recovery finishes **before** the interactive hook is mounted. The browser first performs an owner-authorized `snapshot()` read from index `0`, obtaining one ordered Eve event prefix and the exact cursor at that durable tail; this read remains available when that exact owner is a `viewer`. It is the normal Eve read path only: it neither persists events nor reconciles the Postgres fallback. If that prefix already ends at the current turn boundary, the writer mounts the hook once with those `initialEvents` and that `initialSession`, while an owner-viewer keeps the same data read-only. If no current boundary is present, a temporary low-level `ClientSession` attaches to the same fixed id at the snapshot cursor and iterates `session.stream()`. The recovery loop appends events and explicitly stops and closes the iterator at the first `isCurrentTurnBoundaryEvent(event)`; `stream()` is not assumed to stop at that boundary. Only then does the writer UI mount or remount `useEveAgent` with the combined events and the temporary client's final state; an owner-viewer receives the combined read state without a composer, HITL response, or cursor checkpoint mutation. An external client is never allowed to advance independently of an already-mounted hook, because it cannot update the hook's private cursor. The recovery path never sends a replacement turn, writes `session_events`, or turns the proxy into a relay/reconciler. If Eve is unavailable or recovery cannot reach a boundary, the owner-authorized console route reads the retained exact-root `session_events` through cursor pagination over their stored order, folds the full persisted prefix through `defaultMessageReducer()`, renders that possibly incomplete result read-only, and can retry recovery.

As in the current CRM, this is one-turn-at-a-time by UI convention rather than a server-side queue contract. For writer roles the composer is disabled while the local client is submitted/streaming or the recovered snapshot classifies the session as working; for `viewer` it is always disabled. There is no Postgres FIFO, active-turn lease, or `conversation_busy` response across tabs. Two nearly simultaneous sends by the same authorized owner are therefore unsupported and may be folded by eve's best-effort inbox behavior; two first sends may also create one rejected unbound physical session before the binding compare-and-swap chooses the authoritative id. V1 accepts that edge instead of adding coordination absent from the CRM. Cursor writes from authorized writer roles converge monotonically with `GREATEST`; a stale cursor can still replay events, but the `session_events.meta_id` primary key removes only repeated delivery of the same event, while distinct events from separate retry attempts may both remain in the observational transcript.

The task dispatcher passes a typed `task_id` to the machine-channel adapter. That adapter alone formats or parses `task:<task_id>`, calls `send()` with `mode: "task"`, and coordinates the hook/post-send fill of the authoritative session id. The prefix is a channel protocol detail rather than a domain identifier.

### D4 — Human conversations and task dispatch have different continuation semantics

For a waiting session, `attach(session_id, { streamIndex })` can send the next input only after the proxy rereads the exact owner Member and finds current role `owner | admin | member`. An exact owner downgraded to `viewer` may attach only to its authorized read stream and cannot send or answer HITL. A completed, failed, expired, reset, or otherwise unavailable human conversation remains readable to its current Member owner from Branderize's retained exact-root event log but is no longer continued.

Sending through a terminal fixed handle fails; it does not create or discover another session. Reset also retires that exact id and leaves the handle pinned to it. Starting again therefore requires an explicit product action that creates a new `cmo_conversations` row, remounts the browser store with `key={conversation.id}`, and lets its first `send()` create a new Eve session. Neither the browser hook nor proxy rebinds the old conversation or follows a replacement automatically.

A durable agent task has no continuation lifecycle. Its single claim attempts one task-mode run with fresh history, state, and sandbox after reloading authoritative task and graph context. Only a stale `running` row without `session_id` may return to `queued` to recover an unproven delivery. If both binding paths missed an accepted session, that recovery may send again after the unrecorded owner releases the token. Once the authoritative id is stored, the same task is never sent again; an explicit product retry creates a new task and session.

The runtime events also have different application meanings. `finishTask` stages the canonical validated `TaskCompletion`, and `session.completed` is the normal success boundary. `result.completed` may mirror the structured output for telemetry. `turn.failed`, `session.failed`, and cancellation are terminal application outcomes. Eve follows `turn.cancelled` with `session.waiting`; the application ignores that one expected waiting boundary and never reuses the token. Other waiting is anomalous telemetry and never resumes, succeeds, or requeues the task. If an event-handler database write fails, the durable stream is reconciled manually without redispatch.

### D5 — Runtime identifiers stay behind the UI/proxy boundary

Brain and domain APIs accept Branderize conversation or task ids, never an Eve id or cursor. The browser Eve client necessarily carries `{ sessionId, streamIndex }`, and the transport places the fixed id in session-route paths, but the conversation-aware proxy treats it only as a lookup key and never as a bearer capability. A scoped cancel additionally carries `turnId`, which narrows a stop request but is likewise not authority. The bridge JWT and Eve route auth authenticate the current principal; they do not prove ownership, current role, or permission for the requested operation. `apps/app` rereads those facts for every request, and product mutations do the same at their application boundary. The proxy-only conversation header is likewise an untrusted selector until row authorization succeeds. A future incompatible Eve client shape requires an explicit schema migration, but it cannot change conversation ids, ownership, transcripts, or graph artifacts. The task channel's token builder remains private to that channel and can evolve independently.

## Consequences

- Human chat keeps the production CRM's useful product/runtime identity split while adopting eve 0.31.3's fixed-ID client contract.
- `cmo_conversations` stores the fixed Eve id and the latest monotonic browser-cursor checkpoint as typed columns, with no opaque JSON or client continuation token; cursor lag can only cause safe event replay.
- CMO conversations keep the CRM's single-owner model plus the current-role gate: listing, metadata, transcript, snapshot, stream, and controls all require exact `owner_user_id`. That owner may create, send, answer HITL, checkpoint, clear, compact, reset, or perform related product mutations only while its current Member role is `owner | admin | member`; after downgrade to `viewer` it may still read and may submit only an exact-`turnId` cancel for a turn already observed. No other organization Member can read or control the conversation in v1, and there is no ownership transfer or sharing ACL. Intents, Decisions, Objects, Actions, and tasks canonically committed from the conversation remain ordinary organization-visible brand projections.
- The composer provides the CRM-style best-effort single-flight UX, but simultaneous sends by that owner from multiple tabs are unsupported; v1 provides neither a durable input FIFO nor server-side per-conversation serialization.
- State ownership is enforced by fail-closed ordinary row access: the top-level `session.started` hook and proxy response path converge on one fixed human session per conversation, the create response is not exposed before fill-or-match binding, a child cannot bind, an unknown or mismatched id returns `404`, and one authoritative machine session id belongs to one task.
- Contract tests cover pre-created-conversation enforcement, stripping the proxy-only selector from create, follow-up, stream, and reconnect requests, upstream create failure, missing/invalid `x-eve-session-id`, top-level hook plus proxy bind convergence, bind-before-response ordering, child-bind rejection, concurrent fill-once loss, and table-drive every session-scoped route through exact owner, brand-to-organization resolution, exact current Member role, exact binding, wrong-organization, and unknown-id cases. `owner | admin | member` owner fixtures may create/send, answer `inputResponses`, use controls, and checkpoint; a downgraded `viewer` owner may read transcript/snapshot/stream but every first/follow-up input, HITL response, compact, clear, reset, cursor, and product mutation fails at its proxy/application boundary, with CMO-targeted requests never reaching Eve. Its cancel requires the exact non-empty observed `turnId`; missing or different ids cannot affect a later turn, removed-Member cases fail, and the post-cancel waiting session still rejects viewer input. Alice/Bob fixtures in one organization prove that Bob cannot list or load Alice's conversation, read its metadata or retained exact-root fallback, obtain snapshot/stream/reconnect access, or reach Eve even when Bob is organization owner/admin and knows every runtime locator. The same Bob may still read the ordinary same-brand canonical Action/Object projections produced from Alice's turn. A stale bridge JWT with a former role does not bypass the fresh Member lookup. The proxy test also proves it does not consume the NDJSON body and no viewer turn reaches a filtered/prompt-constrained CMO. Browser recovery tests prove that the index-`0` snapshot and any needed low-level drain complete before the interactive hook mounts; neither path writes `session_events` or reconciles the database fallback; the drain explicitly stops at `isCurrentTurnBoundaryEvent`; the writer hook receives the combined events and final cursor; the owner-viewer receives only read state; and no replacement turn is sent. Cursor saves remain exact-session monotonic for writer roles. A future `/session/:sessionId/*` subroute must be explicitly classified and inherit the same guard before it can be exposed.
- `cmo:<conversation_id>` and `agent_session_states` are removed from the architecture.
- `task:<task_id>` remains only as the channel-local token of the custom machine channel; callers and domain code never use it as a lookup key or follow-up address.
- Agent tasks and human external commitments do not read or increment `tasks.attempts`; only registered retry-safe direct/automatic kinds may use it under ADR-018 as amended by ADR-019.
- A terminal/reset CMO session is never rebound or transparently replaced; starting again creates a new application conversation and a new eve session.
- Task delivery uses `mode: "task"`. The dispatcher recovers only a stale sessionless handoff and never replaces a run after authoritative session binding.
- `session_events` remain the durable raw log for root and child sessions; there is no separate message table. The permanent observed human transcript is computed on read by selecting only the ordered events whose exact emitting session equals the conversation's bound root id and folding them through Eve 0.31.3's `defaultMessageReducer()`. Raw child events are excluded; the parent-session `action.result(subagent-result)` supplies one root-visible dynamic-tool result, the child `subagent.completed` supplies none, and any later CMO summary is separate. Exact root-event re-delivery is deduplicated by `meta_id`, while distinct root replay attempts may both remain as in the current CRM.
- Exact-root conversation events are retained for the lifetime of the brand. Child events and events from task or other non-conversation roots remain telemetry and may receive a future measured retention policy; such a policy must protect only an exact `session_id` referenced by `cmo_conversations`, not every descendant sharing its `root_session_id`.
- Audit-hook ingestion is explicitly best effort and alerts on every persistence failure. Snapshot/recovery remains Eve's normal read path and never repairs root, child, task, or charge rows; the retained fallback may therefore have gaps. Transcript reads still keyset-page the full persisted prefix and never mistake a fixed 2,000-row tail for the conversation.
- `apps/app` and `agent-cmo` pin the same exact Eve version. Upgrading either requires moving both together after a reducer-compatibility fixture replays representative persisted root event streams through the candidate `defaultMessageReducer()` and verifies the resulting `EveMessageData`.
- Automatic and authorized manual compaction retain the active model's provider options/Gateway attribution and persist their raw lifecycle events, but create no `model_charge`. The ledger governs billable application charges and admission rather than total provider spend; Custom Reporting classifies attributed compaction as expected platform COGS without mutating credits. No generation estimate or lookup, Eve fork, OTel billing path, or reconciler is introduced.
- The initiating auth context freezes the billing brand for the session tree. Every later production turn must present the same scalar in `auth.current`; missing, malformed, or mismatched values fail closed before a Branderize telemetry projection or debit. Self-copies and declared subagents reuse Eve's propagated auth and structural parent/root lineage, so no child-session mapping table is introduced.
- End-to-end session tests cover a top-level generation, a built-in self-copy, and a declared subagent and assert the exact emitting session plus root/parent lineage and same-brand charge. The transcript selector returns only the exact bound root's ordered events; folding them with `defaultMessageReducer()` produces each parent `action.result(subagent-result)` as exactly one dynamic-tool result, excludes matching child `subagent.completed` and every raw child event, and leaves a later CMO summary as a distinct assistant part. Compaction fixtures cover heuristic zero-call and one-or-more-call automatic/manual paths: lifecycle events persist, `compaction.requested.usageInputTokens` remains raw decision telemetry rather than provider billing usage, no billable `step.completed`, authoritative provider usage/cost, Gateway generation id, or `model_charge` is fabricated, and any provider call retains expected Gateway attribution. A mismatch test asserts that no tenant-scoped event or debit is committed.

## Out of scope

This ADR fixes the live Eve-session ownership and current-role invariant, including the exact Better Auth organization-membership check derived through the conversation's brand. Cross-member transcript sharing, conversation ownership transfer, and administrator override are out of scope and fail closed in v1 rather than remaining unspecified. General brand query scoping remains governed by ADR-001: membership is organization-wide, operation authority is role-specific, and `brand_id` is still mandatory, while conversation reads add the exact owner predicate above.
