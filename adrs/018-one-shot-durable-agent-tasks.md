## Context

The durable-agent protocol recorded in ADR-007, ADR-016, and ADR-017 reused one eve conversation across up to three dispatcher claims. That conclusion came from a task implementation that is no longer the relevant CRM precedent for autonomous agent runs.

The current CRM runtime models an autonomous execution as one `AgentRun`: one immutable, permission-bounded invocation, one intended Eve task-mode session, and one terminal result. A five-minute recovery covers only the uncertain handoff before the accepted `sessionId` is known. Once a session is bound, neither a technical failure nor a missing terminal projection causes the same run to be dispatched again. A later manual request creates a new run with a new creator key. A deterministic cadence slot becomes a new exact `(schedule_id, scheduled_for)` occurrence only when that schedule has no queued/running occurrence; otherwise Branderize deliberately coalesces the due evaluation on the schedule without creating a run.

That boundary fits Branderize's durable root work. Each task already has a typed brief, fixed root, capability and budget constraints, canonical Action/Object writes, a structured `TaskCompletion`, and an auditable outcome. Correctness comes from the task and work graph in Postgres, not from inheriting model history or sandbox state from a failed attempt.

Eve 0.31.3 also makes the separation practical. A task-mode session runs to completion or failure and cannot park for human approval. Its Workflow run already survives process crashes and redeploys and resumes from durable step checkpoints; application-level redispatch is not the mechanism that makes an accepted run durable. Interrupted steps may still replay, so graph writes remain idempotent while registered create-only provider-draft preparation must be idempotent, deterministically recoverable, or explicitly duplicate-safe and at-least-once. External commitments are not agent tools (ADR-019).

This ADR applies primarily to `execution_mode = agent`, including ADR-020's Growth Decision-impact task and the CMO `rebuild-marketing-plan` / `advance-marketing-plan` tasks. Its original direct-lane section remains only for retry-safe `execution_mode = direct AND activation = automatic` work: local mutations whose effect, Result Action, and guarded success settlement commit in one Postgres transaction, plus side-effect-free idempotent external reads whose observation, Result Action, and settlement commit atomically after the read. Neither form performs an external write. ADR-019 separately defines `direct AND human` external commitments.

## Decision

### D1 — One agent task is one run

`tasks` remains the single durable work table; no parallel `agent_runs` table is introduced. For `execution_mode = agent`, one task row represents exactly one execution occurrence and stores at most one authoritative eve `session_id`. If it is Intent-bound, that same row also stores the immutable common `intent_snapshot` accepted when the task was actually inserted; if it is Plan-routed, it instead stores null Intent plus exact Plan/Move references. Neither later Intent refinement nor delivery recovery changes either origin. The dispatcher intends one run, but the accepted-before-binding ambiguity in D3 means the database cannot prove that eve never briefly accepted an unrecorded session.

For agent tasks, `tasks.status` is:

```text
queued | running | succeeded | failed | cancelled | superseded
```

A future task row remains `queued`; `due_at` determines whether the UI renders that occurrence as `scheduled` or ready. The recurring calendar rule that may create such a row lives separately in `schedules` under ADR-014 D7. `succeeded`, `failed`, `cancelled`, and `superseded` are terminal and require `finished_at`; the last state is legal only for the narrow `queued → superseded` root-wave-route withdrawal defined below. `queued` and `running` require `finished_at IS NULL`.

The original active-work constraint becomes the broader shared-table index after ADR-019:

```sql
UNIQUE (kind, brand_id, subject_key)
WHERE status IN ('awaiting_approval', 'queued', 'running')
```

It still deduplicates future agentic rechecks and active equivalent ordinary work. Human commitments use a proposal-specific subject identity, so independently intended proposals do not coalesce. A terminal failure releases the logical identity. An ordinary request stores its stable creator key and canonical creation hash, so replay returns the same row, reuse of the key with different input fails, and a genuine retry uses a new key. A created deterministic cadence occurrence is the deliberate exception to semantic coalescing: its trusted subject and replay identity are the exact `(schedule_id, scheduled_for)` pair. A separate partial unique guard on active `schedule_id` permits at most one `queued | running` occurrence per schedule; a later due slot observed behind that task is recorded only in the schedule's coalescing fields and never becomes a run.

V1 does not persist aliases for later requests that merely observe or reschedule somebody else's active row. Such a caller receives the existing task id, but its distinct request key is not bound durably. A retry while that task remains active observes it again; a retry after it becomes terminal may create a new task. This narrow loss-of-response window is accepted instead of adding a `task_request_keys` ledger.

### D2 — Claim for delivery and start in task mode

An agent root may claim a row only when all of these hold:

- `status = 'queued'`;
- `due_at <= now()`;
- `execution_mode = 'agent'`;
- `session_id IS NULL`;
- `worker_key = SELF`;
- `kind IN compiledSupportedKinds`;
- the brand pool has autonomous AI credit available under ADR-011 D4.

The balance check is agent-specific and happens before this claim; it is not part of a generic task predicate shared with direct lanes. At zero or negative recorded balance the row remains `queued`, consumes no drain execution slot, and no eve session starts. A positive read is only admission, not a credit reservation: concurrent roots may each claim a different task, and their winning `step.completed` events post `model_charge` rows while work is already running, so the later ledger may go negative as documented by ADR-011. Under ADR-019's amended drain order, agent rows receive only the batch capacity left after human commitments and retry-safe direct/automatic work. Eligible due agent rows are FIFO by `created_at, id`; `due_at <= now()` is a filter, not the FIFO key.

`/internal/dispatch` is a route of the root's custom machine channel. It authenticates the raw `Authorization: Bearer $DISPATCH_SECRET` poke, returns `202`, and registers the bounded drain with the route's `waitUntil`; the request carries no task, tenant, payload, worker, or target selector. The atomic claim inside that drain changes `queued → running` and records `started_at`. It does not increment `attempts` or install an execution lease. The root then reloads the authoritative task and validates its kind payload plus discriminated common origin. Intent-bound work validates and loads only its immutable snapshot; Plan-routed work validates null Intent/snapshot plus exact same-brand Plan/Move references; origin-free registered work loads neither. It then loads only referenced immutable graph Objects plus current safety/capability facts. Current graph reads cannot replace a pinned Intent or treat Strategy/Plan as preauthorization. It constructs a typed billing context from that claimed row and projects its verified `brand_id` as a trusted non-empty scalar in `taskAuth`. It starts the run through Eve 0.31.3's channel-address API:

```ts
const session = await from(`task:${taskId}:${startedAt.toISOString()}`).send(brief, {
  auth: taskAuth,
  mode: "task",
  outputSchema,
});
```

`task:<task_id>:<started_at ISO>` is the raw channel-local correlation and single-owner address for this claim generation; Eve adds the machine-channel namespace. `started_at` is the claim timestamp already required by the task row, not a caller-supplied nonce or a second run table. The same trusted scalar is included in `taskAuth`. Every bind, task-authorized tool, and terminal projection compares it to the locked row before writing. The address is not a Branderize identifier and is never used for a later conversational turn. The returned `session.id` is stored once as the task's authoritative `session_id`; it is not the "latest" member of a sequence.

Every task therefore starts with fresh eve history, state, and session-scoped sandbox. The root receives continuity only through the current task's accepted kind payload, its trusted Intent/Plan-route/origin-free envelope, referenced artifacts, and allowed work-graph projections loaded from Postgres.

The initiating auth context also freezes billing attribution for the complete Eve session tree. The shared audit hook reads `brand_id` from `ctx.session.auth.initiator.attributes`, requires the production `auth.current` value to be the same scalar, and fails closed without a tenant-scoped projection or charge on missing, malformed, or unequal values. Eve copies both contexts into built-in self-copies and declared local subagents. The hook records each child as its own emitting session plus `ctx.session.parent`'s immediate/root lineage, so a child-session mapping table is neither created nor queried.

The generated root and declared-subagent `agent.ts` files separately call the shared `packages/agents` model-config factory. It explicitly merges all existing provider options, sets `gateway.user` from that same trusted initiating `brand_id`, and adds the registry-derived agent/feature/lane/environment tags. A self-copy reuses its root configuration. Custom Reporting is best-effort observability: an Eve dynamic-resolver fallback may be untagged, but cannot suppress or rewrite the authoritative winning `model_charge`.

Automatic compaction inside this one-shot run is not a second billable task step. Eve 0.31.3 may compact with zero, one, or several provider summary calls and emits raw `compaction.requested`/`compaction.completed`, but no billable `step.completed` and no authoritative provider usage, cost, or Gateway generation id for the compaction itself. Those lifecycle events remain in `session_events`; they create no `model_charge`, consume no task credits, and do not affect the pre-claim admission decision. The active model's merged provider options/Gateway attribution remain on any compaction call so Custom Reporting classifies the spend as expected Branderize platform COGS. The application never estimates it or recovers it through generation lookup, a framework fork, OTel billing, or reconciliation.

### D3 — Recover only an unproven delivery

Like the current CRM, a `session.started` hook immediately attempts to bind `ctx.session.id` to the task using trusted task context; it does so only for the top-level session where `ctx.session.parent` is absent. A self-copy's child session never participates in task binding. The post-`from().send()` update uses the returned top-level `session.id` as a second path for the same existing fill-once write. This materially narrows the gap between eve accepting delivery and Postgres knowing its id.

The dispatcher may move an agent task from `running` back to `queued` only when `session_id IS NULL` and `started_at` is older than the five-minute delivery window. In the same transition it clears `started_at`, `completion`, and `next_*` before another claim. The next claim records a new `started_at`, therefore receives a new channel address and trusted generation fence. This recovers a process death between the database claim and persistence of eve's accepted session without letting either delivery inherit or mutate state under the other's claim.

Once `session_id` exists, that task is never dispatched again. A known `send()` rejection, `turn.failed`, `session.failed`, or cancellation produces a terminal `failed` or `cancelled` task. A run with a `session_id` but no projected terminal event remains `running` for investigation; the dispatcher must not guess that starting another LLM run is safe.

The terminal event may race persistence of the returned `session_id`. Event handlers therefore correlate the task from trusted channel context, not by searching for an id that may not be stored yet. The top-level `session.started` hook may only fill a null id on the current `running` task whose `started_at` exactly matches trusted auth; a hook with `ctx.session.parent` writes no task binding. The post-`send()` path uses the same claim tuple and normally performs that fill; it may also fill the id on the already-terminal same generation as a cheap auditability improvement over the CRM's guarded update. Neither path may attach to `queued`, cross a generation, reopen the task, or rewrite its outcome.

There is still an unavoidable narrow ambiguity if eve accepts a session but both binding paths fail: recovery can start another physical session because its new `started_at` deliberately gives it a different address. Branderize therefore guarantees one authoritative bound `session_id` and one write-authorized generation, not exactly one physical acceptance. A late session from the recovered generation may still consume provider work, but its stale `started_at` cannot bind, execute a canonical task mutation, or settle the task. Idempotent tools and first-terminal-writer-wins settlement remain defence in depth.

This separates a known delivery rejection from failure to persist an already accepted handoff. The current CRM wraps `send()` and its post-send `sessionId` write in one `try` and labels an exception from either operation `DELIVERY_FAILED`; Branderize instead treats a post-acceptance binding failure as the recoverable ambiguity above because the eve run may already be executing. The `session.started` hook is the primary binding path in both systems.

V1 uses the existing claim `started_at` as an end-to-end handoff-generation fence instead of adding a `handoff_id`. Dispatch, the channel address, trusted auth, root binding, task-authorized tools, and terminal handlers all carry and compare the same value. A partial comparison would be invalid: missing or mismatched generation context fails closed before a task mutation or billing projection. The five-minute window still bounds when a second physical acceptance can begin, while the generation fence prevents the older unbound delivery from becoming authoritative.

`attempts`, `MAX_ATTEMPTS`, agent execution leases, reclaim after session acceptance, and `retireExhausted` do not apply to `execution_mode = agent`.

### D4 — Stage `TaskCompletion`; settle on `session.completed`

Every durable root exposes an authored deterministic `finishTask` tool. Trusted eve session context supplies `task_id`; the model cannot select another task. The top-level root owns settlement even when it uses built-in self-copies. A child is identified structurally by `ctx.session.parent`; before reading or locking the task, `finishTask.execute` rejects that context with the deterministic application error `FINISH_TASK_ROOT_ONLY` and stages nothing. The tool may remain visible to the child because visibility is not authority. Optional dynamic omission is only UX and is never required for correctness.

For a top-level root session, the tool:

1. locks the current `running` task;
2. validates the common payload and the `result` against that kind's registered schemas; a non-null common `intent_acceptance` additionally requires `status = completed`, a non-null Intent snapshot with non-empty acceptance criteria, and schema-valid same-brand Evidence references. Trusted code derives its exact `intent_id`/`intent_revision` from the snapshot; a Plan-routed, origin-free, or statement-only task is rejected if it attempts one;
3. validates the caller-selected `output_object_ids` as duplicate-free, invokes the kind's pure `requiredOutputObjectIds(validatedResult)`, and replaces the stored field with the canonical sorted set-union. It validates every resulting id under the task's brand and output contract and requires its producing Action to name that exact task; the list need not equal the complete task-linked Object inventory. Omission of a valid required id is normalized, while an invalid required reference fails;
4. fill-or-match stages the normalized completion in the task's typed `completion` JSONB without making it terminal.

Staging is fill-or-match under that task lock and compares the normalized completion, not the model's pre-normalization omission. If no completion is staged, `finishTask` stores the canonical validated value; replay that explicitly includes a required id previously added by code therefore matches the same stage, while a genuinely different normalized value—including a different optional selected-output set—fails with a deterministic conflict and cannot replace the first stage. This handles a replayed durable tool step without turning the selected list into an inventory seal. Task-bound writes still require `status = running`: a write that commits before terminal settlement remains in the full graph inventory, while one that loses to terminalization writes nothing.

Specialist-root self-copies retain all other inherited work tools. They may commit canonical task-bound work and return summaries, result data, candidate output Object ids and created task ids to the parent. The parent selects the final task-linked deliverables, then calls `finishTask` once with the root-level `TaskCompletion`. This is an execute-time authority check over Eve's existing session tree; it introduces no new table, lease, fill-once column, output-inventory cache, or separate handoff-generation field.

`finishTask` returns the normalized staged completion, which the root mirrors through its configured output contract. Eve may emit `result.completed` for that structured return, but that event is observability rather than the database settlement boundary: the value staged by `finishTask` is canonical. Diagnostic comparison normalizes the returned value through the same registered result/output pipeline before declaring a mismatch, and any real mismatch still cannot replace the stage.

The machine channel settles only from the task's authoritative bound top-level session; child-session terminal events remain telemetry and usage:

- authoritative `session.completed` plus a valid staged completion changes `running → succeeded` and retains that exact normalized `completion` as the terminal domain outcome;
- authoritative `session.completed` without a valid staged completion changes `running → failed` with `MISSING_TASK_COMPLETION`;
- authoritative `turn.failed` or `session.failed` changes `running → failed`;
- cancellation of the authoritative session changes `running → cancelled`.

Runtime/session settlement transitions are idempotent and guarded by `status = 'running'`; the first terminal writer wins. For **agent rows**, administrative cancellation may instead change either `queued` or `running` to `cancelled`. This is not a shared direct-task rule: ADR-019 permits direct/human cancellation only from `awaiting_approval` or `queued`, atomically with its Cancellation Action, and never after `running`. `completed`, `partial`, and `blocked` remain deliberate domain outcomes inside the staged `TaskCompletion`, and all three produce execution status `succeeded`. A technical failure is never synthesized into `blocked`.

This is one deliberate fail-closed adaptation of the current CRM runner. CRM permits `session.completed` to fall back to a generic summary when `finish_run` did not stage one. Branderize cannot do that because the typed completion carries the normalized Object references and kind-specific result required for trusted settlement; accepting a fallback would publish an unverifiable result.

Cancellation is an application policy layered on eve's lifecycle. If an accepted turn is cancelled, `turn.cancelled` changes the application task to `cancelled`; eve 0.31.3 then emits its normal `session.waiting`, which is expected in this one case but is ignored and its address is never reused. A canonical mutation authorized by execution of the task itself includes `status = 'running'` in the transaction that commits it. The sole post-terminal CMO transduction `task_questions_resolved` is not task-execution authority: its `task_id` is only a source link and its separate boundary instead requires the exact row be `succeeded` with retained `partial | blocked` completion and non-empty questions. It changes only the projection. A registered create-only provider-draft operation follows its trusted replay contract: stable key, deterministic lookup, or accepted duplicate-safe at-least-once creation. External commitment execution is outside this session and follows ADR-019. Other `session.waiting` events remain anomalous telemetry and never succeed, requeue, or continue the task.

Missing onboarding information does not make a specialist root interactive. The root stages `TaskCompletion(partial | blocked)` with typed `open_questions` and reaches terminal `session.completed`. The retained terminal `completion` makes one read-only task card appear in **Open questions** until a subtype-unique `task_questions_resolved` Action closes that immutable bundle. **Rispondi al CMO** opens or creates only a top-level conversation owned by the current non-viewer Member, with the exact task supplied as trusted turn context; it never attaches to, sends into, or resumes the specialist session. Merely opening or sending that turn closes nothing, and answering does not imply a rerun. After canonical answers exist, any further specialist refinement is a new one-shot task requested through its ordinary current guards. Context.dev Brand Context v0 ingestion itself occurs synchronously in `apps/app` and is outside this task lifecycle (ADR-012, ADR-017).

`finishTask` stages only the task-level `TaskCompletion` and result projection; it is not a publication gate for graph writes. Once a task-bound `produceObject` transaction has verified that the task is still `running`, evaluated Policy from the accepted common origin—pinned Intent snapshot, null structure plus exact Plan/Move, or the registered origin-free branch, always with current restrictions—and committed its Action, Object, and any supersession, that write is canonical. A later `turn.failed`, `session.failed`, cancellation, or terminal completion without a valid staged `TaskCompletion` changes the task outcome but does not supersede, dismiss, invalidate, or roll back already committed Actions or Objects. Those writes retain their own task/origin provenance and idempotency and remain discoverable through their task link. The task status answers whether the overall run completed its declared contract, not whether every earlier tool call still exists.

Likewise, persisted `TaskCompletion.output_object_ids` is the normalized final-deliverable projection: the union of the root's optional selection and the kind-required principal outputs. It neither activates nor inventories graph writes. The full authoritative set remains queryable through `objects.produced_by → actions.task_id`, including omitted, intermediate, superseded and self-copy-produced Objects. UI may foreground the normalized outputs and separately expose activity/history. Plan advancement always rereads canonical graph and task state and never uses selection membership as evidence that a Move is ready or complete. Because completeness is not promised, no late-write seal or reconciliation between the selected list and full inventory is required.

Eve awaits channel event handlers but logs and absorbs their exceptions. Consequently the transitions above describe the healthy projection path, not an exactly-once guarantee: a persisted terminal stream event whose database projection failed can leave the task `running`. That state raises an alert and is reconciled manually from the durable stream and staged result; it is never repaired by starting another agent run.

ADR-020's `verify-roadmap-decision-impact` specializes this same agent lifecycle. The human `recordDecision` transaction inserts the measurable Decision Action/Object/supersession and exact future origin-free Growth task together. At or after `due_at` and subject to the ordinary credit gate, Growth opens one task-mode session, may use any available measurement read tools, writes a current `metric_observation` through `record_evidence`, and stages `TaskCompletion.status = 'completed'` with `intent_acceptance = null`, `result.judgment = supported | not_supported | inconclusive`, its rationale and required Evidence reference for a conclusive judgment. Its null common origin makes any non-null `intent_acceptance` fail validation before staging. Successful terminal projection atomically appends the Growth-authored Verification Action linked to the immutable Decision and task, stores `result_action_id`, and applies the guarded terminal transition without changing any Intent. Only an active `not_supported` head also creates or observes the registered origin-free `decision-reconsideration` CMO task in that transaction. Its one-shot completion is `recommended` with the exact same-task report or `obsolete(decision_inactive)`; terminalization of the causal origin Intent is not an obsolete reason and grants no authority. Neither kind can supersede the Decision or uses a recurring schedule, `scheduleRecheck`, or `next_*`.

`rebuild-marketing-plan` uses the same one-shot lifecycle under the CMO root and normal credit gate. Its trusted payload pins one exact brand-wide Strategy Decision, while the CMO reads current active Intents and selects other current inputs during the run; none is frozen in the queued task. It may commit additional task-bound Evidence and Move Candidate Objects before publication. Those preparatory writes are ordinary canonical tool-write boundaries and remain valid provenance even if the later Plan call or session fails. The final `publishPlanAndRoute` call locks and verifies the rebuild task is still `running`, then locks and verifies the Strategy and current Plan head in the fixed `rebuild task → Strategy → Plan` order, compares canonical submitted Intent refs to one ordered read of current active `{ id, revision }` rows, validates the Plan and every registered route, rejects duplicate derived routes, appends the CMO Action with trusted typed planning Intent snapshots and the canonical complete selected-route mapping, creates the immutable `marketing_plan`, supersedes the prior Plan, and creates or observes all selected internal/preparatory tasks in one transaction. No Intent preauthorization enters those planning snapshots and no external commitment executes from this routing step. If the task is no longer running or any route is invalid/cannot be materialized, the Plan and every new routed task roll back. If the planning refs changed, it writes nothing and asks the same run to reload; if the Strategy changed, it writes nothing and trusted settlement may accept only `TaskCompletion.status = 'completed'` with `result = { outcome: 'obsolete' }` after reconfirming that fact. If another Plan won while the Strategy remains current, the write returns `stale_head` so the CMO must reload and deliberately retry inside the same run; it is not a terminal completion result. The `publishPlanAndRoute` receipt carries the captured Intent refs and distinct task ids from the committed `created | observed` mapping; staged `TaskCompletion.result = { outcome: 'published', plan_object_id }` references the Plan without duplicating either. A later session failure does not roll back a Plan/tasks that already committed. `TaskCompletion` references the resulting Plan Object id but is not its activation gate.

After validating the complete Plan and route request but before any canonical insert, that same transaction processes only explicit `excluded_moves`. It starts from exact root-route task ids in non-null root-origin entries of the previous Plan-producing and later wave Actions. In stable task-id order it conditionally changes a matching route from `queued → superseded`, sets `finished_at` plus `outcome_code = 'plan_move_excluded'`, and records every returned id per Move in the new Plan Action/result. The trusted predicate requires the exact same-brand Move, null Intent, non-null Plan/Move, `agent/automatic`, no retry/replacement/schedule lineage, `parent_task_id` equal to the original routing task, and a referenced Plan/wave Action whose `created` mapping names that row. It never follows an observed lateral descendant with null root origin. A concurrent agent claim and publication serialize on the row: claim-first leaves the row `running`; publication-first makes the claim return zero. Any later failure in Plan supersession or route materialization rolls these transitions back with the rest of publication. Omission, direct work, human commitments, running work and terminal work remain untouched.

Move dependency edges remain immutable Plan content only. `publishPlanAndRoute` creates the initial ready-now routes selected by the CMO, and `advancePlanAndRoute` may create later waves against the same Plan only while its Strategy and planning Intent revisions still match the current brand heads. Those tasks enter the ordinary one-shot lifecycle without blocker fields or dependency-aware claim SQL. Task `succeeded` cannot stand in for Move completion because its domain result may be `partial` or `blocked`, and canonical outputs can survive a later task failure. Only after ordinary Plan-routed terminalization commits, a separate best-effort creator may create or observe a general `advance-marketing-plan` task. Preflight derives a candidate current Plan and stable candidate-Plan/source-task creator key. The transaction resolves any exact inserted-task receipt immediately after that key's advisory lock; only on a miss does it share the general identity lock, hold the candidate Plan `FOR SHARE`, recheck current head plus the Plan-needs-Rebuild projection, and proceed when either that Plan's producing/wave Action maps the source as `created | observed`, or the source's immutable parent chain reaches the first such mapped ancestor. A cycle-safe plain traversal requires source through anchor to be same-brand, null-Intent, and on the exact same non-null origin Plan/Move pair; that pair may name P1 while current P2 adopted the anchor. It never holds the source/ancestor rows or locks/waits for an existing advancement task. A concurrently committed Rebuild therefore wins before the check or waits until the serially valid signal commits; the creator never inserts against a Plan already stale at its validation point. Descendant ancestry is solely wake-up provenance and grants no mapping, readiness, root-origin, withdrawal, or Policy authority. Observing an already-active evaluation stores no pending signal or receipt. An observed/rescheduled descendant whose preserved parent chain reaches no adopted anchor likewise stores no alias and needs human recovery. V1 accepts those remaining pre-enqueue/absorbed/unqualified-observation liveness gaps and provides authenticated **Ricontrolla** plus a distinct per-Move **Avvia comunque** override; it has no failure cascade or lossless automatic cross-Move wake-up.

`advance-marketing-plan` itself follows the same one-shot agent lifecycle and credit gate. Its origin-free trusted payload pins the exact current Plan and optionally one human-overridden included Move. Dedicated creators enforce `signal/Ricontrolla → evaluate` and `authenticated override Action → human_override`; generic enqueue cannot create either payload directly. Every creator and `advancePlanAndRoute` reject a Plan whose Strategy or active-Intent `{ id, revision }` set differs from its producing Action, requiring explicit Rebuild while leaving already accepted work untouched. For an eligible Plan, `advancePlanAndRoute` locks the running task, pinned Strategy, then active Plan head, validates the complete route list, and atomically appends the subtype-unique same-task `plan_wave_evaluated` Action plus the `created | observed` tasks without creating or superseding a Plan Object. General mode may settle normally with `no_ready_moves`. Targeted human-override mode may route only its exact Move and must produce at least one valid route. It cannot reinterpret the request as another readiness judgment: `finishTask` accepts `obsolete` only for a stale Plan and `blocked` only with a closed registry/capability code re-derived by trusted settlement; an unsubstantiated no-route completion is invalid and fails technically. The override never changes claim, credit, capability, Policy, or external-approval rules.

### D5 — Agent-chosen rechecks and deterministic cadences stay distinct

The constrained `scheduleRecheck` protocol remains. Its first cross-kind future booking commits during the tool call and survives a later source failure. Only a running equivalent self-recheck stages one `next_due_at`, `next_payload`, and `next_rationale` tuple on itself through the trusted deterministic tool.

The same transaction that changes the current task to `succeeded` may materialize the staged successor with a stable idempotency key derived from the completed source task, then clear `next_*`. The staged tuple contains only the validated kind template and rationale, not a copied common-origin envelope or parent. If the completion also carries `intent_acceptance.judgment = satisfied` for its pinned Intent revision, terminal settlement first appends/resolves that Verification and attempts the guarded Intent close. A winning close settles the Intent, clears `next_*`, and creates no successor; the task still succeeds. If the close loses because the verified revision is stale, the Verification remains historical and successor eligibility is evaluated against the current Intent normally. `not_satisfied` and `inconclusive` persist their Verification but never attempt the close, so they proceed directly to that normal eligibility check. An actual successor insertion from an Intent-bound task therefore requires the canonical Intent still be `active`, resolves its latest revision and builds its new immutable snapshot at that boundary; if it is no longer active, settlement preserves the source task's success, clears `next_*`, and records no successor. A successor from a Plan-routed task keeps null Intent and the exact source Plan/Move pair. A genuinely inserted successor receives immutable `parent_task_id = completed_source_task_id`; if an equivalent active booking won concurrently, settlement observes that booking and preserves its existing compatible origin and parent rather than rewriting either or rolling back the current task's success. Only a distinct explicit Intent declaration changes origin branch. The postcondition is at most one equivalent active booking, not necessarily a newly inserted row. A `failed` or `cancelled` transition clears `next_*` and creates no successor. This preserves the existing product rule that an agent-authored cadence continues only after the root deliberately completes its current work.

This success-coupled mechanism remains only for bounded decisions made by an agent through the deterministic tool. It is not the implementation of a daily or weekly product cadence.

For deterministic product cadences, Branderize keeps the current CRM's separate durable trigger/occurrence boundary but adds an explicit no-overlap policy. Before its ordinary drain, the responsible root considers only exact registered schedule keys compiled for itself, compare-and-swaps and advances ADR-014 D7's human-enabled `schedules` row, then locks any `queued | running` occurrence for that schedule in the same transaction. If one exists, it inserts nothing and records the evaluated due slot through `coalesced_due_count` and `last_coalesced_for`. If none exists, current null-structure Policy either inserts the exact brand-wide origin-free `(schedule_id, scheduled_for)` task or records a typed `not_allowed` evaluation with zero task. The exact pair remains the replay identity only for an occurrence actually created; the coalescing fields are a summary, not a backlog or alias ledger.

The schedule CAS advances on every successful create, coalesce, or Policy `not_allowed` branch and is never changed by the task's later outcome. Registry, Policy-evaluation, Action, or insertion errors roll the advance back. If materialization locks the active row first, that slot coalesces before terminalization; if terminalization commits first, the materializer sees no active row and may evaluate the due occurrence. The partial unique active-schedule index is the final defence. With no active occurrence after enabled-template downtime, only the oldest missed slot is evaluated and the next cursor is computed directly after `now`; intermediate misfires are skipped. Enable/re-enable always recomputes the first strictly future slot, so disabled time never becomes catch-up. With an active or credit-blocked queued occurrence, later due evaluations advance and coalesce. Terminalization does not synthesize an immediate catch-up; only a future due cursor may create the next task. The daily or weekly calendar is evaluated at a local wall-clock time in its human-configured IANA timezone, not by adding a fixed number of minutes. It uses neither `next_*` nor `scheduleRecheck`.

### D6 — Only retry-safe direct/automatic work retains bounded retry

`execution_mode = direct AND activation = automatic` may continue to use its two-minute lease, `attempts`, three-claim ceiling, reclaim, and exhaustion behavior only for registered retry-safe deterministic handlers. A mutating handler is eligible only when the effect is local to Postgres and its local effect, Result Action, `result_action_id`, `finished_at`, lease cleanup, and compare-and-swap `running → succeeded` all commit in one transaction. The terminal update includes `WHERE id = task_id AND status = 'running' RETURNING`; zero returned rows abort and roll back the entire transaction, including the effect and Action. The effect uses a stable key derived from the durable task/effect identity and an idempotent insert or upsert as a second replay defence; that key does not replace the terminal compare-and-swap.

A side-effect-free idempotent external read may occur before that transaction because it changes no provider state. Its validated observation and Result Action still commit in the same Postgres transaction as `result_action_id`, `finished_at`, lease cleanup, and the guarded `running → succeeded` transition; a zero-row compare-and-swap rolls all of those local writes back. No `direct/automatic` handler performs an external write. Within the remaining bounded drain capacity after human commitments, eligible rows are FIFO by `created_at, id` and precede agent rows. ADR-019 resolves the separate case: `direct AND human` external commitments use no lease, attempts, reclaim, or `MAX_ATTEMPTS`.

The explicit status mirrors that existing lifecycle without changing its mechanics:

- the first claim changes `queued → running` and increments `attempts`;
- a failed handler leaves the unfinished row `running`; after lease expiry it is reclaimable below the limit;
- a reclaim renews the lease and increments `attempts` while status remains `running`;
- successful deterministic completion changes `running → succeeded` only in the same transaction as its local effect or observation and Result Action;
- exhaustion retirement changes `running → failed` and clears `next_*`. For a provider Verification poll, the retirement transaction also appends the terminal provider-outcome Verification Action `unverified(technical_exhaustion)` required by ADR-019.

For every provider-outcome terminal branch, that settlement transaction commits before any Plan wake-up. A separate best-effort ADR-021 creator receives only the immutable Verification Action id, derives and validates the originating commitment through the poll and accepted Result Action, and may create/observe an origin-free `advance-marketing-plan(evaluate)` under a Verification-scoped key. `pending` never invokes it. No enqueue failure, replay conflict, stale Plan, or invalid causal chain can roll back the poll task or Verification Action.

Only retry-safe direct/automatic rows consult `MAX_ATTEMPTS` or use `leased_until`. Generic claim and retirement helpers must branch on both `execution_mode` and `activation` before reading either field.

### D7 — Database checks hold the shared-table state machine

For agent and direct/automatic rows, the migration encodes these invariants; ADR-019 adds the direct/human checks below them:

- for an agent row, `status IN ('succeeded', 'failed', 'cancelled', 'superseded')` if and only if `finished_at IS NOT NULL`; for direct/automatic the terminal set remains `succeeded | failed | cancelled`;
- the row-local CHECK for an agent `superseded` row requires `activation = 'automatic'`, `outcome_code = 'plan_move_excluded'`, `started_at IS NULL`, null Intent/snapshot, non-null Plan/Move, null retry/replacement/schedule lineage, no session/`completion`/`next_*`/lease state, and `attempts = 0`; no ordinary claim, retry, cancellation, or generic supersession helper may produce it;
- equality between a root wave row's `parent_task_id` and the origin rebuild/advancement task named by the Plan/wave Action's `created` mapping is cross-table provenance: the routing boundary proves and records it in the trusted transaction and integration tests cover it; a normal PostgreSQL `CHECK` does not claim to enforce it;
- `status = 'running'` requires `started_at IS NOT NULL`;
- `status = 'queued'` requires `started_at IS NULL`, and a queued agent row also requires `session_id IS NULL`;
- agent rows require `attempts = 0` and `leased_until IS NULL`;
- direct rows require `session_id IS NULL` and `completion IS NULL`; only direct/automatic rows may have lease/attempt state;
- every terminal row has `leased_until IS NULL`;
- typed `completion` JSONB is null for direct rows and for agent rows in `queued | failed | cancelled | superseded`; it may be non-null while an agent row is `running` after `finishTask`, and every agent `succeeded` row requires and permanently retains it. Settlement does not copy it into an unnamed second outcome field;
- `next_due_at`, `next_payload`, and `next_rationale` are either all null or all non-null, and a non-null tuple requires `status = 'running'`;
- nullable `intent_id` and `intent_snapshot` are null together; when present, the same-brand foreign key is valid, the snapshot's id agrees with the relational id, and the snapshot passes the common schema. The snapshot is immutable after insertion and is never stored inside `payload` or `next_payload`;
- nullable `plan_object_id` and `move_candidate_id` are null together and use same-brand Object foreign keys. A directly Plan-routed row requires that pair, null Intent/snapshot, registered non-Intent support and exact type/inclusion validation; its trusted subject is namespaced by `plan-route:<move_candidate_id>`. A task cannot carry both an Intent and Plan-route origin;
- `schedule_id` and `scheduled_for` are either both null or both non-null; the non-null pair requires `execution_mode = 'agent' AND activation = 'automatic'`, null ordinary creator key, null Intent/snapshot, null Plan/Move, null parent/retry/replacement lineage, and a registry-derived origin-free payload/subject. It is unique, identifies a created deterministic cadence occurrence, and never shares the general request-key alias semantics;
- partial uniqueness on non-null `schedule_id` while `status IN ('queued', 'running')` permits at most one nonterminal occurrence for that schedule. Scheduled agent tasks have no other nonterminal status.

ADR-019 additionally requires `agent -> activation = automatic`, rejects `agent/human`, and requires direct/human rows to have zero attempts, no lease/session/stage/`next_*`, mandatory revision/payload hash, and an Approval Action from `queued` onward. Every recovery and terminal transition clears the lane-specific transient fields that must not survive it. Cancellation is lane-specific: agent cancellation follows D5, while direct/human cancellation follows ADR-019 and cannot target `running`. These checks keep one shared table implementable without adding a parallel run table.

## Consequences

- An authoritatively bound agent run is never replaced because an application lease expired; agent rows have no execution lease. Only the unbound handoff ambiguity in D3 can produce more than one physical acceptance for the same row.
- Agent failures become visible terminal records instead of silently consuming another inference run.
- A retry is auditable as a new task with a new task id and creator idempotency key.
- A genuine retry or newly inserted successor of Intent-bound work snapshots the then-current Intent revision; Plan-routed work instead preserves null Intent and its exact Plan/Move origin. Replaying or observing an existing task preserves its original origin, so queued/running work cannot change meaning beneath a one-shot session.
- A deterministic cadence is auditable as one durable schedule plus only the immutable task occurrences that were actually materialized. At most one may be queued/running per schedule; suppressed due evaluations leave only monotonic coalescing metadata, not a backlog. One occurrence's failure never pauses or advances the calendar a second time.
- Eve owns durability inside the accepted run; Postgres owns enqueue idempotency, domain state, and the handoff record.
- Billing attribution is carried by trusted initiating auth and Eve's session tree rather than a parallel child-session registry. Root and self-copy steps are observed by the root's inherited audit hook; every generated declared subagent mounts that shared extension in its own isolated hook scope.
- `finishTask` records domain completion only from the top-level root before its authoritative `session.completed` publishes the terminal task transition. Self-copy outputs flow back to that parent; child completion never settles the task.
- Successful task-bound graph writes are canonical at their own commit boundary. A failed, cancelled, or incomplete run may therefore retain Actions and Objects it produced before termination; no task-level rollback or compensating supersession is implied.
- Human CMO conversations continue to persist their Eve-generated fixed `session_id` plus an opportunistic checkpoint of the browser-owned `stream_index` on the owning conversation under ADR-016; this ADR changes no human-chat behavior.
- Direct deterministic work has two registry-selected lifecycles in the same table: bounded retry only for retry-safe automatic kinds, and ADR-019's one-shot human/external commitments. An automatic mutation is retry-safe only when its stable-key local effect, Result Action, and guarded success settlement are one transaction; an external read remains side-effect-free and commits only its observation, Result Action, and settlement atomically. Both roll back every local write when the terminal compare-and-swap loses, and neither writes externally. Tests and helpers must branch on both mode and activation.
- Decision-impact Verification reuses the one-shot agent lifecycle. Its origin-free future task is part of the human Decision transaction; its terminal Growth-authored Action is part of task settlement, cannot mutate an Intent, and technical session failure is visible task failure rather than a negative marketing judgment.
- Marketing Plan rebuild and advancement use separate one-shot CMO agent kinds under the ordinary credit gate. Recording a Strategy creates the initial rebuild atomically; console Rebuild creates a new Plan version, while Ricontrolla/Avvia comunque request same-Plan advancement. A committed Plan or wave Action/tasks remain canonical even if the enclosing task later fails.
- Branderize does not add an immutable agent-version table in v1. Its roots are internal product code, and `compiledSupportedKinds` remains the deploy-skew boundary. This is an explicit, low-cost divergence from the CRM's user-deployed version model.

## Alternatives considered

- **Keep conversation mode and three claims** — rejected: it conflates an application retry with continuation of an accepted durable run, permits overlapping inference after lease expiry, and no longer follows the relevant CRM execution model.
- **Three fresh task-mode sessions on the same task row** — rejected: this is neither the CRM one-shot unit nor a clean audit model; one row would have multiple session identities and competing terminal results.
- **Create a separate `agent_runs` table** — rejected for v1: the existing task already is the durable execution occurrence, so another layer would duplicate identity without buying a required capability.
- **Add a per-claim `handoff_id` fence** — deferred: it would close the accepted late-callback race only if every dispatch update, trusted eve callback, task-bound tool, and terminal handler compares the same generation. The current CRM runs without it, and v1 copies its narrower hook-plus-timeout discipline instead of introducing a partially enforced protocol.
- **Persist every coalesced request key in a `task_request_keys` ledger** — not adopted in v1: active-work dedup still returns the existing task, but exact replay after that task becomes terminal is guaranteed only for the request that created it. The accepted failure window requires a lost response followed by settlement before the caller retries.
- **Store a deterministic daily/weekly cadence as a future task that reschedules itself** — rejected: the task is one execution occurrence, so coupling the next slot to its outcome either stops a product cadence after failure or conflates it with agent-authored `scheduleRecheck`. The separate schedule cursor follows the current CRM boundary and advances whenever the due-evaluation transaction commits, whether that transaction creates an occurrence or coalesces behind the active one.
- **Apply one retry policy to every direct kind** — rejected by ADR-019: the CRM's local transactional `AgentAction` safety does not generalize to provider writes. Internal transaction-safe work may retry; human external commitments make one automatic call and stop on ambiguity.
