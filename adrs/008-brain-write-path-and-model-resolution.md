## Context

A second dig into [trycompai/crm](https://github.com/trycompai/crm) (`lib/facts.ts`, `channels/crm.ts`, `lib/enrichment.ts`, `lib/model.ts`, `packages/db/src/settings.ts`, `agent/agent.ts`, `docs/agent.md`) surfaced disciplines that their incident history produced. These are not features to copy but rules whose violation they already paid for. Three clusters: how the write path behaves, how tools are designed, and how the model is chosen.

## Decision

### 1. Write-path rules (`packages/brain`)

The single write path (ADR-002) enforces in code — never in prompts:

- **Never overwrite a human.** For immutable Object heads, human ownership is computed from *provenance* (the Actor type of the producing Action), not from a flag on the row. A system bootstrap may be superseded by later specialist work; neither system nor agent code may supersede a human-authored Object head. Intent authorship is the deliberate exception to that inference: it comes from immutable `intents.author_actor_id`, because a human-authored Intent may be transduced by a CMO-authored Action; its lifecycle is protected by ADR-012's status/revision guards. ADR-020 makes Decisions stricter still: every active v1 Decision is recorded or superseded only by an authenticated human `recordDecision(expectedHeadId)` boundary. Agents and system operations may emit typed recommendations or Verifications, never canonicalize a Decision.
- **Never re-offer an exact dismissal.** For graph Objects, normal supersession/dismissal remains explicit. For an executable proposal, ADR-019 moves the lifecycle to the direct task: terminal `dismissed` plus a Dismissal Action blocks the same `(brand_id, kind, canonical payload hash)` until an explicit human reopen Action.
- **Never write without evidence.** Below the evidence floor, content is not even stored. Claim grading (`proven / plausible / assumption`) is priced by the write path from what the tools *observed* — no tool accepts a confidence offered by the model as proof.
- **Mutations are one transaction**: supersede the prior Object and create the new one atomically. A successful `produceObject` call commits its Action, Object, and any supersession as canonical state immediately; the enclosing agent task is not an outer transaction. A later task failure, cancellation, or missing/incomplete `TaskCompletion` neither rolls back nor invalidates that committed write. Each tool-level write carries its own provenance and idempotency, while task status describes the run as a whole. Current state is then read directly through the indexed active-Object query; there is no materialized projection to refresh or update. *"Never overwrite a human" is only true if the transaction says so* — hence integration tests against real Postgres.
- **Intent refinement is a guarded mutation, not an overwrite**: `refineIntent` locks the exact same-brand row, compares `expectedRevision`, and commits typed criteria/constraints, one revision increment, and one before/after `intent_refined` Action atomically. Zero updated rows return `stale_intent` and commit no Action. In an authenticated product mutation the human is the Action Actor; in CMO chat the explicit human reply is already the authorization, the CMO is the producing Action Actor, and the current human plus trusted conversation/session/turn/call locator are frozen as causal and Policy provenance. The interactive tool rejects viewer, autonomous/task, child, consultative, and system contexts at execution time; visibility or prompt wording is not the boundary. It does not edit the statement, create an `intent_versions` table, or imply a second confirmation. Intent-bound task insertion constructs a trusted immutable snapshot from the latest row; its writes later evaluate that pinned input rather than reloading a newer objective. Plan-routed work is deliberately not Intent-bound: it evaluates null structure, current brand restrictions and exact trusted Plan/Move context, and cannot produce an Intent-acceptance judgment or settle an Intent.
- **Tool results instruct the model.** Creating a human-activation task returns: *"Prepared for human review. This is a normal outcome, not a failure."* A model told “rejected” will game the score; a model told “normal outcome” moves on. The returned task id is an observation, not authority to queue or execute it.

### 2. Tool design rules

- **ids-on-every-read.** Every brain read returns the ids of neighbouring objects (intent, decisions, artifacts). *"A preamble or tool result that names a record without its id is a bug"* — the only recovery left to the agent is asking the human, which hands the join back to the user. The graph must be traversable without ever asking "can you paste the id?".
- **Capabilities and connections are per-brand.** Which connections *this* brand has (Notion connected? Resend domain verified?) is declared in the specialist's session preamble, so it plans around what exists. Checked **before** the task's soft work budget is consumed; a missing connection is never an error and never throws. In v1 every OAuth grant is brokered by Vercel Connect. The durable `brand_connections` row belongs to `brand_id`, never to the Better Auth user who completed onboarding, and stores `connector_uid`, `installation_id`, effective account metadata/scopes, and status — never access or refresh tokens. `installation_id` is optional only for a connector that guarantees a single installation; providers whose connector is intrinsically single-tenant use one distinct connector per brand. That human is the audited Actor of connect/disconnect, not the later credential owner. This is a planning snapshot, not a pinned provider account: an ADR-019 commitment handler resolves the brand's current active connection and records the account actually used in its result receipt. API-key and other non-OAuth credentials remain outside this decision; a future connection may store only an opaque broker reference, not the secret.
- **External preparation is a closed create-only surface.** A durable root may receive an authored provider-draft operation only when the registry marks that provider state as non-committal. The tool cannot update/delete a previous draft or select its own connector method, effect class, worker, or commitment status. Every external commitment is prepared as a human-activation task and executed later by plain code (ADR-019).
- **The brand context splits in two.** The full document is an Object in the brain (stewarded by the product-marketer after deterministic v0, ADR-004); what rides in every session preamble is a **size-capped extract**, with the cap enforced by the write path, not by the prompt asking nicely (their "Who we are": 320 chars + 3 lines, `MAX_NARRATIVE` in code). The extract is prompt-cached — paid once, read on every turn; the full document is fetched on demand via tool. The eve template's single 20k-char document in every prompt is the anti-pattern. Two sub-rules from the same source: the extract **states what the context is for** (usage instructions for the reader — for us: "claims are graded; hedge on assumptions" — because a model with facts and no instruction starts selling our own product back to us), and it **dies with the website**: a change to the brand's `website_url` marks the extract stale and enqueues a product-marketer rebuild task, with a stand-down cooldown after a finished rebuild so an unreadable site is not re-fetched at cost on every sweep forever.
- **Brand Context v0 is deterministic application onboarding.** A server-side `apps/app` onboarding action first persists the brand and its human-authored **active revision-1** onboarding Intent, closes that transaction, and then performs the context.dev request. It never holds a Postgres transaction across provider I/O, opens no Eve session, makes no model call, creates no task, and does not consult the agent-credit balance. It validates and normalizes structured data, then safely downloads each selected optional binary, hashes its bytes, and uploads it idempotently to the brand-scoped content-addressed Blob key before any canonical database reference exists. One guarded `packages/brain` transaction records a producing Action as the fixed `system:context-dev` Actor, creates one Artifact Object per successfully mirrored variant, and creates Brand Context v0 plus its size-capped extract with typed artifact-id references. The human remains the Intent author/initiator, never the content producer. The Object also records typed provider evidence such as normalized domain, original source URLs, request hash, and `fetched_at`; source URLs are not canonical assets. The write uses a trusted stable operation key derived from the brand and website revision, so an exact retry observes the same canonical bootstrap rather than creating another active singleton. A failed optional mirror omits that Artifact without replacing it with a remote URL; a provider/bootstrap failure leaves the brand incomplete and the onboarding UI offers retry. An upload followed by a failed DB transaction may leave an accepted orphan Blob, but no Object may point to a not-yet-uploaded key. No background dispatcher silently continues the call. The Actor identifies provenance; exact-head and idempotency guards still arbitrate concurrent human edits and retries.

### 3. Model resolution chain

The model is a resolver, not a constant. Their entire mechanism is 15 lines: `defineAgent({ model: defineDynamic({ fallback, events: { "session.started": () => selectedModel() } }) })`.

- **Three levels**: global compiled fallback → per-specialist default in the `packages/agents` registry (the seo-analyst wants a long window, distribution wants speed) → the active per-brand `model_override` Decision head at the derived key `decision:model:<agent_key>`. Its content selects only a registered `model_profile_key`; it cannot inject an arbitrary provider/model/options blob. The authenticated console writes it through human `recordDecision`, preserving author, rationale, exact Object-id version, and supersession chain. A plain settings row has no provenance, and ADR-002 forbids that for normative choices.
- **One resolver factory in `packages/agents`**, shared by every generated root and declared-subagent wrapper (ADR-006) — no drift. This is ordinary TypeScript called from each consumer-local `agent.ts`, not an eve extension contribution: extensions cannot provide agent config. A built-in self-copy reuses its root definition and needs no second wrapper.
- **The resolver always returns the complete Eve selection object** `{ model, modelContextWindowTokens, modelOptions }`: eve does not inherit a changed window from the fallback, and a smaller-window model compacted against a number it does not have fails at the provider *after* the context has been assembled and paid for. The factory explicitly merges existing `modelOptions` and every provider-options namespace before injecting Custom Reporting; Eve 0.31.3 does not deep-merge a dynamic result with the fallback options. Routing, service tier, caching, reasoning, provider-native options, and Gateway attribution therefore remain on the active model when Eve uses it for automatic or manual compaction.
- **Gateway attribution is trusted and generated.** For every model-bearing session, `providerOptions.gateway.user` is the already-verified scalar `brand_id`. Stable registry/deployment values generate exactly `agent:<actor_key>`, `feature:<reportingFeature>`, `lane:<cmo|consultation|task>`, and `env:<production|preview|development>` tags. The brand is not duplicated as a high-cardinality tag, and browser, model, task payload, or delegation message cannot override reserved attribution. Other explicitly registered low-cardinality tags are unioned deterministically.
- **Degrades, never throws**: no row, DB down, resolver error → compiled fallback, reason logged. The alternative is a session quietly running on a model nobody chose.
- **Reporting is best effort, application accounting is not.** Channel and task adapters reject a missing or malformed billing tenant before calling Eve. After that boundary, an internal dynamic-resolver failure may still make Eve use its compiled fallback without request tags; this does not suppress a winning billable `step.completed` or its local `model_charge`. Eve 0.31.3 compaction is different: automatic or manual compaction can perform zero or more model calls, emits raw compaction lifecycle events but no billable `step.completed`, authoritative provider usage/cost, or Gateway `generationId`, and therefore creates no `model_charge` or credit debit. The active model's merged `providerOptions` and Gateway attribution remain so Custom Reporting can expose that Branderize-paid overhead and other attribution deltas. The append-only ledger is authoritative for billable application balance, admission, and customer billing—not total provider spend—and no estimate, hot-path `getGenerationInfo()`, Eve fork, OpenTelemetry biller, or reconciler fills the intentional gap.
- **Budget tie-in**: model selection is a separate trusted resolver that may consume the admission/budget context and choose a cheaper registered profile for autonomous work. The resolved model is not a fifth Policy-authority input and cannot change an effect verdict.
- **"Not a frontier model, on purpose."** Reliability is bought on the write path and the policy, not on model size. What sessions actually want is window length and answer speed.

### 4. Operational traps recorded for Phase 0/1 (from their post-mortems)

- In Eve 0.31.3, a human CMO conversation has a stable Branderize id, one owner, and only the fixed client cursor `{ sessionId, streamIndex }`. One browser `useEveAgent` store owns the live handle and stream for the selected conversation; the same-origin proxy authorizes every route and binds the create response's id before returning it, but never consumes the stream. The underlying fixed handle never creates or follows another session, so a terminal/reset session requires an explicit new application conversation rather than silently replacing the old binding. The task custom channel remains separate: it owns its deterministic `task:<task_id>` token, attempts one `mode: "task"` run, and binds the authoritative returned `session_id` through `session.started` plus a post-send fallback. Only an unbound delivery may be recovered (ADR-016, ADR-018).
- **`eve dev` never fires schedules.** The poke pattern (write the task row → fire-and-forget poke to the dispatch route → drain; cron as backstop) makes dev behave like production. *"An agent that is down costs sixty seconds, not the work."*
- eve's `jwtHmac()` resolves to `principalType: "service"`: any bridge carrying a human must remap the principal so identity, tenant ACLs, read capabilities, and Actor attribution see the real user. External-commitment approval does not run inside eve; `apps/app` evaluates it from the Better Auth session (ADR-019).
- **Eve has no brand connection principal.** Eve 0.31.3 connection principals are `app` or `user`; neither replaces the application's brand owner. The human CMO bridge and machine task auth both carry an application-verified `brand_id`. `packages/connections` resolves the matching active brand row from that trusted context and obtains its token through `@vercel/connect` with `subject: { type: "app" }` and the row's `installationId`; Eve dynamic auth/authored reads and ADR-019 direct handlers must reuse that resolver. `toolCall.providedArguments` may hide and inject a trusted brand or remote-account argument for MCP/OpenAPI, but it neither performs the ACL check nor chooses or stores the credential. Interactive Eve OAuth remains user-scoped and is not the ownership model for a headless brand grant; `apps/app` owns onboarding while Vercel Connect owns token storage, refresh, and rotation. Each of the seven Vercel projects is linked to every connector its compiled surface may resolve; deployment code has no token-storage or refresh fallback.
- **Machine routes fail closed**: an unset credential means the route *refuses* rather than opens — the absence of an optional capability must never widen access. The CRM's single `AGENT_BRIDGE_SECRET` is precedent for that fail-closed rule only, not our configuration name or authority model. ADR-009 splits human-principal signing (`CMO_BRIDGE_SECRET`), dispatch pokes (`DISPATCH_SECRET`), and cron ingress (`CRON_SECRET`) so possession of a wake-up credential cannot impersonate a user.
- The audit hook attempts to write **every raw root and child session event to our DB** for telemetry, billing, traceability, and conversation durability; ingestion is best effort and every persistence failure alerts. There is no separate message table and no automatic reconciliation from Eve. A permanent human transcript selects only events whose exact emitting session is the Eve root bound to the CMO conversation, keyset-pages the full stored prefix, replays it in ingestion order through Eve 0.31.3's `defaultMessageReducer()`, and never selects raw child streams. The parent root's `action.result(subagent-result)` is therefore the one visible tool result, while the child's `subagent.completed` remains telemetry. When the bound Eve session remains available, live chat still hydrates from its authorized index-`0` snapshot; the retained exact-root event log is the durable fallback, but it may contain a visible gap after an alerted hook failure and does not pretend to reconstruct Eve's winning history.

## Consequences

- `packages/db`: Object lifecycle and evidence metadata remain; executable-proposal lifecycle, exact dismissal memory, and approval/result links live on tasks and Actions (ADR-019).
- `packages/brain`: the write functions implement the three rules and the transaction discipline; tool results are crafted messages, not bare statuses.
- `packages/agents`: registry entries declare `model`, `modelContextWindowTokens`, `reportingFeature`, and mode defaults; the shared attribution-aware resolver factory; the preamble builder (brand-context extract + per-brand capabilities + ids).
- `apps/app`: a server-only onboarding service owns the context.dev adapter, input/output schemas, provider deadline, normalization, retry response, and call into `packages/brain`. It is not an Eve connection, model tool, registry kind, or browser-side fetch.
- Console: the brand settings page shows the effective resolution chain (brand override → specialist default → global) — provenance made visible.
- CI integrity metrics gain two entries: every Object carries a lifecycle status; an exactly dismissed commitment payload is not recreated without a human reopen Action.

## Alternatives considered

- **Model as env var or per-agent constant** — rejected: redeploy to change; impossible per-brand.
- **Model choice as a plain settings row** (their `AppSetting`) — rejected *for us*: multi-tenant, and ADR-002 makes normative choices versioned Decisions with provenance.
- **Brand context as one full document in every prompt** (the template's approach) — rejected: crowds out the actual work and is paid at every turn; the extract/full split is the CRM's lesson.
- **Enforcement by prompt** ("please don't overwrite human edits") — rejected: everything in this ADR exists because the CRM team watched prompts fail at exactly this.
