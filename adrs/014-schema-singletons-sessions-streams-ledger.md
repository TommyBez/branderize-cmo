## Context

Third self-grilling round, at schema level. Six questions; three needed re-explanation and one (session retention) surfaced a platform constraint that changes how much we may rely on eve's session storage.

## Decisions

### D0 — Actor identity separates initiator from producer

`actors.type` is `human | agent | system`; `actor_key` is globally unique and stable. `actors.user_id` is a nullable foreign key to the global Better Auth User with `UNIQUE` and `ON DELETE RESTRICT`. A database check requires `(type = 'human') = (user_id IS NOT NULL)`; human keys are deterministically `human:<user_id>`, while agent and system rows have no `user_id`. Actors have neither `organization_id` nor `brand_id`: a User has exactly one human Actor across every organization, while the separate Better Auth `Member(organization_id, user_id)` remains the source of current role and access. `actions.actor_id` and `intents.author_actor_id` are non-null foreign keys to `actors`, while `objects.produced_by` remains a non-null foreign key to `actions`. An originating Decision uses its own typed relation and is never stored in an Actor FK. Intent authorship is immutable: adopting an agent-authored draft records the human in `actions.actor_id` but does not rewrite `intents.author_actor_id`; an interactive refinement records the CMO as Action producer plus the authorizing human in its typed payload/Policy snapshot and likewise preserves the author.

`ensureHumanActor(tx, userId)` is the only materialization path. Trusted code derives the key, performs `INSERT ... ON CONFLICT (user_id) DO NOTHING RETURNING id`, and, when another transaction won, selects the row by `user_id` in the same transaction. A browser, model, or provider never supplies an Actor id or key. Two first writes for the same User, even in different organizations, therefore converge on one row; the brand-scoped Intent or Action still records the relevant tenant, and human authorization still resolves the exact Member before the protected write.

V1 disables and does not expose hard Better Auth User deletion. Offboarding deletes the exact organization Member rows and revokes sessions, leaving the global User and Actor as historical identity. The restrictive Actor foreign key makes accidental hard deletion fail loudly rather than cascading or nulling authorship. Removing one Member never affects the same User's memberships elsewhere. A future self-service erasure requirement must define explicit pseudonymization/tombstoning and amend the human `user_id` check; it is not silently approximated by `SET NULL`.

The migration idempotently seeds the fixed `system:context-dev` Actor. Only its dedicated trusted brain operation may resolve that key; neither Server Action input, model output nor provider data supplies an Actor id/key. Context.dev onboarding therefore records the exact same-brand chain `human-authored onboarding Intent → system:context-dev producing Action(intent_id) → Brand Context v0 Object(produced_by)`. A system identity is provenance, not authority: Policy denies system Actors by default and each dedicated operation additionally enforces its exact Action/Object types, structural links, expected head and stable operation key. ADR-020 Decision-impact Evidence and Verification instead use the Growth agent Actor because the measurement and judgment are agentic.

Canonical writes that promise exact replay store a nullable trusted `actions.operation_key` together with nullable `request_hash`; a check requires both or neither, and a partial `UNIQUE(brand_id, operation_key) WHERE operation_key IS NOT NULL` is the database backstop. After the applicable identity/access lock and Actor resolution, the operation acquires one transaction-scoped advisory lock derived from that exact brand/key before looking up the receipt; concurrent first calls therefore serialize and the loser observes the winner instead of failing a later head check. The producing Action is the durable replay receipt: its type-validated payload and `objects.produced_by` recover the historical result, while any deterministically derived child task is found by its own exact key. A replay hash-validates that receipt before current-head or write-Policy checks. It returns the original outcome even if canonical heads have since advanced; a new operation alone evaluates current authority and state. Trusted code namespaces and derives operation keys; a caller never supplies an unqualified key. This is write idempotency for an Action that actually committed, not an alias ledger for requests that merely observed another task.

### D1 — Object cardinality: singletons get a database constraint

Object types declare cardinality in the brain's type registry. **Logical heads** use a non-null trusted `singleton_key`: `brand_context` has one active head per brand; `marketing_plan` uses the fixed brand-level key `marketing-plan`; and every v1 Decision uses ADR-020's derived key for its exact roadmap, brand-policy, per-agent-model, or Intent-preauthorization slot. Producing a replacement supersedes the exact previous head in the same transaction. Object content, provenance, and authorship never change, but lifecycle metadata does: after locking and validating the expected head, the transaction changes the previous row from `active` to `superseded`, inserts the new `active` row, and sets the previous row's `superseded_by` to the new id. A head mismatch follows ADR-007's `stale_head` no-write path. The new Object id is its version identity; neither Decision nor Plan has a mutable revision column. **Collections** (`artifact`, `evidence`, `move_candidate`, `report`, and future registry-declared collection types): many active; supersession is explicit, per object. In particular, an Evidence `content.key` is not unique and identifies no logical head; immutable relations cite the Evidence Object id. An executable proposal is no longer an Object collection item; ADR-019 represents it as a human-activation direct task.

Enforcement is mechanical, not conventional: `objects.singleton_key` (NULL for collection items) plus

```sql
CREATE UNIQUE INDEX objects_singleton_active
  ON objects (brand_id, singleton_key)
  WHERE status = 'active' AND singleton_key IS NOT NULL;
```

`objects` also declares `UNIQUE(brand_id, id)`. Although `id` remains the global primary key, PostgreSQL requires the exact referenced column set for composite same-brand foreign keys such as `actions(brand_id, decision_id) → objects(brand_id, id)`; the redundant unique pair makes those tenant-integrity constraints creatable.

The unlikely-but-possible double-write (a retry-safe direct/automatic lease expiry overlapping a live handler, an interrupted eve step replaying inside one accepted run, admin intervention, or a future bug) becomes a loud constraint violation instead of silent ambiguity in every downstream "load the brand context". Human external commitments do not use lease reclaim. Invariants live in the substrate where the substrate can hold them.

### D2 — The owning record stores eve binding; eve state is working memory

> **Amended by ADR-016 and ADR-018.** Branderize separates application identity from Eve runtime identity. A CMO conversation owns the application binding to its Eve-generated fixed `session_id` and stores an opportunistic checkpoint of the browser-owned `stream_index`; the browser hook owns the live `ClientSession`. A durable agent task owns one authoritative bound `session_id`, while its custom channel owns the deterministic channel-local address. The narrow accepted-before-binding ambiguity is recorded in ADR-018 D3. There are no prefixed application lookup strings, opaque human `session_state`, or polymorphic session-state mapping table.

The CRM precedent has two distinct paths:

- Human chat: `AgentConversation.id` supplies the useful application/runtime identity split. Branderize maps Eve 0.31.3's public fixed-session cursor `{ sessionId, streamIndex }` to `cmo_conversations.session_id NULL UNIQUE` plus a monotonic, possibly stale `stream_index NOT NULL DEFAULT 0`. The application id remains the URL and ownership key; only the single `owner_user_id` with current Better Auth Member role `owner | admin | member` may create/send, answer HITL, checkpoint, or otherwise mutate it, while a brand may have many owner-scoped conversations. The same owner as `viewer` may read an otherwise-authorized transcript/snapshot/stream and submit only ADR-016's exact-`turnId` stop for an already observed turn. The browser `useEveAgent` store owns the live writer handle and reconnect; the proxy authorizes routes and binds the first returned id without consuming the stream. Whether another member of that organization may read one is a separate ACL decision.
- Automated work: the durable task remains the product and run identity. Its custom channel derives `task:<task_id>`, attempts delivery with `mode: "task"`, and binds the authoritative `session_id` on the task through `session.started` plus post-send. Only a stale unbound handoff may send again. Domain code never uses the token as a lookup key, and a later product retry is a new task rather than a continuation of the failed session.

**The platform constraint:** on Vercel, workflow run data is retained per plan (1 day Hobby / 7 Pro / 30 Enterprise after completion; stream chunks TTL 30 days in beta) — `sessionTimeoutMs: false` keeps the token alive but cannot extend the storage underneath. Therefore:

- **Eve session state is working memory, never the product's only copy.** The graph, application-owned CMO conversation rows, and every raw root/child event successfully captured by the best-effort audit hook live in Postgres. There is no separate message table, hook-time transcript projection, or automatic replay from Eve into Postgres. The permanent transcript of a CMO conversation is the ordered raw `session_events` whose exact emitting `session_id` equals the immutable `cmo_conversations.session_id`; application reads fold that event list with Eve 0.31.3's exported `defaultMessageReducer()`. Raw self-copy and declared-subagent sessions are excluded by that exact-id selector. Their result still appears once because Eve emits the parent root's `action.result(subagent-result)` in the bound root stream and the default reducer renders it as the corresponding tool part; the child's parallel `subagent.completed` and raw stream remain child telemetry. For an available session, an authorized Eve `snapshot()` from index `0` supplies the exact event prefix and cursor used to hydrate the live browser UI. The persisted root-event log is durable once written and remains the unavailable-session fallback, but an alerted hook failure can leave a permanent gap there.
- A waiting human session continues through its browser-owned `useEveAgent` store bound to the fixed id. Underneath, Eve targets that exact `ClientSession`; neither the hook nor proxy creates or follows a replacement. A terminal, reset, or unavailable conversation remains readable by reducing its retained root `session_events`; starting again explicitly creates a new application conversation and a new Eve session.
- Escape hatch, documented not adopted: `@workflow/world-postgres` backs eve's workflow state with our own Postgres and implements no TTLs. We start on Vercel-managed workflow and migrate only if retention becomes a product constraint; permanent transcripts do not depend on that choice.

### D3 — `structure_level` is derived, never stored

`intents` is the canonical current row: same-brand author and parent references, statement, nullable non-empty typed `acceptance_criteria`, nullable non-empty typed `constraints`, status, and monotonic `revision NOT NULL DEFAULT 1`. A check requires criteria whenever constraints are non-null, so refinement cannot skip the middle structural layer. The trusted human-declaration path inserts `active` revision 1 with the current human author; the trusted autonomous proposal path inserts `draft` revision 1 with the build-time agent author. Neither author nor status is caller/model-authored. `draft` means only an unadopted agent proposal, not low structure. There is no `intent_versions` table. Declaration, proposal, adoption, abandonment and refinement each use a trusted stable `requestId`, namespaced Action `operation_key`, canonical `request_hash`, and receipt-first replay before current-state guards. `packages/brain.refineIntent` then locks the exact brand/Intent row, compares `expectedRevision`, requires `status IN ('draft', 'active')`, and commits the typed field update, `revision + 1`, and one append-only `intent_refined` Action whose type-validated payload contains before/after snapshots and a discriminated producer context. The direct-human form uses the human Action Actor. The CMO-interactive form requires a current top-level bound conversation turn, uses the CMO Action Actor, and stores trusted `authorizing_human_actor_id`, `conversation_id`, `session_id`, `turn_id`, and `call_id`; its `policy_snapshot` freezes the current Member role/verdict. The request hash covers authorizer/Member, `(conversation_id, session_id, turn_id, intent_id)`, expected revision, and typed mutation, but explicitly excludes `call_id`; that id remains immutable provenance of the first committed receipt. The locators have no FK to best-effort `session_events`. Only the wrapper constructs either producer context. `adoptIntent` uses the same row/revision lock, requires `status = 'draft'`, atomically changes it to `active`, increments the revision, and appends one human `intent_adopted` Action without changing the original author. Human `abandonIntent` accepts only a nonterminal exact revision, changes it to `abandoned`, increments once and appends `intent_abandoned`; it never cancels already-created work. Every row mutation and matching Action share one transaction. A lost compare-and-swap returns `stale_intent` and leaves both tables untouched, while exact replay returns its historical result after later mutations. Refinement does not edit the statement in v1.

`structure_level` remains a pure function in `packages/policy`: no acceptance criteria → low; non-empty acceptance criteria → medium; non-empty acceptance criteria **plus** non-empty constraints **plus** at least one applicable linked pre-authorizing Decision → high. At an Intent-bound new-work boundary it first requires the canonical current Intent row be `active`, then derives from it and only active `intent_preauthorization` heads with `content.authorized = true`, whose producing Action has that exact same-brand `intent_id` and whose registered key applies to the requested task/effect. A draft contributes no structure and cannot receive preauthorization. An active false head is a revocation and never raises structure. Roadmap, model and brand-restriction Decisions never raise structure. Every non-Intent-bound operation—including administrative brand Decisions, Plan-routed tasks, and registered origin-free tasks—records `structure_level = null` and no preauthorizing Decision ids; Policy applies a dedicated unstructured branch that is never more permissive than `low`, reloads current brand restrictions, and does not reinterpret Strategy, Plan, or origin-free work as authorization. For an already-created Intent-bound task structure derives from its immutable `intent_snapshot`, including the exact pre-authorizing Decision Object ids and typed policy facts selected at creation. The value or explicit null, source Intent revision when present, and selected Decision ids are recorded in the Action's `policy_snapshot` for replay. No mutable level column can drift, and a later Intent refinement cannot reinterpret accepted work.

`tasks` stores a nullable same-brand `intent_id` plus a nullable typed `intent_snapshot`. They are null together for work with no Intent; otherwise the snapshot is mandatory and its `intent_id` equals the relational column. The snapshot contains `intent_id`, `intent_revision`, current statement, acceptance criteria, constraints, and only the selected immutable exact-Intent preauthorization Object ids plus their minimal typed policy facts. `intents` exposes `UNIQUE(brand_id, id)`, allowing the task's composite `(brand_id, intent_id)` foreign key to prevent cross-tenant binding; schema/constraint tests reject malformed or disagreeing snapshots. Task insertion requires the referenced row be `active` and builds this value from trusted rows and structural Action links; request payloads cannot supply or override it. Existing task snapshots are immutable across Intent refinement, task edit, claim, retry delivery, and settlement.

The same table also stores nullable same-brand `plan_object_id` and `move_candidate_id` foreign keys to `objects(brand_id, id)`. They are both present or both null. `parent_task_id` is a nullable same-brand FK and insertion-only causal provenance: a newly created route points to its rebuild/advancement task, while every newly created task-bound lateral, recheck, materialized self-successor, retry, replacement, or commitment points to the exact existing source task that created it. The model/browser cannot provide it, and observation or rescheduling never reparents an existing row. Because a new row may point only to a source that already exists and the field never changes, conforming writes form a DAG; traversal is nevertheless cycle-safe and fails closed on malformed legacy data. A route row created by `publishPlanAndRoute` or `advancePlanAndRoute` requires the Plan/Move pair, requires `intent_id = intent_snapshot = null`, and stores the authoritative rebuild/advancement routing task as `parent_task_id`; trusted code additionally verifies `marketing_plan`/`move_candidate` types and that the Move is included and not excluded in that Plan. Its ordinary registry subject is namespaced as `plan-route:<move_candidate_id>:<registered-subject>`, so work for another Move or an Intent-bound request cannot win the same active identity. Every routing Action maps the exact task id and `created | observed` disposition plus nullable `origin_root_routing_action_id` and `origin_root_routing_task_id`. For `created`, those are the current preallocated Action id and routing task; for `observed`, trusted code preserves them only when an earlier Plan/wave Action's `created` mapping originally materialized the immutable row. A semantically equivalent lateral descendant may be observed but has null root origin and cannot later be withdrawn as a root. A later wave or Plan may therefore observe an active row for the same Move and subject without mutating or misattributing its original Plan, parent, payload, or provenance. That mapping remains the authoritative adoption relation. For post-terminal advancement, a source qualifies at depth zero when the current Plan maps it, or as a descendant when its immutable parent chain reaches the first task that Plan maps. Every row from source through that anchor must be same-brand, null-Intent, and carry an identical non-null origin Plan/Move pair; the current Plan may differ from that origin Plan when it adopted the anchor. The chain authorizes only an origin-free evaluation wake-up and never adds mapping/root provenance or withdrawal eligibility to a descendant. An observed/rescheduled row retains its old parent and qualifies only if that preserved chain already reaches an adopted anchor; no alias is invented. Plan-routed successors, lateral work and commitments preserve the same Plan/Move pair and null Intent unless a separate explicit operation creates a genuine Intent. The origin-free `advance-marketing-plan` coordinator is the narrow exception that pins its Plan and optional target Move inside a trusted kind payload while leaving these common-origin columns null.

`publishPlanAndRoute` may also terminalize an old root wave route as `superseded` when the new Plan explicitly lists that exact Move in `excluded_moves`. Trusted code obtains and deduplicates candidate task ids only from non-null root-origin entries in the previous Plan-producing Action and later `plan_wave_evaluated` route mappings. The guarded update requires the same brand and exact excluded `move_candidate_id`; `execution_mode = 'agent'`, `activation = 'automatic'`, `status = 'queued'`; null Intent/snapshot; non-null Plan/Move; null `retry_of_task_id`, `supersedes_task_id`, and `schedule_id`; `parent_task_id = origin_root_routing_task_id`; and an origin Action whose `created` mapping names the same row. It sets `finished_at` and `outcome_code = 'plan_move_excluded'` while session, staged completion, `next_*`, lease, and attempts remain absent. The new Plan Action records the exact ids returned by the guarded updates. No `supersedes_task_id` is required because the replacing authority is the new Plan rather than another task. Omitted Moves, running rows, direct work, human commitments, retries, replacements, schedule occurrences, lateral descendants, and other unmapped descendants are outside this update even when they preserve the same Plan/Move pair.

An acceptance Verification stores the exact `intent_id` and `intent_revision` whose criteria it evaluated. Human `settleIntent(..., expectedRevision, requestId)` resolves its Action receipt first and then uses `status = 'active' AND revision = expectedRevision` on the locked current row; the same transaction sets `settled`, increments the revision and appends `intent_settled`. Automatic settlement uses the exact task-bound Verification Action as its replay receipt and performs the same guarded transition/increment. In an authoritative task terminal transaction, automatic acceptance settlement is evaluated before any staged `next_*` successor: a winning close clears that tuple and inserts no successor, while a stale close leaves the Verification historical and falls through to the ordinary active-Intent eligibility check. Settlement and refinement share the same row lock/guards: a refinement winner makes old evidence stale, while a settlement winner makes later refinement affect zero rows. Evidence for an older revision remains queryable but cannot settle a newer canonical Intent. Filling structure fields therefore stays delegable work while preserving the rule that state is a projection rather than an independent object.

### D4 — Two streams: `actions` vs `session_events`

The partition is decided by **code path, never by the model**:

- **`actions`** — the grammar log, written only by brain write-path functions and boundary executions. Each row has a type-validated `payload` JSONB for its discriminated domain fact; it is not a free-form model field. Nullable `operation_key`/`request_hash` form a checked pair; the partial per-brand unique key above protects exact replay for operations that use it. A nullable `decision_id` uses a composite same-brand foreign key to `objects(brand_id, id)`. It is required by the Decision-impact Verification subtype together with `task_id`; partial subtype-specific unique constraints permit one Decision-impact Verification per impact task and one Intent-acceptance Verification per eligible Intent-bound task. The origin-free Decision-impact kind is categorically ineligible for Intent acceptance, so one task can never produce both subtypes. An Intent-acceptance payload stores the trusted snapshot-derived `intent_id`/`intent_revision`, the closed judgment, rationale, and validated Evidence ids; only `satisfied` can run the guarded Intent close. For Verification subtypes created during terminal settlement, the Action insert, task result link and settlement are one transaction. A `marketing_plan` producing Action instead stores canonical typed `planning_intent_snapshots[]` derived from one ordered read of current active Intent rows: id, revision, statement, criteria and constraints, but never preauthorization facts. These are immutable synthesis provenance and the basis of the `plan_needs_rebuild` projection, not task common origin or Policy authority. That Action commits atomically with the Plan, route mapping, exclusions and routed tasks at the tool boundary; `TaskCompletion` and terminal task settlement happen later and cannot roll the published graph back. This is what provenance, policy replay, and the CI integrity metrics query. Append-only for the brand's lifetime; brand deletion cascades it with the rest of the tenant data (ADR-019, ADR-020).
- ADR-021 adds no wave table or Plan mutation. A human `plan_move_readiness_overridden` Action links its exact targeted advancement task and stores typed Plan/Move references plus rationale and Policy snapshot. A CMO `plan_wave_evaluated` Action links its authoritative advancement task and stores the exact Plan, optional override Action, evidence/rationale, outcome, and canonical route mapping with nullable immutable root-routing Action/task ids. A partial unique constraint on `actions.task_id` for `type = 'plan_wave_evaluated'` permits exactly one wave receipt per advancement task; that Action and all mapped task creates/observations commit together. A later `TaskCompletion` must cite that exact receipt, but a later session failure does not roll back the already committed wave, consistently with other tool-level canonical writes. These references are trusted and same-brand/type-validated at write time; Plan/Move Objects are immutable and survive for the brand lifetime.
- **`session_events`** — raw Eve stream log and telemetry: the audit hook attempts to ingest every event with Eve's stable `meta.id` as the global primary key, its complete reducer-consumable event envelope/payload, and an application ingestion sequence used to replay one session in observed stream order. `meta.id` deduplicates delivery but is not used as a total-order cursor; Eve documents its ULIDs as only broadly time-ordered. Each row belongs to trusted `brand_id` with `ON DELETE CASCADE`; in addition to the exact emitting `session_id`, it denormalizes Eve's structural lineage: `root_session_id` equals that id for a top-level session and comes from `ctx.session.parent.rootSessionId` for a child; `parent_session_id` and `parent_call_id` are null at the root and come from the same parent context below it. The hook uses `INSERT ... ON CONFLICT DO NOTHING RETURNING meta_id`; only a returned winning insert may project a derived row, and those writes share the same transaction. Every session depth remains eligible for billing, but event kind is decisive: only a validated billable `step.completed` may create `model_charge`; raw compaction events never do. There is no message table and no hook-time event folding. A conversation transcript query joins the conversation's exact bound `session_id`, requires the emitting row's `session_id` to equal it, orders those raw rows by the stored ingestion sequence, and uses the pure `defaultMessageReducer` exported by `eve/client` to fold the complete prefix through `.reduce` from `.initial()` into `EveMessageData`. It must not select by `root_session_id`, because that would mix child streams into the human transcript. Retried steps that genuinely re-emit under new ids remain distinct, which is correct: Eve 0.31.3 retains every attempt in the event stream while durable history keeps only the completed attempt and exposes no winner field. The reconstructed UI is therefore an observed transcript, not a canonical reconstruction of durable model history. The parent root's `action.result(subagent-result)` naturally becomes one dynamic-tool result; the child's raw brief, narration, reasoning, actions, messages, and `subagent.completed` remain telemetry. Actions carry `session_id`/`call_id`, so any grammar action traces to its telemetry. Child ownership needs no separate mapping table: the event contains its own lineage, while the existing task or conversation row remains the only top-level runtime binding.

Hook delivery is **best effort**, not a second durable queue: Eve does not give the application a lossless acknowledgment for a successful persistence callback, and callback failures must be caught and reported to alerting. V1 deliberately copies the CRM here: neither `snapshot()` nor browser recovery writes back to `session_events`, and no automatic reconciler fills a missed root, child, task event, or charge. Rows that were written remain durable under the retention contract; a failed callback can leave the Postgres fallback incomplete, so the alert is operationally significant and the UI must not present that fallback as certified complete.

Transcript reads consume the **full ordered prefix** with cursor/keyset pagination over the stored replay sequence and reduce all pages from `initial()`; an implementation may not render only a fixed tail or silently stop at a 2,000-row page. `apps/app` and `agent-cmo` pin the same exact Eve version so the stored event schema and reducer agree. An Eve upgrade is blocked by a fixture that replays representative stored root streams—including tools, subagent results, HITL, failure, and retry events—through the candidate `defaultMessageReducer()` and verifies the expected `EveMessageData` before both consumers move together.

The mental test for the partition: *would a human ever ask "why did this happen, and who authorized it?"* — yes → Action; "what did the model do along the way" → telemetry.

### D5 — `credit_ledger`: three entry types, idempotent by key

- `grant` — monthly pool, purchases, and later settlement/top-up of overage; a grant is not required in advance of a human-approved charge
- `model_charge` — one row for every winning **billable `step.completed`** event, for human conversations, top-level agent runs, and their child sessions. It stores `session_event_id UNIQUE`, `session_id`, trusted `brand_id`, nullable owning task/conversation ids, model id, input/output token details, actual gateway cost, and `generation_id` when the gateway metadata provides it. One human turn may contain several model steps and therefore several charges; session closure and compaction create no additional debit
- `action_charge` — one row only for a billable Execution/Result Action whose task reached `succeeded` with a validated stable provider receipt; idempotency key `action_id`. Its amount and pricing version come from the authorization snapshot, not the current price table. `failed`, `outcome_unknown`, `expired`, `cancelled`, and `needs_regeneration` produce no charge. A later Verification Action never backfills the unknown commitment's charge in v1; it is billable only when its own registered operation is separately chargeable

**Compaction is platform COGS, not a credit event.** In Eve 0.31.3, automatic and manually requested compaction can complete with zero model calls through framework heuristics or make one or more summary calls. The stream exposes raw `compaction.requested` and `compaction.completed` events, but no compaction call emits a billable `step.completed`; those events expose neither authoritative provider token usage/cost nor Gateway `generationId`. `compaction.requested.usageInputTokens` is a context-size input to the compaction decision, not provider-reported billable usage. The audit hook stores the raw compaction events in `session_events`, while the ledger projector deterministically ignores them and creates no `model_charge`. Their provider cost belongs to Branderize platform COGS and does not consume customer credits or affect admission.

V1 leaves the active model reference and its complete `providerOptions` in place for compaction, including the reserved AI Gateway `user` and generated tags. Gateway Custom Reporting can therefore measure attributed compaction overhead even though the local event contract cannot itemize it. A report-to-ledger comparison classifies that known compaction component as expected platform COGS, never as a reconciliation error or evidence for a customer debit; missing attribution and any remaining aggregate delta stay diagnostic. `credit_ledger` is authoritative for **billable application charges and admission**, not total provider spend. V1 does not estimate compaction cost, call `getGenerationInfo()` on the hot path, fork Eve to add usage events, turn OpenTelemetry into a billing source, or add a cost reconciler.

Before that transaction, every model-bearing top-level adapter constructs a typed application `billingContext` from the authorized conversation or claimed task. Its required `brand_id` is projected into Eve as a trusted non-empty scalar auth attribute. The audit hook reads the immutable tenant from `ctx.session.auth.initiator.attributes.brand_id`; for every production event, `ctx.session.auth.current.attributes.brand_id` must also be a non-empty scalar with the same value. Missing, array-valued, or unequal values are an invariant failure: the hook fails closed and commits no Branderize event or charge under a guessed tenant. Neither attribute is accepted from browser input, the payload-free dispatcher poke, the model, or a subagent message.

The same trusted initiating attribute feeds a shared **model-config factory** in `packages/agents`. Registry materialization calls that factory from the consumer-local `agent.ts` of the CMO root, every specialist root, and every declared specialist; the audit extension cannot supply agent configuration. A built-in self-copy reuses the root config. The dynamic selection explicitly preserves and merges all existing `modelOptions.providerOptions`, then reserves `gateway.user = brand_id` and generated low-cardinality tags `agent:<actor_key>`, `feature:<reportingFeature>`, `lane:<cmo|consultation|task>`, and `env:<production|preview|development>`. Brand id is not repeated as a tag, and runtime input cannot replace these fields.

Eve 0.31.3 copies `auth.current` and `auth.initiator` into both built-in self-copies and declared local subagents. It also exposes the immediate and root parent relation to the child hook. Therefore the same validation and billing derivation works at every depth without looking up a child session. A self-copy inherits the root hook registry. A declared subagent does not: parent hooks do not fire for its turns, so its generated declaration must mount the shared audit extension locally under ADR-015.

The audit transaction then attempts the `session_events` insert and creates a `model_charge` only when that insert returns the winning row and the event contains validated billable model usage. Exact replay of the same `meta.id` creates neither a second event nor a second debit. A model retry that genuinely completes as a new billed generation emits a distinct event id and is charged separately. Missing optional `generation_id` does not trigger `getGenerationInfo()` on the hot path; the event id remains the ledger idempotency key. `credit_ledger.model_charge` is the sole authority for billable application balance, admission, and customer billing, but deliberately does not represent total provider spend. AI Gateway Custom Reporting is a best-effort comparison and investigation surface: periodic reports may expose attributed compaction/platform overhead, missing attribution, or aggregate deltas, but never create, modify, backfill, or replace a charge. Eve deliberately degrades a failed dynamic model resolver to its compiled fallback, so absence of reporting tags cannot block a generation or erase its locally observed charge. `getGenerationInfo()` remains an operator-invoked investigation for a known generation, never the normal projector.

Unique constraints on the keys make replay of a charge projection safe. In v1 the balance is an indexed aggregate query over the append-only ledger that the dispatcher reads before an **agent-lane** claim (ADR-011 D4), not a PostgreSQL materialized view and not an eligibility condition for either direct lane. That read creates no reservation, so concurrent positive-balance claims and already-running conversations may post multiple `model_charge` rows and take the ledger below zero. A human-approved boundary call likewise proceeds at zero pool balance. When it reaches billable `succeeded`, its Result Action, task settlement, and one `action_charge` commit in the same transaction under `UNIQUE(action_id)`; every other outcome commits its Result Action and settlement without a charge. Either kind of debit may make the balance negative: the negative amount is payable overage, later settled by billing rather than a credit grant that must exist before execution. `model_charge` derives from the immutable winning telemetry event and `action_charge` derives from the durable successful boundary Action; ordinary telemetry retention can rewrite neither. Brand-scoped ledger rows still follow ADR-019's tenant cascade; any separately retained issued invoice is a billing-layer document, not a surviving work-graph row.

**Retention is a policy knob, not a v1 partitioning scheme.** `session_events` remains an ordinary unpartitioned table so PostgreSQL can enforce the global `meta_id` primary key exactly, matching the current CRM. Its real replay index includes `(session_id, ingestion_sequence)`; `meta_id` is not a total-order cursor. Events whose exact emitting `session_id` is referenced by a CMO conversation are retained for the lifetime of that conversation's brand, including after archival or Eve-side expiry, and disappear only with brand cascade deletion. A future measured retention policy may prune child and other non-conversation telemetry, but must classify protected rows by exact `session_events.session_id = cmo_conversations.session_id`, never by `root_session_id`, so descendants do not inherit transcript retention. Monthly range partitioning cannot simultaneously enforce the global event key without including the partition column, so it is not predesigned. Any later archival or partition migration must preserve global replay deduplication and ordered exact-root transcript reconstruction.

### D6 — `objects` content shape: three columns, three jobs

- `content JSONB` — machine-readable, validated per type by the write path's zod schemas (ADR-012's `output_contract`)
- `content_text TEXT` — the per-type human-readable projection, with a generated `tsvector` column powering the graph browser's full-text search
- `blob_key` — one nullable pointer to a brand-scoped content-addressed Blob for an `artifact` Object. Each binary/variant gets its own Object; other Objects reference those artifact ids and never embed a remote URL as their canonical binary (ADR-011 D6)

### D7 — Deterministic cadences are durable schedules, not future tasks

The current CRM separates an `AgentTrigger` from each `AgentRun` it creates and advances the trigger in the same transaction as the run upsert. Branderize copies that durable rule/occurrence identity and atomic cursor boundary for deterministic product cadences, while adapting the deployment trigger, wall-clock calendar, and overlap policy.

`schedules` stores one durable recurring rule per brand and stable `schedule_key`. A row has `brand_id`, registry-validated `worker_key` and task `kind`, a typed immutable-per-occurrence payload template, `cadence = daily | weekly`, `local_time`, nullable `local_weekday`, an IANA `time_zone`, `enabled`, `revision`, `next_scheduled_for`, monotonic `coalesced_due_count NOT NULL DEFAULT 0`, and nullable `last_coalesced_for`. `UNIQUE(brand_id, schedule_key)` protects deterministic setup/upsert. Daily rows require no weekday; weekly rows require exactly one. `next_scheduled_for` is the indexed UTC instant for eligibility, but the next value is always recomputed as a calendar occurrence in `time_zone`; adding 1,440 or 10,080 minutes is forbidden. A brand-timezone or cadence change is a deterministic schedule update that increments `revision` and recomputes the next instant. It never rewrites an already-created task occurrence.

A scheduled task occurrence snapshots the validated schedule kind, payload, root, and calendar slot. If the template is Intent-bound, the insertion branch also requires that Intent be active, resolves its latest revision and constructs the common immutable `intent_snapshot`; the schedule template never caches that snapshot. If it is no longer active, the due evaluation still advances the schedule cursor but creates no task. It sets nullable `schedule_id` and `scheduled_for` together, requires `execution_mode = agent AND activation = automatic`, and is protected twice: `UNIQUE(schedule_id, scheduled_for)` preserves exact replay identity, while a partial `UNIQUE(schedule_id) WHERE schedule_id IS NOT NULL AND status IN ('queued', 'running')` permits at most one nonterminal occurrence for that schedule. Scheduled agent tasks have no other nonterminal status. Their trusted subject is occurrence-scoped, derived from the exact pair; the partial index, not semantic subject coalescing, prevents overlap across slots. Ordinary request creators retain the existing creator `idempotency_key`; a deterministic schedule occurrence uses this explicit composite identity instead. There is no general `task_request_keys` or alias table, and replay of a created occurrence returns that exact task without mutating its accepted snapshot.

At the start of its `/internal/dispatch` work, each root reads only due rows with `worker_key = SELF`, `kind IN compiledSupportedKinds`, `enabled = true`, and `next_scheduled_for <= now()`. For each bounded candidate, it remembers the old `next_scheduled_for` as `scheduled_for`, computes the first future wall-clock occurrence strictly after `now`, and runs one transaction:

1. compare-and-swap the schedule by id, `revision`, `worker_key`, `enabled`, and the exact old `next_scheduled_for`, setting the computed future `next_scheduled_for` and next revision;
2. lock the schedule's possible `queued | running` task with `SELECT ... FOR UPDATE`. If it exists, insert no task and update the already-locked schedule with `coalesced_due_count = coalesced_due_count + 1` and `last_coalesced_for = scheduled_for`. If none exists and an Intent-bound template's referenced Intent is not active, commit the cursor advance with no task. Otherwise insert-or-observe exactly one queued task under `(schedule_id, scheduled_for)` with `due_at = scheduled_for` and the schedule snapshot.

A lost compare-and-swap inserts and coalesces nothing. A failure of a task insertion that was actually attempted rolls back the schedule advance; the explicit inactive-Intent branch is a successful no-task evaluation, not an insertion failure. The task-row lock defines the race with terminalization: if materialization locks the active task first, this slot is coalesced and terminalization follows; if terminalization commits first, the materializer rechecks the predicate after waiting, sees no active row, and may insert this slot when its origin remains eligible. The partial unique index is the final defence. Concurrent or repeated pokes therefore leave at most one nonterminal occurrence and one future cursor without a distributed lock.

If several slots were missed while the root was unavailable and no occurrence is active, the transaction materializes only the oldest missed slot and advances directly to the first slot after `now`; intermediate slots are deliberately skipped rather than replayed as a burst. If an occurrence is already queued—including indefinitely at the credit gate—or running, the oldest evaluated due slot is recorded only through the counter and last-slot fields and no task is created. Intermediate skipped calendar slots are not separately counted: `coalesced_due_count` counts suppressed due evaluations, not a reconstructable backlog. Once the active task becomes terminal, no catch-up task is synthesized; the next task can be created only when the schedule's already-advanced cursor becomes due. Task success, failure, cancellation, credit blocking, or delivery recovery never changes that cursor.

This table is not the agentic `scheduleRecheck` mechanism. A deterministic daily/weekly schedule exists before a run, advances whenever its due evaluation commits whether that evaluation creates a task, coalesces behind one, or suppresses an occurrence for an inactive Intent, and never uses `next_*`. `scheduleRecheck` remains a bounded model-authored follow-up on a current task. A first cross-kind future recheck is created or rescheduled immediately by the successful tool call and survives a later source-task failure; only an equivalent running self-recheck uses the row's `next_*` slot and materializes that successor during successful settlement. Both retain ADR-017/ADR-018's active-work and origin-eligibility rules.

## Deferred notes

- **RLS** stays deferred: explicit `brand_id` plus the single write path is the primary defense, and v1 keeps authorization in that application boundary rather than maintaining a second policy system in SQL. ADR-005's transaction-capable adapter could support transaction-local database context, so pooling is not the reason for this deferral. Revisit RLS as defense in depth if the console ever queries outside the brain.
- Task active identity uses `(kind, brand_id, subject_key) WHERE status IN ('awaiting_approval', 'queued', 'running')`. Ordinary creators use a separate `idempotency_key UNIQUE` plus canonical creation hash to deduplicate replay of the request that inserted the task and reject key reuse with different input. Deterministic cadence occurrences instead use exact `(schedule_id, scheduled_for)` replay identity, an occurrence-scoped trusted subject, and the partial active-occurrence guard on `schedule_id`. V1 stores no alias keys for distinct requests coalesced onto a row and no general `task_request_keys` table. Human commitments use a proposal-specific subject identity, so the ordinary active index does not semantically collapse independently intended proposals. A second partial unique index on `(brand_id, commitment_conflict_key) WHERE activation = 'human' AND status IN ('queued', 'running') AND commitment_conflict_key IS NOT NULL` prevents simultaneous approval/execution only for registry-declared non-commutative commands; it is a conflict guard, not proposal deduplication or FIFO.
- Shared fields include registry-derived `execution_mode` and `activation`. Valid combinations are agent/automatic, direct/automatic, and direct/human; agent/human is invalid. ADR-018 holds the agent lifecycle. An agent/automatic row additionally permits the narrow `queued → superseded` transition for an explicitly excluded root wave route proven by its origin routing Action/task; every other agent supersession is invalid. Only direct/automatic may use `leased_until`, `attempts`, and bounded reclaim. Direct/human adds `awaiting_approval`, `outcome_unknown`, `expired`, `needs_regeneration`, `dismissed`, and `superseded`; it stores revision/payload hash, `approved_at`, plus Approval/Result Action links, while task-linked Cancellation Actions settle atomically without a separate proposal table. `approved_at` is a denormalized lifecycle timestamp written with the Approval Action, not a generic priority. It never uses session state, staged completion, `next_*`, lease, or attempts (ADR-019).
- `tasks` has nullable `next_due_at`, `next_payload`, and `next_rationale` fields only for the single pending successor of an equivalent running agent recheck or a registered direct/automatic kind. They form one tuple and are updated atomically. Human external commitments never stage recurring successors. Agent failure/cancellation or direct/automatic exhaustion clears the tuple and creates no successor. Provider-outcome polling uses distinct occurrence tasks rather than this `next_*` slot (ADR-017, ADR-018, ADR-019).
- ADR-020's `verify-roadmap-decision-impact` is a one-shot agent/automatic origin-free Growth task with null Intent/snapshot and Plan/Move, an exact non-null same-brand `decision_id` in its typed payload, and idempotency/subject keys derived from that immutable Object id. It opens one ordinary Eve task session, passes through the agent-credit gate, may use any available measurement read tools, rejects non-null `intent_acceptance`, and never uses `schedules`, `scheduleRecheck`, or `next_*`; a measurable Decision and this future task are inserted in the same `recordDecision` transaction.
- An Intent-bound task's creator request hash covers the caller's stable request (`intent_id`, kind, typed payload), not whatever Intent revision happens to be current on replay. Creator-key replay is resolved before current-Intent loading and returns the historical row. Only an actual insertion snapshots the latest revision; an active-work conflict likewise returns the winning task without rewriting it. The common snapshot is not duplicated inside the kind payload or `next_payload`, and no `intent_versions` table exists.
- Every brand-scoped grammar and runtime table has a real foreign-key path to `brands` with cascading delete. Durability means surviving process/deploy failure, not surviving deletion of the tenant. External provider resources are not part of the cascade.
- Lane-specific partial claim indexes support the ADR-009 admission queries: queued human commitments by root/deadline/`approved_at`/id, eligible automatic-direct rows by root/creation FIFO, and eligible agent rows by root/creation FIFO. Query-plan tests cover the due/status/mode predicates and ordering. There is no generic task-priority column or index.
