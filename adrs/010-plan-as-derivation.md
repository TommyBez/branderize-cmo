# ADR-010: The plan is agentic synthesis with deterministic persistence

- **Status:** active
- **Date:** 2026-08-05
- **Deciders:** Tommaso (human), grilling session on the authenticated [Magister](https://magistermarketing.com) product (Chat, Plan, Permissions, Workflows, Briefs, MCP reference)
- **Builds on:** [ADR-002](002-postgres-work-graph.md) (projections), [ADR-004](004-extended-roster.md) (CMO role), [ADR-007](007-approvals-and-tasks-queue.md) (approvals), [ADR-008](008-brain-write-path-and-model-resolution.md) (capabilities), [ADR-009](009-agent-deployment-and-console-data-surface.md) (console)
- **Amended by:** [ADR-019](019-human-approved-external-commitments.md) — the UI cannot enable unattended external commitments; every direction uses the human-task gate
- **Amended by:** [ADR-020](020-typed-decisions-and-impact-verification.md) — roadmap inputs are closed human-authored Decision heads; recording a Strategy also creates its CMO Plan-rebuild task
- **Amended by:** [ADR-021](021-plan-advancement-and-human-readiness-override.md) — later waves advance the same Plan; changed roadmap content or active-Intent planning inputs require a rebuild

## Context

An authenticated exploration of Magister surfaced six questions. The richest finding was their presentation of a marketing plan as **compiled, not authored** — `Compile status: active`, separate "Rerun audit" and "Rebuild plan" buttons, plan versions, and roadmap inputs (budget, bandwidth, goal, timeline, channels, autonomy, constraints) that *"resize and reprioritize the compiled roadmap"*. Branderize keeps the rebuildability and provenance lesson but rejects a stronger inference: selecting, sequencing and excluding marketing moves under a semantically rich Strategy still requires model judgment. Pretending that those choices are a pure function merely hides the intelligence inside arbitrary weights and agent-authored impact estimates.

## Decision

### 1. The Plan is agent-generated and provenance-bound (Q1, refined)

Two phases with a typed data boundary:

- **Ingredient production** (agentic): audits, research and probes by specialist roots normally produce structured Evidence and Move Candidate Objects whose citations are exact immutable Evidence Object ids. Evidence keys remain labels, never reference identities.
- **Plan synthesis and routing** (agentic): one durable `rebuild-marketing-plan` CMO task reads the exact brand-wide Strategy Decision, the current active Intents, and available Evidence and Move Candidates. It may consult specialists and use its read tools, record additional typed Evidence through `record_evidence`, and author the Move Candidates it needs through the canonical brain write path. It then calls one typed `publishPlanAndRoute` boundary with the closed Plan, the exact Intent revisions it coordinated, plus the internal/preparatory task requests it selected for included moves. One Postgres transaction publishes the Plan and creates or observes every routed task, or publishes nothing. This routing is model judgment constrained by registered task kinds, not a deterministic `Move → task` compiler. It never executes an external commitment: any later schedule, publish, send, activate, spend, merge, pause, unpublish, cancel, or close still reaches `awaiting_approval` and the human button. The rebuild is a normal `agent/automatic` task and therefore uses Eve, consumes model credit, and may remain queued at the credit gate. V1 adds no prerequisite-task or dependency engine.

The model owns prioritization, sequencing, cross-Intent tradeoffs, exclusions, dependencies, assumptions, rationale, and which registered internal/preparatory task kinds should advance the included moves. Deterministic application code owns the boundary around that judgment: schema validation, same-brand/type checks, exact input references, current-Strategy guard, active-Intent input validation, task-kind/payload validation, Action provenance, idempotency, immutable Object creation, task materialization, and supersession of the previous Plan head. The transaction first locks and verifies the authoritative rebuild task is still `running`, then locks the exact active Strategy before the current Plan head, validates the submitted `{ intent_id, intent_revision }` set against one canonical read of current active Intents, validates and canonicalizes every selected route before any canonical write, and commits the Plan plus that complete selected-route result together. The producing Action stores full typed snapshots of those Intent revisions, excluding preauthorization facts: they are planning provenance, never a common origin or Policy authority. This guarantees the portfolio and routes the model actually coordinated, not semantic completeness of every possible Plan action. A Move Candidate pins the exact Evidence Object ids that originated it; the Plan's producing Action separately pins the exact Strategy, Intent snapshots, Evidence and Move Candidate Object ids used in that synthesis and records the route request/result mapping. Those two Evidence sets need not be equal: newer Evidence may support including an existing candidate, but neither relationship may be reconstructed from a shared label. A newly inserted routed task is intentionally non-Intent-bound: it stores null Intent/snapshot plus its parent rebuild task and exact Plan/Move ids, and its Move-namespaced subject cannot collide with another Move or ordinary Intent-bound work. If active-work dedup observes compatible unfinished work for the same Move, that row remains immutable and the new Plan Action records the observed task id instead. Thus *"which objectives did this Plan coordinate?"*, *"why does the candidate exist?"*, *"why does the Plan say this?"* and *"which work did it start or reuse?"* remain mechanically answerable even though rebuilding is a new model execution rather than byte-identical pure-function replay.

That resource-lock sequence is the first-application path after an operation-key receipt miss. Exact replay is resolved and hash-validated from the producing Action before requiring the historical rebuild task to remain running.

`dependency_move_candidate_ids` is Plan-level explanation and sequencing input, not a runtime task dependency. Trusted validation requires unique same-brand references to other included Moves, rejects self-edges, and requires the resulting graph to be acyclic. The CMO's `routes[]` means only the bounded wave it judges executable **now**; it may route preparatory work that can safely run in parallel but omits work whose required Object or fact does not yet exist. Dependencies are never copied onto task rows and the dispatcher never reads them. Later progress uses ADR-021's `advance-marketing-plan` against the same immutable Plan; it does not manufacture another Plan version. After Plan-routed work reaches a terminal state, a separate best-effort signal may create or observe a general advancement for the **current** Plan when either that source is mapped `created | observed` by the Plan or its immutable parent chain reaches the first ancestor so mapped. Every task from source through anchor must have the same brand, null Intent/snapshot, and the exact same non-null origin Plan/Move pair; the current Plan may be a newer head that deliberately adopted the older-origin anchor. This ancestry is wake-up provenance only: it neither maps the descendant, proves readiness/completion, nor makes it a withdrawable root route. Authenticated humans can also request **Ricontrolla** or target one included Move with **Avvia comunque**. The routed wave enters the ordinary automatic lifecycle subject to the credit gate and `completed | partial | blocked` domain outcomes; v1 promises neither lossless automatic advancement, successful wave completion, nor automatic completion of the entire Plan.

An explicit entry in `excluded_moves` also has one narrow operational meaning: within that publication transaction it supersedes only matching queued **root wave routes** proven by the previous Plan-producing Action or a later `plan_wave_evaluated` Action. Trusted code starts from mapping entries with a non-null immutable root-origin Action/task pair and rechecks the complete stored shape: same brand and exact excluded Move, null Intent/snapshot, non-null Plan/Move, `agent/automatic + queued`, no retry/replacement/schedule lineage, `parent_task_id` equal to the original routing task, and an origin Action whose `created` mapping names that row. An observed lateral descendant carries no root pair and keeps its independent lifecycle. Mere omission withdraws nothing, and the operation never stops running work, direct work, or human commitments. The new Plan Action records the exact task ids actually superseded. This is a bounded withdrawal rule over existing task rows, not a dependency or cancellation engine.

Strategy and Marketing Plan are one brand-level head each, not one per Intent. A Strategy's optional `originIntentId` explains which objective triggered that human choice; it neither limits the Strategy to that objective nor imports its structure/preauthorizations. The single Plan is where the CMO coordinates all current active Intents and records their exact revisions in the producing Action.

Only an explicit authenticated product mutation by a current non-viewer Member may record a canonical Strategy Decision or request **Rebuild plan**; ADR-001 owns the role matrix. In the same transaction, a new Strategy head creates or observes one initial CMO rebuild task with payload `{ strategy_decision_id }`; if that task cannot become durable, the Decision write rolls back. A manual Rebuild action invokes the same task kind through a distinct authenticated request. The active-work guard coalesces concurrent rebuilds for the same Strategy, while a later explicit rebuild may create a new task after the prior one is terminal. Intent creation/refinement/adoption/settlement/abandonment does not automatically enqueue another rebuild; it only changes the deterministic Plan-needs-Rebuild projection and the console invites an explicit Rebuild.

**Rebuild plan** and **Advance plan** are deliberately different console commands. Rebuild reruns synthesis and may supersede the Plan head. Advance pins the current Plan, creates no Object, and lets the CMO append one attributable wave Action plus selected work. **Avvia comunque** is the targeted form: it records one human readiness-override Action for an exact Plan/Move and obliges the CMO either to route valid work for that Move or surface a typed hard block; it grants no external-effect authority.

The old Plan remains canonical history while rebuilding. The UI derives `plan_needs_rebuild` when its producing Action pins a Strategy id different from the current head **or** its canonical active-Intent `{ id, revision }` set differs from the brand's current set. A draft proposal does not count until adoption. The projection never edits the Plan or cancels accepted work, but Advance, Ricontrolla and Avvia comunque refuse to start a new wave until an explicit Rebuild publishes a fresh Plan. Before a new Plan can supersede it, the write transaction verifies that the task's exact Strategy is still active and that the submitted planning Intent refs equal one current ordered read; a mismatch asks the CMO to reload and retry. A task started for an older Strategy completes with the typed `obsolete` outcome and cannot put an obsolete Plan back online. `stale_head` is reserved for a concurrent Plan replacement that changed the expected Plan head while this run was synthesizing.

### 2. The policy UI writes Decisions (Q2)

The original Magister-derived design exposed per-category ask/auto switches. ADR-019 narrows that autonomy boundary: external preparation may be enabled or restricted, but the UI cannot turn any external commitment into an unattended operation. Any policy controls are human-authored brand-scoped `policy_restriction` Decision heads with closed keys and provenance. They may tighten access for that brand; they never change the organization role matrix, expand authority, or lower the human-button floor for schedule, publish, send, activate, spend, merge, pause, unpublish, cancel, or close.

### 3. The dangerous thing is impossible at the connector, not just gated (Q3)

Preparation and commitment are **separate capabilities**. Durable roots may receive only registered, create-only staging operations, such as creating a private draft or a paused campaign. They never receive generic update/delete/publish tools. Schedule, publish, send, activate, spend, merge, pause, unpublish, cancel, and close are human-activation direct task kinds executed later by deterministic code. The “safe direction” is not an authority exception: it uses the same button.

### 4. MCP server channel + agent-native signup, in the roadmap (Q4)

Phase 3/4: expose the product as an MCP server — read tools by default; writes behind opt-in scopes; commitment-task status polling (for example `get_commitment_status(task_id)`) rather than polling a nonexistent pending Approval Action; a redacted authorization/receipt appears only after the human click and later execution facts. A missing integration returns a **one-click link to the authenticated `apps/app` brand-scoped onboarding flow** (the capability degradation of ADR-008 with the UX attached), never a user-owned Eve grant; billing is never bypassable via MCP. Plus agent-native signup (a single POST an agent can make) — cheap to build, markets itself.

### 5. Open questions as a first-class projection (Q5)

The console surfaces what the graph is *missing*: a projection over **active** Intents with low `structure_level` plus incomplete typed recommendations, rendered as questions (their plan asks: *"with paid spend capped at 0, should the roadmap remain fully organic?"*). An explicit answer in the authenticated top-level CMO turn is already the authority to transduce unambiguous acceptance criteria or constraints through `refineIntent`; the typed write commits in that turn without another confirmation, while an ambiguous answer causes another question and no write. A durable choice or exact-Intent preauthorization instead requires the explicit human `recordDecision` boundary. Agent-authored draft Intents appear separately under **Intent proposals** with Adopt/Abandon; they have no structure or work authority. The resulting canonical facts may raise derived structure and unlock autonomy; a Decision does not stand in for missing criteria, and an incomplete measurable recommendation is not committed as a Decision. The external approval inbox is "what awaits execution authorization"; Intent proposals are "what awaits adoption"; open questions are "what awaits information".

### 6. `brand → agent endpoint` is a lookup, never a constant (Q6)

ADR-009's topology (agent as its own deployment behind a proxy) makes per-brand dedicated deployments possible as a future enterprise tier. The resolution of which agent deployment serves a brand is a lookup from day one, so the option never closes. (Their "dedicated server" claim is unverifiable marketing — plausibly one OpenClaw instance per customer, plausibly a shared row with a subdomain. If we ever offer isolation, ours will be mechanically real.)

## Consequences

- `packages/db`: Evidence, Move Candidate and `marketing_plan` Objects remain immutable; a Plan is a trusted singleton head whose producing Action pins its exact input Object ids and typed planning Intent snapshots.
- `packages/brain`: `publishPlanAndRoute` validates and atomically commits a new Plan plus its initial routes; `advancePlanAndRoute` validates and atomically records a later wave against the same Plan without creating an Object. There is no pure `compilePlan(brandId)` function.
- `packages/agents`: `rebuild-marketing-plan` and `advance-marketing-plan` are separate CMO-owned `agent/automatic` kinds. Strategy recording and console Rebuild enqueue the former; Plan progress signals and the human **Ricontrolla / Avvia comunque** boundaries enqueue the latter. Both route only registered internal/preparatory work. Their canonical producing/wave Action receipts—not a generic completion field—record the complete `created | observed` mapping.
- `packages/policy`: reads current brand `policy_restriction` heads as restrict-only inputs, but never lowers the external-commitment approval floor.
- Connectors: create-only preparation and deterministic post-approval commitment are separate registered operations; no generic mutation tool or automatic safe-direction path.
- Console: policy switches UI, the open-questions surface, and a Plan page that separates Rebuild, Ricontrolla/Advance, and per-Move Avvia comunque.
- Roadmap: MCP channel + agent-native signup (Phase 4); enterprise isolation stays open.
- ADR-004 amended in role: the CMO recommends Decisions and generates structured Plans; the human records active v1 Decision heads.

## Alternatives considered

- **A deterministic Plan compiler** — rejected: a semantically rich Strategy cannot be reduced to trustworthy ordering without hiding judgment inside arbitrary weights and agent-authored estimates.
- **Free-form CMO plans without pinned inputs** — rejected: they are not auditable or safely supersedable. Agentic generation is accepted only through the typed, provenance-bound Plan write.
- **Policy as a settings table rendered as switches** — rejected: no provenance; switches write Decisions instead.
- **Let the agent call a commitment tool and park it at an approval gate** — rejected by ADR-019: the agent lacks that tool. It creates a pending direct task, and the deterministic worker becomes the sole executor after the human click.
