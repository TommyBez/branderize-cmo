**Status:** Accepted — 2026-08-06

**Amended by:** [ADR-019](019-human-approved-external-commitments.md) — direct mode splits into transaction-safe automatic work and one-shot human external commitments; executable proposals are tasks

## Context

ADR-006 declared every specialist twice: as an eve declared subagent for in-process CMO delegation and as a named root agent for queue dispatch. ADR-011 then required both activation doors to deduplicate against in-flight work before starting another specialist session.

That guard is not implementable as a hard invariant around a local declared subagent with eve 0.31.3's public API:

- eve lowers each declared subagent into a framework-owned model-visible tool;
- an authored tool cannot shadow that tool because name collisions are rejected;
- authored `ToolContext` exposes no public operation for invoking a declared subagent after application code acquires a database claim;
- hooks observe events after they are durably recorded and cannot intercept a subagent call;
- dynamic subagent availability is resolved at session or turn scope and rechecked before child start, but it is not an atomic claim over the call's task identity.

A prompt sequence such as "check the tasks table, then call the specialist" would therefore be both model-optional and racy. The lane-specific queue claim does not close the gap for a direct child session: that session has no task row on which Postgres can enforce either the agent status transition or the direct lease.

The product still benefits from fast specialist consultation inside the CMO conversation. We accept that a read-only consultation can occasionally duplicate inference spend; we do not accept hidden canonical writes, follow-ups, commitment tasks, or external effects from that lane.

The original queue lifecycle in this ADR came from a CRM path that is no longer the relevant precedent for autonomous agent execution. ADR-018 replaces that portion only. The current CRM `AgentRun` has explicit terminal status, a unique `sessionId` and idempotency key, one `mode: "task"` session, and recovery only while a claimed run is still missing its accepted session id. Once the session exists, a failure is terminal and a later retry or schedule occurrence is a new run.

Branderize keeps three adaptations required by its product: enqueue deduplication is a partial unique index over active task status; an ordinary creator `idempotency_key` deduplicates replay of the insertion that won; and an equivalent self-recheck is staged on the running task before successful completion processes that tuple under acceptance-first and current-origin eligibility, creating or observing at most one active successor. V1 deliberately stores no aliases for other requests coalesced onto that row. ADR-014 D7 separately gives each created deterministic cadence occurrence exact `(schedule_id, scheduled_for)` replay identity and uses partial uniqueness on active `schedule_id` to coalesce later due slots instead of overlapping tasks. The consultative subagent also remains mechanically read-only because Branderize has multiple specialist activation surfaces.

We retain the separation between immediate work and recurring `recheck` work: they have distinct task kinds even when they resolve to the same root specialist and execution logic. Without that distinction, an active booking due weeks from now would make an immediate request for the same subject return `already_active` and wait until the future date.

## Decisions

### D1 — The two declarations have different authority

The shared registry still materializes every specialist in two forms, but they are no longer equivalent activation doors:

1. **Consultative declared subagent** — in-process, session-bound advice to the CMO. It can read context and return analysis, but cannot create durable work or perform boundary actions.
2. **Standalone durable root agent** — task-bound execution started by that root's dispatcher. Each specialist root is its own eve app/deployment (ADR-009), and explicitly configures its standard `eveChannel` with `auth: [localDev()]`: the session and info routes reject production traffic while health remains public. Its agent lane owns one-shot specialist production, budget enforcement, graph writes, registered create-only provider-draft preparation, and Growth's ADR-020 Decision-impact measurement using any available measurement read tools. Its direct lane owns retry-safe deterministic automatic handlers and post-approval external commitments; those handlers do not run inside eve. Automatic handlers may mutate local Postgres state only when effect, Result Action, and guarded task success share one transaction, or perform a side-effect-free idempotent external read whose observation, Result Action, and settlement share one transaction after the read. They never write externally. Context.dev onboarding is not part of either root lane: `apps/app` owns that synchronous deterministic bootstrap and writes its result through `packages/brain`. Human and console writes continue to use the brain path without impersonating a specialist.

They continue to share specialist identity, core instructions, skills, model defaults, `actorKey`, and the attribution-aware model-config factory. Their mode addenda, input/return contract, executable tool surfaces, connection allowlists, and sandbox/egress policies differ mechanically. `packages/agents` generates the consultative form inside `agent-cmo` and the durable wrapper inside the specialist's standalone app from that one shared entry. Each generated `agent.ts` calls the factory locally because declared children do not inherit the parent's model config; self-copies do inherit it.

### D2 — Consultation is read-only by construction

The generated declared-subagent manifest receives a `consultTools` surface containing only:

- brand and graph reads;
- read-only research tools and connection methods;
- helpers that transform data without persisting it.

It physically excludes:

- `produce_object`, `recommend_decision`, `record_evidence`, and every other graph mutation;
- `schedule_recheck`, task creation, and follow-up scheduling;
- commitment preparation/approval/execution and every connection method with an external effect.

Declared subagents inherit no authored parent slots, but eve can still supply framework-default tools. Their generated definition therefore disables networked/effectful defaults explicitly: the consultation sandbox may hold disposable scratch files, but uses `deny-all` egress. External research is exposed only through authored or connection operations whose read-only behavior is allowlisted and validated in code.

The subagent definition configures a token-capped `ConsultationReturn` as its default task-mode result, and the CMO requests the same shape when delegating:

```text
{ summary, recommendations[], source_refs[], suggested_work[], open_questions[] }
```

eve's native subagent tool permits the caller to provide an `outputSchema`, so the fixed shape is not an authorization boundary by itself. Any consultation reused as durable input is validated again by application code. Safety comes from the missing mutation and effect tools, not from trusting the returned shape.

The configured contract contains no `output_object_ids` or claimed `follow_up_tasks`, because the subagent has no capability to create either. `suggested_work` is advice to the CMO, not evidence that a task was enqueued. The result is conversation material, not a canonical Object. `open_questions` likewise returns to the parent CMO as data; the task-mode child cannot call `ask_question`, enter `session.waiting`, or retain a parked turn for a human reply. Tool descriptions and instructions teach the CMO when consultation is appropriate; the restricted manifest ensures that misrouting cannot turn into a durable side effect.

Direct consultations do not create task rows and are not deduplicated. Their child sessions remain metered and observable through normal eve telemetry. Eve propagates the CMO session's initiating/current auth into the declared child and exposes its immediate/root lineage, but the CMO parent hook does not receive the child's `step.completed` and the declared child does not inherit the parent's model config. The generated declared specialist therefore mounts the mandatory shared audit extension and calls the shared model-config factory in its own scope. Duplicate consultation spend is an explicit accepted limitation, not a property the task lease claims to prevent.

### D3 — Every durable specialist execution starts from one active task

No named specialist root may be activated without a task row. Any immediate CMO request that may create or supersede an Object, record evidence, prepare an external draft, or create a human commitment enters through a typed task path. Agent work requested by trusted producers or typed lateral edges uses `enqueueOrObserveTask`; a human `recordDecision` may instead atomically create ADR-020's exact future impact task as part of that canonical boundary. Agents only recommend Decisions. Preparing a human commitment creates a distinct direct row in `awaiting_approval` through ADR-019's constrained service. Agent-judged future follow-ups use `scheduleRecheck`; deterministic daily/weekly cadences use durable `schedules` that the root evaluates and advances before draining, materializing a task occurrence only when that schedule has no queued/running one.

The shared `enqueueOrObserveTask` service resolves `brand_id` from trusted application context and accepts one trusted origin branch. Ordinary work validates a same-brand `intent_id`; the narrow Plan route accepts only an already-validated Plan id, included Move Candidate id, and authoritative routing task from `publishPlanAndRoute` or `advancePlanAndRoute`. Both branches validate the registered `kind` and typed payload, resolve the specialist, and derive the registry subject. Neither tenant nor any complete common origin/subject field is model-authored. The only model-visible origin selector is the interactive CMO operation below: its `intent_id` is a candidate semantic reference, not an `IntentSnapshot` or capability token.

```text
request_specialist_work({ intent_id, kind, payload })
  -> accepted       { task_id, task_state: scheduled | queued,
                      origin: { intent_id, intent_revision } }
  -> already_active { task_id, task_state: scheduled | queued | running,
                      origin: { intent_id, intent_revision } }
```

This operation is exposed only in an application-bound top-level CMO turn whose current caller is the conversation owner and still has Member role `owner | admin | member`; child, self-copy, consultation, task/autonomous, system and viewer contexts cannot execute it. The CMO may nominate an existing or just-declared/refined active Intent when the current human request identifies it without ambiguity, including “continue Intent X”. Semantic disambiguation is the CMO's authored transduction judgment, while the executor mechanically enforces session/conversation/Member/tenant/state guards. When several Intents remain plausible, the CMO asks which one and makes no tool call. There is no persisted conversation focus and no second confirmation. For this wrapper the stable creator identity is derived from `(conversation_id, session_id, turn_id, intent_id, digest(kind + canonical typed payload))`; its canonical hash covers `intent_id`, `kind`, and that payload. Eve's `call_id` remains causal telemetry and does not participate in either identity. The same semantic request re-emitted in the turn with another call id therefore converges, while a different kind or payload receives a different key rather than being collapsed merely because it shares turn and Intent. A request whose insertion wins receives exact creator-key replay; `already_active` instead reports the existing row and its preserved origin without storing an alias for the observing request, so replay after that row becomes terminal may legitimately create new work.

A durable root already executing a task instead uses `request_lateral_work({ kind, payload, rationale })`. Trusted Eve/task context supplies its current task id, brand, parent, and common-origin branch; the model cannot pass an Intent, Plan, Move, subject, or worker. The registry must contain the exact `(source worker → target worker, kind)` edge. If the source is Intent-bound, insertion resolves that Intent's current revision; if it is Plan-routed, the target must declare `acceptsPlanRouteOrigin: true` and receives the same exact Plan/Move pair with null Intent. A newly inserted lateral row also receives immutable `parent_task_id = source_task_id`; observing an active equivalent preserves that row's existing parent and records no alias.

Only the branch that actually inserts a new Intent-bound row locks the canonical Intent, requires `status = 'active'`, reads its latest revision plus applicable active exact-Intent `intent_preauthorization` heads with `content.authorized = true`, whose producing Actions link that Intent, builds the shared typed `intent_snapshot`, and persists it beside the kind payload. A draft is a non-executable agent proposal and contributes no structure or preauthorization. An active false head is a revocation and is excluded. Roadmap, model and brand-restriction Decision heads are also excluded. The caller cannot send that snapshot. Creator-key lookup and canonical-hash validation happen before current Intent guards, so replay after Intent adoption, refinement, settlement, or abandonment returns the historical task instead of comparing against current state. Only on a replay miss does the service lock and revalidate the active Intent and construct the snapshot. An active-key conflict likewise returns the winning row and its original snapshot. A new creator key captures a newer revision only if it results in a new task row.

`publishPlanAndRoute` and `advancePlanAndRoute` invoke the same internal create-or-observe primitive inside their enclosing transactions, but only for a target kind declaring `acceptsPlanRouteOrigin: true`. Trusted code persists `intent_id = intent_snapshot = null`, the exact Plan id, validated included/non-excluded Move Candidate reference, and the authoritative rebuild/advancement task as parent. It rejects a raw registered subject beginning with the reserved `plan-route:` prefix, then namespaces it as `plan-route:<move_candidate_id>:<registered-subject>`, so another Move or an Intent-bound request cannot collide. An active row is accepted as `observed` only when it has the same kind and derived subject, is non-Intent-bound, and names that same Move; its original Plan/parent/provenance remain immutable and the current routing Action records the association. That mapping preserves a non-null root-routing Action/task only if an earlier Plan/wave `created` mapping originally materialized the row; a semantically equivalent lateral descendant may be observed but has no root origin. The registered subject, not an additional payload comparison invented by this path, defines semantic equivalence. Any incompatible conflict rolls the complete publication or wave transaction back.

The new-Plan publication may withdraw an old root wave route only when its Move is explicitly present in `excluded_moves`. After full Plan/route validation, it starts from exact ids whose mappings carry a non-null root origin, then conditionally locks and updates same-brand `agent/automatic + queued` rows with null Intent, non-null Plan/Move, no retry/replacement/schedule lineage, a parent equal to the original routing task, and an origin Plan/wave Action whose `created` mapping names that row. Returned rows become terminal `superseded`; the new Plan Action records their exact ids per Move. The ordinary agent claim and this update compete on the same row: claim-first leaves `running` untouched, publication-first makes the claim affect zero rows. Omission, direct work, human commitments, lateral descendants and terminal rows never match.

The Plan's Move dependencies do not create task dependencies. Only route requests the CMO judges executable now become rows; their ordinary lane rules determine claimability. A route may later use `request_lateral_work` for another phase of the **same** Move when it has produced the required Artifact, but that does not activate a different dependent Move. A separate dependent Move left unrouted may be selected by a later `advance-marketing-plan` task against the same Plan. After ordinary Plan-routed work terminalizes and commits, a separate best-effort creator may request that evaluation. It resolves the current Plan head and accepts a source directly adopted by an exact `created | observed` producing/wave mapping or a source whose immutable parent chain reaches the first such adopted ancestor. Source through anchor must remain same-brand, null-Intent, and on one identical non-null origin Plan/Move pair; the current Plan may be newer than that origin when it adopted the anchor. The stable key remains the exact terminal source plus current Plan. This wakes the CMO after a same-Move lateral/recheck/other derived phase finishes, but neither maps that descendant nor treats terminality as Move readiness or completion. Enqueue failure never rolls back the terminal result. The explicit human **Ricontrolla** path recovers an absorbed or unqualified observed-row signal, while **Avvia comunque** creates a distinct targeted advancement and records the human Action. No task result cascades through the Plan graph.

An immediate kind and its future-recheck kind are separate queue identities. Every immediate kind that permits a follow-up declares one deterministic `recheckKind` in the registry. That target is a registered kind owned by the same durable root; both kinds may share a brief schema, output contract, core brief builder, and execution handler. If the source kind accepts Plan origin, the target must also declare `acceptsPlanRouteOrigin: true`. The recheck kind may point its own `recheckKind` relation back to itself for recurring work. Names such as `seo-audit` and `seo-audit-recheck` are illustrative, not a naming convention.

`scheduleRecheck` is an authored, constrained tool available only to durable roots. The agent judges when and why it should return and supplies only bounded, registry-validated scheduling input: the typed recheck payload, `due_at`, and human-visible rationale. It does not choose an arbitrary task kind. The current `task_id` comes from trusted Eve session auth/context established by the authenticated machine channel; application code reloads the current row, resolves its sole authorized `recheckKind`, verifies that the target belongs to the same root and accepts the current origin branch, validates the target kind's payload, and derives `brand_id`, trusted origin, `subject_key`, and `worker_key` through the task row and registry. The model never supplies any of those identities or the target `kind`. For the first cross-kind future booking, that tool call itself is the new-work boundary: an Intent-bound insert requires the Intent still be active and captures its latest snapshot then, while a Plan-routed booking preserves null Intent and the exact source Plan/Move. The committed booking survives later source-task failure. Only an equivalent running self-recheck stores a payload template in `next_*`; successful settlement rechecks Intent eligibility and resolves the then-current active revision, or clears the tuple with zero successor when the Intent is inactive. A Plan-routed self-successor keeps null Intent and the exact source Plan/Move pair. If conflict-safe create-or-observe finds an already-active successor, that row keeps its own earlier origin. Only a separate explicit Intent declaration changes branches. This agentic protocol never reads or writes ADR-014 D7's deterministic daily/weekly `schedules`: those durable rows pre-exist runs, are evaluated and advanced independently of task settlement.

For ordinary future work, the tool calls `scheduleOrRescheduleTask`: it inserts a new booking or moves an already-scheduled equivalent booking's `due_at`, rationale, and scheduling template. Mutation is legal only when the existing booking's complete accepted common origin equals the newly derived one—exact Intent id/revision/snapshot or exact Plan/Move pair. An origin mismatch returns `origin_conflict` and leaves the booking unchanged, so a new payload can never be paired with an older snapshot. The first follow-up from an immediate task has a different kind and therefore a different queue identity from the running task; a newly inserted row stores immutable `parent_task_id = source_task_id`. Rescheduling or observing an existing booking preserves its original parent and creates no substitute lineage.

An equivalent self-recheck occurs when a running recheck schedules the same registered recheck kind and subject again. The partial unique index prevents a second active row, while moving the running row's own `due_at` would cause its next execution to disappear as soon as that row completes. The deterministic tool implementation therefore leaves the current `due_at` and accepted payload unchanged and updates the running task's single pending-successor slot instead:

```text
next_due_at
next_payload
next_rationale
```

Repeated valid self-recheck calls replace that pending booking; they do not create additional successors. The model chooses the bounded schedule data, but trusted code chooses the row and applies the database transition.

The self-recheck write is one conditional statement against the current task, not a read followed by a general source-task lock:

```sql
UPDATE tasks
SET next_due_at = :due_at,
    next_payload = :payload,
    next_rationale = :rationale
WHERE id = :current_task_id
  AND status = 'running'
RETURNING id;
```

The application supplies `current_task_id` from trusted session context. If `RETURNING` yields no row, `scheduleRecheck` returns `task_closed` and performs no fallback insert or reschedule. Every terminal transition updates that same physical row, so Postgres row-update serialization settles the race without a separate `SELECT ... FOR UPDATE`: if scheduling commits first, successful agent completion processes the staged tuple only after any Intent-acceptance Verification and under the resulting current-origin eligibility—creating/observing a successor or clearing the tuple with none—while agent failure/cancellation or direct/automatic exhaustion clears it; if settlement commits first, the conditional scheduling update affects zero rows. Human commitments never use this successor slot. This narrow self-target guard is a single conditional statement and does not itself require an interactive transaction; it still runs through the canonical Drizzle/`pg` adapter selected by ADR-005.

This is not a general liveness fence on the task that asks for other future work. A follow-up from an immediate kind targets a distinct recheck row, and scheduling from another authorized task retains the accepted last-write-wins scheduling semantics. The conditional guard exists for the self-recheck only because its trusted source task and target booking are the same row.

There is exactly one future booking per queue identity even when multiple authorized tasks owned by the same root independently schedule it. If the target row is still scheduled and its common origin matches exactly, every valid `scheduleOrRescheduleTask` call atomically replaces that row's `due_at`, typed payload, and rationale while preserving its parent; a mismatched origin changes nothing. If the equivalent target is running, every valid same-origin call atomically replaces its single `next_due_at`, `next_payload`, and `next_rationale` tuple. When successful settlement materializes a genuinely new self-successor, trusted code sets its immutable `parent_task_id` to the completed occurrence; observing an equivalent active row preserves that row's older parent. Postgres row-update serialization arbitrates concurrent compatible callers: the last valid database write wins. "Last" means the update that wins database ordering, not the agent that started first or whose wall-clock request arrived last. There is no earliest-date priority, preference for an immediate source task, field merge, or second successor.

Postgres arbitrates concurrency with the partial unique index:

```text
(kind, brand_id, subject_key) WHERE status IN ('awaiting_approval', 'queued', 'running')
```

ADR-018's ordinary `queued | running | succeeded | failed | cancelled` lifecycle remains complete for agent tasks except for one bounded publication transition: a root wave route proven by a Plan/wave `created` mapping and selected by a later Plan's explicit `excluded_moves` may move `queued → superseded`. That state is terminal, carries `finished_at` and `outcome_code = 'plan_move_excluded'`, and is never claimed, reclaimed, retried in place, or given session/stage/`next_*` state. ADR-019 separately adds `awaiting_approval`, `outcome_unknown`, `expired`, `needs_regeneration`, `dismissed`, and `superseded` for direct/human commitments. Only retry-safe direct/automatic rows may additionally be rendered as reclaimable or awaiting retirement from `leased_until` and `attempts`. An ordinary task stores one stable creator `idempotency_key UNIQUE` plus its canonical creation hash. A created deterministic cadence task instead stores unique `(schedule_id, scheduled_for)`, and a partial unique index on active `schedule_id` permits at most one `queued | running` occurrence for that schedule. A later due evaluation behind it creates no task or alias; it advances the schedule and updates only its coalescing summary. V1 still stores no alias for a distinct ordinary request that only observed or rescheduled another active row.

Enqueue first resolves the supplied creator key and validates its canonical request hash. If that key exists, replay returns its historical task—even when another equivalent task is currently active and even if an Intent has since advanced. Otherwise, if insertion wins, the caller pokes the dispatcher and returns `accepted`. If the active-key constraint wins, `enqueueOrObserveTask` returns the existing row as `already_active` without modifying its `due_at`, typed payload, common origin, or human-visible rationale and without persisting the caller's distinct request key. A Plan route additionally rejects the conflict unless the row is non-Intent-bound and carries the same Move reference. A genuinely new request uses a new key. Before inserting direct/automatic work, the same transaction may retire a matching expired exhausted retry-safe row. A human commitment instead receives a proposal-specific subject identity and remains `awaiting_approval` until the exact human transition; later Intent refinement or proposal editing does not refresh its origin. A commitment derived from Plan-routed work inherits null Intent plus the exact Plan/Move pair and still follows `direct/human → awaiting_approval`; it is never retired or reclaimed by the generic direct helper.

Dedup ensures one active logical work item for ordinary task identities. The execution guard then depends on both mode and activation: agent/automatic uses ADR-018's one-shot eve handoff; direct/automatic may use `FOR UPDATE SKIP LOCKED` plus a bounded lease; direct/human follows ADR-019's approval receipt and one-shot provider call.

For `execution_mode = agent`, the root first applies the agent-specific autonomous-credit gate. With balance available, claim selects a due `queued` row with `session_id IS NULL` only where `worker_key = SELF AND kind IN compiledSupportedKinds`, then atomically changes it to `running` and records `started_at`; at zero balance it leaves the row untouched. It does not read or increment `attempts` and installs no execution lease. After the claim, the machine channel reloads and validates the authoritative kind payload plus its discriminated common origin. An Intent-bound row loads only its immutable `intent_snapshot`; a Plan-routed row requires null Intent/snapshot, validates its same-brand Plan/Move types and references, and loads those exact Objects; origin-free registered work loads neither. Current safety/capability facts and brand restrictions may still tighten every branch, but runtime cannot replace a pinned snapshot or treat Strategy/Plan as preauthorization. It then constructs a typed billing context from the row, projects its verified `brand_id` as a trusted scalar in `taskAuth`, and calls ``from(`task:${taskId}`).send(brief, { auth: taskAuth, mode: "task", outputSchema })``; the payload-free dispatcher poke and model cannot choose that brand. The raw address is channel-local and eve adds the channel namespace. A CRM-style `session.started` hook binds `ctx.session.id` only when `ctx.session.parent` is absent, while the post-send path binds the returned top-level `session.id`; self-copy child sessions do not participate. Those paths race to fill the single authoritative id. Only a `running` row still missing it after five minutes may be reset to `queued`, atomically clearing `started_at`, staged completion, and `next_*`. Once the id is stored, that task is never redispatched. If both binding paths missed an accepted session, recovery can physically start another only after the unrecorded owner has released the shared address; the guarantee is one authoritative binding, not proof of one physical acceptance.

For `execution_mode = direct AND activation = automatic`, the existing bounded retry protocol remains: select a due unleased-or-expired row below `MAX_ATTEMPTS`, claim with `FOR UPDATE SKIP LOCKED`, and increment attempts. The registered handler must satisfy ADR-018's retry-safety boundary: a local mutation commits its stable-key idempotent effect, Result Action, and guarded `running → succeeded` settlement in one Postgres transaction; a side-effect-free idempotent external read may precede that transaction, but its observation, Result Action, and settlement remain atomic. A zero-row terminal compare-and-swap rolls every local write back, and the lane never performs an external write. For `direct AND human`, only `approveTask` may create `queued`; registry-declared serialized kinds first acquire their trusted target slot in that approval transaction. The responsible root completes deterministic preflight, re-derives any persisted conflict key from the final registered payload, then claim atomically checks its Approval Action and changes it to `running`, with no lease or attempts. Neither direct path consults the agent credit balance. The human claim is the point of no return: it makes at most one provider call and never returns to `queued`. Generic helpers must branch on mode and activation before reading balance or lease/attempt fields. Unsupported kinds remain untouched; an obsolete human commitment is explicitly moved to `needs_regeneration` before handler support is removed.

Only dispatcher code inside the custom machine channel starts a specialist root in production. Every task's registered kind supplies worker, mode, activation, and execution contract; a root may claim only `worker_key = SELF AND kind IN compiledSupportedKinds`. Agent mode attempts one eve run through the channel-local address with `mode: "task"`; `session.id` is its authoritative runtime identity. Direct mode executes the fixed plain-code handler inside the same responsible deployment. For a human commitment, preflight and the claim transaction reload and validate the final revision and durable Approval Action before the row becomes `running`; they do not re-evaluate the approver's later Better Auth Member row or organization-wide role. After that point the fixed handler consumes the claimed immutable payload and does not reinterpret or reauthorize it. Neither the model nor an HTTP caller supplies a replacement brief or connector method. Public/user routes cannot invoke a root directly, and an eve callback never becomes a second commitment executor.

Dispatch wakeup is centralized but execution is not. One Vercel Cron route in `apps/app` verifies `CRON_SECRET` without forwarding it, then uses `DISPATCH_SECRET` and `Promise.allSettled` to send seven parallel `POST /internal/dispatch` pokes with independent two-second timeouts. `/internal/dispatch` is authored as a route of each root's custom machine channel. It carries no task, brand, payload, worker, schedule, or target selector: the CMO and six specialist roots authenticate only the raw Bearer poke, return `202`, and register their own work through the route's `waitUntil`, using exclusively their compiled root-and-kind allowlists. There are no Eve schedules. A process-local `collapsing()` guard is best effort. On every tick, each healthy root first performs a bounded due-schedule pass for `worker_key = SELF`: one transaction advances the schedule CAS, locks any queued/running occurrence, and either inserts/observes the exact `(schedule_id, scheduled_for)` task or records the due evaluation only in the schedule's coalescing fields. It then terminalizes only its own stale human commitments as `outcome_unknown` and runs a small bounded number of invocation-local slot loops. Schedule CAS, exact replay identity, partial uniqueness on active `schedule_id`, atomic task claims, bounded direct/automatic leases, and one-shot human-commitment claims arbitrate overlapping pokes across instances. The task-row lock orders terminalization against materialization; a credit-blocked queued occurrence remains the only active task while later slots coalesce and never form a backlog. Each slot chooses by lane order at each claim: human commitments by deadline and Approval time, remaining start capacity to retry-safe direct/automatic work FIFO, then agent FIFO. A direct/human slot may scan ids, but it preflights and claims one row only when ready to enter its provider handler, settles it, and only then selects another. `DRAIN_BATCH` counts executions started rather than ids scanned or rows pre-claimed. This is query order, not stored priority, preemption, or a global semaphore; overlapping Fluid invocations multiply the invocation-local limit (ADR-009, ADR-014, ADR-019).

For `execution_mode = agent`, `finishTask` obtains `task_id` from trusted session context, validates that kind's `TaskCompletion`, derives required principal outputs from the already-validated result, and stages the normalized canonical value without changing status. Caller-selected ids must be duplicate-free; the stored sorted set-union must be same-brand, permitted by the kind's output contract and linked through each producing Action to that exact task. The list is intentionally non-exhaustive; the complete task Object history remains graph-derived. It first checks the structural Eve session relationship: when `ctx.session.parent` is present, execution fails deterministically with `FINISH_TASK_ROOT_ONLY` and writes nothing. Only the top-level root session may stage completion. Built-in specialist self-copies otherwise retain the full inherited work surface, so a child may perform task-bound writes and return its results and candidate deliverables; the parent selects additional outputs and calls `finishTask`. The tool may remain model-visible in a child. Dynamically omitting it would be optional UX only, never the authorization boundary.

`finishTask` returns the normalized staged completion for the root to mirror. `result.completed` may carry that top-level return for telemetry but cannot replace the staged value; diagnostic comparison applies the same normalization before declaring a mismatch. Only the authoritative top-level task session's `session.completed` with that value normally changes `running → succeeded`; child terminal events are telemetry and usage, not task settlement. Top-level completion without a valid staged value becomes `failed` with `MISSING_TASK_COMPLETION`. `completed`, `partial`, and `blocked` are all valid domain outcomes under `succeeded`. Delivery error, `turn.failed`, `session.failed`, and application cancellation of the authoritative top-level session are terminal `failed` or `cancelled` transitions. Eve follows `turn.cancelled` with `session.waiting`; Branderize ignores that boundary and never reuses the address. Other waiting remains anomalous. A failed terminal projection leaves the task running for alert and manual stream-based reconciliation, never redispatch. The root-only check uses existing Eve context and the already-bound authoritative `session_id`; it adds no table, lease, fill-once field, or handoff generation.

ADR-020's `verify-roadmap-decision-impact` is one such origin-free agent task. `recordDecision` has already created the exact Growth row due at the horizon with null Intent/snapshot and null Plan/Move; its immutable Decision and producing Action retain causal provenance. Its one-shot session passes through the ordinary credit gate, may use any compiled measurement read tools, writes any current `metric_observation` through `record_evidence`, and stages `TaskCompletion.status = 'completed'` with `intent_acceptance = null`, `result.judgment = supported | not_supported | inconclusive`, rationale and the required Evidence id for a conclusive judgment. Terminal settlement validates the same-brand/task links and atomically appends the Growth-authored Verification Action, links the task result, never changes an Intent, and, only for a still-active `not_supported` head, creates or observes the registered origin-free `decision-reconsideration` CMO task. That task's closed completion is either `recommended(report_object_id)` with an exact same-task report or `obsolete(decision_inactive)` without one. Its origin Intent remains immutable causal provenance and may be terminal; the CMO may recommend a replacement but cannot call the human-only `recordDecision` boundary.

Compaction follows session lineage for telemetry and reporting but not commercial billing. At the CMO root, a specialist root, a self-copy, or a declared specialist, Eve 0.31.3 may compact with zero or more model calls and emits raw `compaction.requested`/`compaction.completed` without a billable `step.completed` or authoritative usage/cost/generation id. The audit hook persists those events at the emitting session, while the charge projector ignores them. Each generated declaration preserves the active model's merged Gateway provider options, and a self-copy inherits them, so Custom Reporting classifies the attributable spend as expected Branderize platform COGS. No credits are consumed and no estimate, generation lookup, Eve fork, OTel billing source, or reconciler turns that overhead into `model_charge`.

For `direct/automatic`, no eve event exists: a registered retry-safe deterministic handler may settle success or remain under its bounded retry policy. The Result Action is not a post-commit audit append: it and the handler's local effect or external-read observation commit with `result_action_id`, `finished_at`, lease cleanup, and the `status = 'running'` compare-and-swap to `succeeded`; a lost compare-and-swap rolls the whole transaction back. A provider-outcome Verification poll is one such handler: it reloads the accepted Result Action, performs a side-effect-free idempotent provider read, and records a typed Verification Action without eve, an LLM, or agent credits. `pending`, `completed`, provider-domain `failed`, and provider-domain `unverified` settle the current poll as technically `succeeded`; only `pending` creates or observes one same-root successor atomically after releasing the current active identity. Deadline and technical exhaustion record `unverified` with distinct reason codes, and only technical exhaustion marks the poll task `failed`. After any terminal Verification settlement commits, a distinct fire-and-forget creator may wake the current Plan by deriving the originating commitment through the immutable Verification/poll/Result links and applying ADR-021's existing ancestry guard; `pending` never does. The poll remains origin-free, and enqueue failure cannot roll back its Verification. For `direct/human`, the provider-specific fixed handler must return ADR-019's closed `CommitmentOutcome`: `accepted` with a schema-valid stable receipt settles `succeeded`, `rejected` is permitted only with proof of non-application and settles `failed`, and `unknown` settles `outcome_unknown`; every result is terminal. The generic dispatcher only exhaustively switches over that union. It never interprets HTTP statuses or SDK exceptions, and any unexpected throw after claim becomes `outcome_unknown`, never `failed`. Appending its Result Action, linking `result_action_id`, and the compare-and-swap from `status = 'running'` are one Postgres transaction, so a lost terminal race rolls back the Action too. A billable `succeeded` inserts its sole `action_charge` in that transaction from the approval's pricing snapshot; if its kind declares eventual verification, the same transaction creates or observes the first poll task. No other result is charged. Human commitments never carry `next_*`. Explicit administrative cancellation appends its own Action and may win only from `awaiting_approval` or `queued`; removing or degrading the approver is not an implicit cancellation. Once the claim has changed a row to `running`, the only application outcomes are `succeeded`, `failed`, or `outcome_unknown`; neither administrative cancellation nor a deadline can revoke or reclassify a provider request that may already be in flight.

`retireExhausted` is direct/automatic-only. It cannot select a human-activation row. Agent failures are already terminal, and retrying agent work is a new task. Retrying an external commitment after `failed` or `outcome_unknown` also creates a new task, but only through another human approval.

An authoritatively bound agent task has no execution lease or reclaim path. Eve may replay an interrupted step inside that run, and a retry-safe direct/automatic handler may overlap after lease expiry only when its registered semantics make that acceptable. A human external commitment has neither mechanism: after its claim there is no automatic provider re-call. Before each drain, its responsible root closes still-`running` rows older than ADR-019's `STALE_AFTER = 10m` as `outcome_unknown`. Its provider call is aborted after `PROVIDER_HTTP_TIMEOUT = 90s`; the custom-channel `waitUntil` remains inside Eve's shared Fluid Function, whose v1 uncustomized Default Max Duration is 300 seconds. Provider idempotency keys remain useful where supported, but an unknown outcome still stops for a human because no database transition makes the API call transactional.

The ordinary-work dedup identity is never `(specialist, brand_id)` alone. Every registered task kind defines a deterministic `subjectKey(payload)`, producing `(kind, brand_id, subject_key)`. Immediate and recheck kinds may derive the same subject but remain distinct by kind. Human commitment proposals are the deliberate exception to semantic coalescing: each independent proposal uses a stable identity such as `commitment:<task_id>`, while creator-key replay still returns the same row. A separate trusted `commitment_conflict_key` may exclude simultaneous `queued | running` inverse commands without coalescing their proposal identities, ordering them, or acting as a caller-supplied nonce.

The queue does not carry a separate contract version in v1. A published kind changes only backward-compatibly. Breaking payload, preview, ownership, policy, handler, or execution semantics use a new kind. Agent and direct/automatic rows may drain under expand-contract. Human commitments that can no longer execute safely are moved to `needs_regeneration` before the old handler is removed; they are never reinterpreted by a new generic executor.

The active-key constraint promises one equivalent active task row, while the task's creator key protects replay of the creation that won. V1 intentionally does not promise exact replay for distinct requests coalesced onto that row. Completed work may be requested again under a new creator key; eve step replay and direct lease expiry still require conflict-aware brain writes and idempotent boundary tools.

### D4 — Promoting consultation to durable work creates a task

If a human later asks to save, develop, schedule, or act on a consultation result, that current request must identify the target same-brand **active** Intent without ambiguity before the CMO calls `request_specialist_work`. The typed payload may include a bounded `consultation_context`: selected recommendation keys, a size-capped snapshot, and origin session/message/turn references added or verified by application code. This is conversational brief context, not an artifact and not canonical evidence. Artifact-sized content still travels by Object id. The service validates every reference, selected value, snapshot limit, and task payload, then requires the Intent still be active and builds the immutable common snapshot from its latest canonical revision in the winning insertion transaction; a previous model result is input, never trusted proof or authority to choose an Intent.

The root specialist may reuse the consultation rather than repeat its research, but it remains responsible for validating the durable output contract and performing the canonical write. Promotion never lets the CMO write under a specialist's identity and never grants write tools back to the declared subagent.

If the user requests durable work from the outset and identifies its Intent without ambiguity, the CMO skips consultation and enqueues it directly. Otherwise it asks which active Intent the work should serve.

The onboarding refinement is the concrete HITL form of this rule. `apps/app` first creates the human-authored active revision-1 onboarding Intent, obtains context.dev data during the server-side onboarding request, and commits Brand Context v0 through `packages/brain` as `system:context-dev`; no root task is involved. The persistent CMO conversation may then run the local product-marketer declaration in task mode for read-only diagnosis. When that consultation returns `open_questions`, only the top-level CMO may present them with `ask_question` and remain in `session.waiting`. An explicit current non-viewer human reply is already the authority for the CMO to transduce unambiguous criteria/constraints through typed `refineIntent` in that same bound conversation turn; there is no second confirmation or Approval Action. The CMO is the producing Action Actor, while trusted runtime context records the authorizing human/Member and conversation/session/turn/call lineage without changing the Intent author. Ambiguity produces another question and no write. Task/autonomous CMO, durable roots, self-copies, consultative subagents, and system Actors cannot invoke that branch. A durable choice or preauthorization becomes canonical only when the authenticated human explicitly invokes `recordDecision`; the CMO may prepare the recommendation but cannot call that boundary or impersonate the human.

After the answers are canonical, the same explicit human request identifies the onboarding Intent for a separate `request_specialist_work` call and no second confirmation is required. Winning task creation snapshots the then-current onboarding Intent revision and applicable active exact-Intent preauthorization Object ids/policy facts with `content.authorized = true`. The standalone root executes that pinned statement, criteria, and constraints; it may reload those immutable Decisions and current capabilities, but a later refinement cannot rewrite its accepted input. If its brief is still underspecified, it stages `TaskCompletion(partial | blocked)` with `open_questions` and ends the run. The CMO can ask those questions, refine the canonical Intent, obtain an explicit human Decision, and enqueue another task whose newly inserted row receives the latest revision; it never sends a follow-up to, parks, or resumes the completed task session.

- a conversation transcript selector can include a raw child event, can select by inherited `conversation_id` or `root_session_id` instead of exact `session_events.session_id = cmo_conversations.session_id`, or folding the ordered exact-root events through `defaultMessageReducer()` omits or duplicates the parent `action.result(subagent-result)` tool part;
- a compaction lifecycle event creates a charge, compaction overhead changes admission or credits, its active model loses merged Gateway attribution, or report-to-ledger classification treats that expected platform COGS as a reconciliation error;
- Eve end-to-end coverage does not execute and verify correctly attributed winning charges plus Gateway `user`/tags for a top-level root step, a built-in self-copy step, and a declared-subagent step, including exact-root transcript selection and default-reducer reconstruction, a fail-closed current/initiator mismatch, a provider-options merge case, and zero-call plus model-calling compaction fixtures that persist raw lifecycle events with no charge.

Self-copies inherit the work authority of the session that spawned them with one explicit exception: task settlement remains top-level-root-only. CMO copies see only the same consultative specialist surface as the CMO; named specialist-root copies retain every parent work tool and remain inside the already-dispatched task, but `finishTask.execute` rejects their child context with `FINISH_TASK_ROOT_ONLY`. Their parent owns aggregation and the sole valid completion stage. A copy cannot widen its parent's tools or turn consultation into durable work.

This is a capability boundary, not a prompt convention.

## Consequences

- Native in-process specialist consultation, structured returns, cancellation, and control-plane events remain available to the CMO.
- Every durable specialist outcome and commitment enters the task lane. The active-task constraint prevents equivalent ordinary work rows and creator keys protect exact replay, while independent commitment proposals intentionally keep distinct identities. Eve owns durability after authoritative session binding; only the documented unbound agent handoff and bounded retry-safe direct/automatic lease expiry can create application-level overlap. Human external commitments never auto-reclaim after claim.
- Intent adoption/refinement and task execution now have a deliberate temporal boundary: newly inserted work requires active status and receives the latest canonical revision, while replay, dedup, approval editing, waiting, claim, and execution preserve the snapshot of the row that already exists. A later refinement changes future work, not work already accepted; an unadopted draft changes no work at all.
- A consultation may overlap a durable task, repeat external reads, or return stale or conflicting advice; it still cannot commit either result.
- Declared specialist sessions no longer park on graph-write, boundary-action approval, or connection onboarding. A missing brand-owned read connection simply removes that capability and is surfaced to the application; `apps/app` owns any later brand-scoped connect flow.
- Only the persistent CMO conversation is HITL. Specialist consultations return questions to it and durable roots terminate with `partial` or `blocked`; neither specialist surface waits for a human turn. Context.dev bootstrap is synchronous deterministic application onboarding, while any later product-marketer refinement is ordinary agent work.
- Durable autonomous sessions and CMO chat create the same `awaiting_approval` direct task at an external commitment boundary; neither parks an executable tool. The responsible root's plain-code lane executes after the click.
- The CMO receives immediate answers for consultation but receives task state for durable work. Agent tasks render scheduled, queued, running, succeeded, failed, cancelled, and the narrowly provenance-linked superseded outcome for an explicitly excluded root wave route. Human commitments additionally render awaiting approval, unknown outcome, expired, needs regeneration, dismissed, and superseded. Reclaimable and awaiting-retirement are direct/automatic-only substates.
- An immediate duplicate request observes the active immediate task without rewriting its accepted brief or timing. A future recheck uses a distinct registered kind, so its active booking cannot swallow a request to do the work now. Only `scheduleRecheck` may reschedule an equivalent agentic future booking; concurrent authorized calls atomically replace the single booking or running row's single `next_*` tuple, with the last valid database write winning and no priority or merge. Successful completion materializes at most that one staged successor. Deterministic daily/weekly schedules are a different source: each root always advances an evaluated due cursor, but materializes its exact occurrence only when that schedule has no queued/running task. Later due slots coalesce into schedule metadata, not work backlog, and terminalization creates no immediate catch-up. Task outcome never rewrites the calendar.
- The two modes require separate evals: consultation quality and read-only enforcement for the subagent; output-contract, provenance, idempotency, and task completion for the root.
- No cross-session waiter is required for deduplication. A future notification feature may announce task completion, but it is not part of the concurrency guard.
- A badly designed registry `subjectKey` can still over- or under-deduplicate work; registry tests and review own that semantic risk.

## Alternatives considered

- **Prompt-ordered check followed by native subagent call** — rejected: optional, non-atomic, and subject to a check/use race.
- **Dynamic subagent availability as the guard** — rejected: capability composition is not a per-call task claim, and eve documents it as insufficient as the sole authorization boundary.
- **Put every consultation through the queue** — rejected for now: strongest spend deduplication, but it removes the low-latency in-process consultation that motivated the interactive declaration.
- **Authored gateway that claims a task and invokes the root agent over HTTP** — deferred: it can recover synchronous-looking durable delegation, but adds self-call authentication, cross-session waiting, cancellation, approval relaying, and failure handling.
- **General source-task guard with `SELECT ... FOR UPDATE`** — rejected for scheduling: it adds an interactive transaction plus lock-ordering and retry concerns. The only required late-call guard is the self-recheck's single conditional update on the row it already targets.
- **Lease owner, heartbeat, per-attempt token, and write fencing for agent work** — rejected: the one-shot agent run has no application execution lease. ADR-019 also removes lease reclaim from human external commitments; only registered retry-safe direct/automatic work retains the bounded lease.
- **Conversation continuation or intentional multiple task-mode runs on one agent row** — rejected by ADR-018: one task stores one authoritative session and one terminal outcome; only unbound delivery recovery may resend, and a genuine product retry creates a new task.
- **CRM-style catch-all research lane for unknown kinds** — rejected: our task kind determines typed payload, output, owner, and execution mode, so version skew must leave the row untouched rather than guess after consuming an attempt.
- **Per-row `contract_version` and coordinated all-root deployment** — not adopted in v1: backward-compatible evolution, new kinds or explicit expand-contract rollouts, and the compiled supported-kind filter provide a smaller fail-closed protocol.
- **Import or patch eve private subagent execution internals** — rejected: the guard must not depend on an unsupported runtime seam.
- **Disable the specialist HTTP channel with eve's internal `disableRoute()` sentinel** — rejected: eve 0.31.3 does not export it from the supported `eve/channels` entrypoint. An explicit `eveChannel({ auth: [localDev()] })` is public, fails closed in production, and preserves local tooling.

## Out of scope

This ADR does not define general tenant ACL resolution or query scoping. It defines only the narrow runtime billing injection required by agent work: trusted application code projects the already-authorized `brand_id` into the initiating Eve auth context, every production current context must match it, and Eve propagates both through the child session tree. ADR-001 defines organization-wide brand access. ADR-019 applies it at the human commitment boundary: `approveTask` resolves the task brand's `organization_id`, locks and validates the exact Better Auth `Member(organization_id, user_id)` in the approval transaction, and thereby orders a concurrent organization-role downgrade or removal.
