# ADR-012 — Contracts: one approval source, the brief schema, the intent lifecycle, Plan generation

**Status:** Accepted — 2026-08-05
**Amends:** ADR-007 (the inbox's single source), ADR-010 (Plan inputs and persistence)
**Amended by:** [ADR-017](017-consultative-subagents-durable-root-work.md) (D1: no parked specialist consultation; D2: split consultation and durable contracts)
**Amended by:** [ADR-018](018-one-shot-durable-agent-tasks.md) (D4: `finishTask` stages the return and `session.completed` is the terminal success boundary)
**Amended by:** [ADR-019](019-human-approved-external-commitments.md) (D1: the single inbox source is `tasks.status = 'awaiting_approval'`; no external commitment parks an eve session)
**Amended by:** [ADR-020](020-typed-decisions-and-impact-verification.md) (D2/D4: exact-Intent preauthorization selectors and registered roadmap heads; active Decisions require an explicit human boundary)
**Amended by:** [ADR-021](021-plan-advancement-and-human-readiness-override.md) (D4: same-Plan route waves use a separate typed boundary)
**Refs:** ADR-002, ADR-006, ADR-011, ADR-016, ADR-018; current trycompai/crm `AgentRun` and staged `finish_run` boundary; Magister (impact baselines); context.dev (onboarding data)

## Context

Second self-grilling round, aimed one level down: not "do the ADRs compose?" but "do the contracts between the pieces hold when written in code?". Four decisions were approved; three further questions (policy matrix, specialist chaining, sandbox rules) were sent back for deeper reasoning and are handled separately.

## Decisions

### D1 — One source of truth for "what awaits judgment"

> **Amended by ADR-017 and ADR-019.** The one-inbox rule remains, but its source is now the execution identity itself: human-activation direct tasks in `awaiting_approval`.

ADR-007 left two places where pending human judgment could live: eve session state and proposal Objects. Both are rejected for external commitments.

Rule: interactive CMO chat and autonomous durable roots call the same typed preparation service, which creates a distinct direct task in `awaiting_approval`. The inbox is a query over those tasks. Approving from chat or inbox invokes the same `approveTask` transaction, appends one Approval Action, and queues the same row. The CMO conversation need not remain parked, and no resumed eve tool may execute the provider call (ADR-019).

This one-inbox rule is about authorization of external execution. An agent-authored draft Intent awaiting adoption is not an Approval and never enters `tasks.status = 'awaiting_approval'`; it appears in the separate **Intent proposals** projection described in D3.

### D2 — The brief contract, and the return contract

> **Amended by ADR-017.** The schema below is now the durable task/root `TaskCompletion` contract. A declared subagent instead uses a configured `ConsultationReturn` with summary, recommendations, source references, suggested work, and open questions — no selected output Object ids or claimed follow-up tasks. A promoted consultation becomes a validated durable task with bounded conversational context; the consultation result itself is not canonical evidence.

"Self-contained brief" is now a schema, not a phrase. `packages/brain` owns the common task-origin envelope and `IntentSnapshot` schema, while each task kind in `packages/agents` declares the zod schema for its kind-specific payload and return:

```text
brief:    { brand_id,
            intent_context:
              | { kind: intent, snapshot: {
                    intent_id, intent_revision, statement,
                    acceptance_criteria, constraints,
                    preauthorizing_decisions[]: { decision_id, policy_facts }
                  } }
              | { kind: plan_route, plan_object_id, move_candidate_id }
              | { kind: none },
            preamble_extract (size-capped), object_ids[], capabilities_snapshot,
            session_budget, output_contract, due_at, kind_payload }
return:   { status (completed | partial | blocked), summary (token-capped),
            output_object_ids[], open_questions[],
            intent_acceptance (null | {
              judgment (satisfied | not_satisfied | inconclusive),
              rationale (token-capped), evidence_object_ids[]
            }),
            result (nullable, kind-specific registered schema) }
```

`acceptance_criteria` and `constraints` are nullable, non-empty typed arrays validated by shared zod schemas; `null` means that structure has not yet been supplied. `TaskCompletion.status` keeps the common execution-domain vocabulary; a kind-specific business outcome belongs in the registered `result` field and may not invent additional status values. `intent_acceptance` is instead one common optional Verification judgment. It is valid only with `status = completed`, a non-null Intent snapshot, and non-empty pinned acceptance criteria. Trusted code derives `intent_id` and `intent_revision` from that snapshot rather than accepting them from the model. It validates every cited Evidence Object under the same brand; `satisfied` and `not_satisfied` require at least one, while `inconclusive` may explain why none is available. Only `satisfied` attempts automatic settlement; the other judgments remain task-bound Verification facts. Each pre-authorizing Decision entry pins the exact immutable positively-authorizing `intent_preauthorization` Object id and the minimal typed policy facts actually relied upon; entries are canonicalized in ascending `decision_id` order before persistence. Trusted Intent-bound task creation selects only active heads with `content.authorized = true`, whose producing Action has the exact same-brand `intent_id` and whose registered preauthorization key applies to that task/effect. An active false head is a revocation and never enters the array. Roadmap, model and brand-restriction Decisions never enter it. The id remains the canonical content reference; the small fact snapshot prevents an execution-time projection from silently changing the accepted policy input. A Plan-routed task instead carries exact trusted Plan/Move references and no Intent snapshot or preauthorization; `none` is reserved for registered work such as brand-level rebuilds and deterministic cadences that has neither origin. The model and browser never author any common origin envelope. The interactive CMO may nominate only an `intent_id` identified without ambiguity by the current human turn; that reference is not an envelope and grants no facts by itself.

Artifacts travel by id, never by content. The `output_contract` declares which Object types the session may produce, and the brain's write path rejects anything else. The return contract keeps the CMO's context small: a summary plus references, never full artifact bodies. Kind-specific payload data may refine how the work is performed, but may not duplicate or override any common origin field.

The caller supplies `output_object_ids` as a duplicate-free optional selection of principal deliverables, not an inventory of every canonical Object written during the run. After validating the kind-specific `result`, trusted `finishTask` obtains any mandatory principal ids from the registry's deterministic `requiredOutputObjectIds(result)` and persists the canonical sorted set-union of those ids and the model-selected list. Thus omission of a valid mandatory Plan, report or observation is repaired by code rather than another model turn; an invalid required reference still fails. Every stored Object must be same-brand, permitted by the task kind's `output_contract`, and produced by an Action whose exact `task_id` is the current trusted task; an Object produced by another task cannot be claimed. Built-in self-copy writes qualify because they use that same accepted task id, but the top-level root decides which additional deliverables to foreground. Omission neither hides, invalidates nor supersedes any non-required Object. The authoritative full activity inventory is the graph query `objects.produced_by → actions.id WHERE actions.task_id = current_task_id`, including Evidence, intermediate or later-superseded Objects and writes from self-copies. UI and summaries may foreground the normalized `output_object_ids`; audit, provenance, graph reads and Plan advancement use canonical rows and never treat this selected list as exhaustive or as proof of readiness/completion.

`capabilities_snapshot` is input to agent planning, not a pin on a later commitment. ADR-019's deterministic executor resolves the brand's current active connection at execution time and records the effective provider account in the Result Action receipt.

Task relationships are not copied into a generic completion list. Newly created task-bound children are queried through immutable `parent_task_id`; Plan publication and advancement expose their complete `created | observed` route mappings through the canonical producing/wave Action receipt. A merely observed ordinary active task creates no alias and is not retroactively presented as this task's child. A self-recheck staged in `next_*` has no task id until successful settlement materializes or observes it under acceptance-first and current-origin eligibility.

For a durable agent task, the authored `finishTask` tool obtains `task_id` from trusted eve context, validates the registered return schema, normalizes required outputs, and stages the canonical result without settling the row. It returns that normalized completion for the root to mirror through its configured output contract. `result.completed` is telemetry and cannot overwrite the staged value; diagnostic comparison passes the returned value through the same result/output normalization so omission-versus-explicit inclusion of a required id is not a false mismatch. `session.completed` with the staged value is the normal success trigger. Every declared status — `completed`, `partial`, or `blocked` — is a considered domain outcome under execution status `succeeded`. A delivery error, `turn.failed`, `session.failed`, application cancellation, or terminal completion without a valid staged result is a terminal technical failure, never a synthetic `blocked` outcome or an automatic retry of the same run. A failed terminal-event projection is reconciled manually from the durable stream rather than by redispatching the agent.

### D3 — The intent lifecycle

`intents.status`: `draft → active | abandoned`; `active → settled | abandoned`.

The canonical row also stores `statement`, nullable typed `acceptance_criteria`, nullable typed `constraints`, and monotonic `revision NOT NULL DEFAULT 1`. A statement-only Intent is already structurally valid; `draft` does **not** mean underspecified. It means only “agent-authored proposal not yet adopted.” V1 adds no `intent_versions` table. The append-only Action log records adoption and refinements, while task snapshots preserve the exact accepted execution input.

Intent creation has two trusted entry points, not one model-selectable status flag:

- `declareIntent(brandId, statement, parentIntentId?, requestId)` is available only from an authenticated human product boundary or the interactive CMO turn acting on that current human's explicit request. Trusted session/application context resolves the same-brand human Actor and inserts revision 1 as `active` with that Actor as `author_actor_id`. The same transaction appends `intent_declared`; its Action Actor is the human for a direct product mutation or the CMO for chat transduction, while the Intent author remains the human in both cases.
- `proposeIntent(brandId, statement, parentIntentId?, requestId)` is available only to an allowlisted CMO or durable root operating under its build-time agent Actor. It inserts revision 1 as `draft` with that agent as author and appends the agent's `intent_proposed` Action in the same transaction. A consultative subagent and a system Actor cannot create either branch.

Neither operation accepts `author_actor_id`, Actor key, initial status, tenant, or creator mode from model/browser input. The mounted tool or authenticated application boundary selects the branch. In the interactive branch, the CMO performs transduction but does not become the author of the human's stated objective. Both creator paths derive a namespaced operation key from their trusted boundary/Actor and stable `requestId`, hash the complete intended row, and resolve the Action receipt before insertion: same key/same hash returns the original Intent, while same key/different hash fails. A lost response can therefore never duplicate the declaration or proposal.

`packages/brain.adoptIntent(brandId, intentId, expectedRevision, requestId)` is human-only and requires current Member role `owner | admin | member`. It uses the standard namespaced operation-key/request-hash receipt protocol before current-state guards. On a first application, one transaction resolves the global human Actor, locks the same-brand row and performs `draft → active` guarded by `revision = expectedRevision`, increments the revision once, and appends one `intent_adopted` Action containing the expected/resulting revision and current statement/criteria/constraints. `author_actor_id` remains the agent who proposed it; the adopting human is the Action Actor. A zero-row or stale compare-and-swap returns `stale_intent` and commits no Action; exact replay returns the historical receipt even after later refinement. This revision bump serializes adoption against refinement.

`packages/brain.abandonIntent(brandId, intentId, expectedRevision, requestId, rationale)` is the corresponding human-only non-viewer boundary for either a `draft` or `active` row. After resolving the replay receipt first, one transaction locks the exact same-brand nonterminal Intent, performs `status IN ('draft', 'active') AND revision = expectedRevision → abandoned`, increments the revision, and appends one human `intent_abandoned` Action without changing the original author. Stale input commits nothing; exact replay returns the historical receipt. Abandonment deletes nothing, does not cancel or reinterpret already-created tasks and snapshots, and prevents only later new Intent-bound work.

`packages/brain.settleIntent(brandId, intentId, expectedRevision, requestId, rationale)` is the explicit human-only non-viewer close path. It resolves its receipt first, then atomically performs `status = 'active' AND revision = expectedRevision → settled`, increments the revision and appends one human `intent_settled` Action. A stale first application writes nothing; exact replay returns the historical close. Automatic acceptance settlement has no separate user request: its already-idempotent task-bound Verification Action is the receipt, but it uses the same locked status/revision compare-and-swap and resulting revision increment. When that terminal task also carries a staged equivalent self-recheck, trusted settlement resolves the acceptance Verification and guarded Intent close **before** testing eligibility for the staged successor. If the close wins, it clears `next_*` and creates no successor for the now-settled Intent; if the exact revision guard loses, the Verification remains historical evidence and the ordinary current-Intent eligibility rule decides whether a successor may be created. Both forms preserve all Objects and accepted task snapshots.

`packages/brain.refineIntent(brandId, intentId, expectedRevision, { acceptanceCriteria, constraints }, requestId)` is the only refinement path and has two trusted, non-model-selectable callers. A direct authenticated product mutation uses the current non-viewer human as its Action Actor. The interactive CMO wrapper may call it only while executing the top-level application-bound CMO conversation for the current human caller with Member role `owner | admin | member`; the explicit reply is already the authorization, so the CMO transduces an unambiguous answer immediately without an Approval Action or second button. In that branch the CMO remains the producing Action Actor, the Intent's immutable author does not change, and trusted runtime context injects the current human Actor/Member plus `conversation_id`, `session_id`, `turn_id`, and `call_id`. The current human/Member, `(conversation_id, session_id, turn_id, intent_id)`, expected revision, and typed mutation participate in the canonical request hash and `policy_snapshot`; `call_id` is stored only as immutable causal provenance of the first committed Action and is explicitly excluded from that hash. None of these locators is a foreign key to the best-effort `session_events` archive. The model/browser cannot supply or override Actor, role, branch, provenance, or operation identity. The wrapper derives its stable operation identity from `(conversation_id, session_id, turn_id, intent_id)`, so one human reply can refine a given Intent at most once even if the model emits another tool call. Exact replay returns the original receipt and retains its first `call_id`; a second call in that turn with different typed content fails the canonical hash check. `ctx.session.parent` must be absent, the session must match the bound conversation, and task-mode/autonomous CMO, durable roots, self-copies, consultative subagents, viewers, removed Members, and system Actors are rejected at execution time. If the answer cannot be mapped unambiguously to typed criteria/constraints for the exact Intent, the CMO asks another question and performs no write.

After selecting either caller branch, `refineIntent` validates the typed fields, derives the standard operation key/hash, and resolves an exact receipt before current-state guards. On a first application it locks the exact `(brand_id, intent_id)` row and performs a compare-and-swap update guarded by `revision = expectedRevision` and `status IN ('draft', 'active')`. The same transaction appends one `intent_refined` Action with rationale, previous and resulting revision, current statement, and the typed before/after criteria and constraints, then increments the row revision exactly once. If that guarded same-brand row cannot be updated, the transaction returns `stale_intent` and commits neither the update nor the Action; an exact replay instead returns its historical resulting revision even after later changes. The model, browser, and console never perform a read-then-unconditional-update sequence. The interactive guarantee covers Eve durable-step replay and repeated tool calls within the same turn. V1 deliberately does not add a reply-delivery ledger: the browser submits one answer at a time and never automatically retries a submitted `message` or `inputResponses`, because Eve 0.31.3 delivers an already-consumed/stale response as a new user message and therefore a new turn. Refinement creates no task by implication: any later `request_specialist_work` is a separate new-work boundary that requires the current human request to identify the target Intent without ambiguity. A new insertion snapshots the resulting revision, while an observed or already-active task keeps its original snapshot.

This v1 refinement changes only acceptance criteria and constraints. It includes the current statement in the Action and every later task snapshot, but introduces neither an implicit statement-edit operation nor another version lifecycle. A future statement mutation must be decided explicitly rather than smuggled into `refineIntent`.

Every task that is created for an Intent stores the common immutable `intent_snapshot` shown in D2. On an actual insertion, task creation requires `intents.status = 'active'` and resolves that latest canonical revision inside the transaction. A draft cannot create a task, commitment, follow-up, retry, recheck, or other new Intent-bound work. A later `refineIntent` never rewrites the snapshot or kind payload of an existing `awaiting_approval`, `queued`, or `running` task. An idempotency replay or active-work dedup returns the already-existing task and therefore its original snapshot; only a newly inserted task captures the then-current revision. A staged `scheduleRecheck` payload is a template, not a precomputed snapshot: successful successor materialization resolves the latest active Intent then, unless it merely observes an already-active task whose older snapshot remains authoritative.

Policy uses only an `active` canonical Intent when authorizing genuinely new Intent-bound work or an exact-Intent `intent_preauthorization` Decision. A draft has no structure authority and cannot receive an Intent preauthorization. Only applicable active exact-Intent preauthorization heads with `content.authorized = true` may raise structure; an active false head is a revocation. Current brand restrictions are evaluated separately and can only tighten authority. Every non-Intent-bound boundary—registered administrative brand Decisions, the brand-wide Strategy even when it records a causal origin Intent, Plan-routed tasks, and registered origin-free tasks such as a Plan rebuild—uses explicit null structure and no preauthorization rather than a fabricated snapshot; that branch cannot be more permissive than low. Neither a Strategy origin nor a Plan Action's planning Intent snapshots change that branch. Once a task exists, root execution and writes that fulfil that existing task's accepted contract use its pinned origin; reloading current graph data may resolve referenced immutable Objects or enforce current safety/capability facts, but may not replace an Intent snapshot or treat Strategy/Plan as authorization. Creating a distinct follow-up, lateral, commitment, retry, or scheduled occurrence is a **new-work boundary even when requested by a running root**: an Intent-bound insertion requires the canonical Intent still be active and gives the new row its latest snapshot, while a Plan-routed source keeps null Intent and its exact Plan/Move pair. Every genuinely inserted task-bound derivative also receives immutable `parent_task_id = source_task_id`; observation/rescheduling preserves the existing row's parent. Only a separate explicit Intent declaration changes branches. A typed acceptance Verification may be produced only by work already bound to an active Intent snapshot and cites the exact `intent_id` and `intent_revision` whose criteria it evaluated. It may settle the Intent automatically only with one `status = 'active' AND revision = verifiedRevision` guard; otherwise it remains valid historical evidence and the current Intent stays unsettled or already closed. Human settlement uses the same current-revision guard. Row locking serializes adoption, refinement, and settlement: whichever commits first makes the other's old revision/status guard affect zero rows, so no draft starts work, no closed Intent is refined, and no stale criteria settle a newer one.

- Decomposition (`parent_intent_id`) is an Action open to the intentionally allowlisted human, CMO, or durable specialist-root paths — always with rationale, always in the graph. A human-explicit child objective may be declared active through the trusted interactive boundary; an autonomously proposed child is a draft and cannot become task origin until a human adopts it. A consultative subagent may only suggest the follow-up to the CMO. A system Actor receives no generic decomposition capability; `system:context-dev` is restricted to the exact onboarding bootstrap operation.
- Closing an Intent requires receipt-first human `settleIntent` on the current revision or a task-bound Verification attesting the acceptance criteria of that exact current revision; either guarded winner moves it to `settled` and increments once.
- `abandoned` deletes nothing: Objects, already-created work, and provenance survive.
- The Intent part of **Open questions** has one stable predicate: `status = 'active' AND derived structure_level = 'low'`. It has no task-presence or recency filter. Agent-authored drafts instead appear in the distinct Intent proposals projection with **Adopt** and **Abandon** controls; they are neither open work nor external approvals. An incomplete measurable Decision recommendation remains an open question/output; ADR-020 forbids committing a canonical measurable Decision without its complete impact plan and future task.

### D4 — Plan generation and persistence contract

The CMO's judgment is agentic, so the surrounding data contract must make its inputs and output auditable. The relevant typed Object kinds are:

```text
evidence:        closed subtypes, including
                 metric_observation: { key, metric: { name, description,
                   unit, scope }, value, window_start, window_end,
                   source, rationale }
move_candidate:  { key, title, evidence_object_ids[], effort, impact_class, funnel_stage }
report:          closed subtypes, including
                 decision_recommendation: { proposed_decision, origin_intent_id?,
                   rationale, observed_head_id: ObjectId | null }
marketing_plan:  { schema_version, strategy_decision_id,
                   moves[]: { move_candidate_id, evidence_object_ids[],
                     rationale, dependency_move_candidate_ids[] },
                   excluded_moves[]: { move_candidate_id, rationale },
                   assumptions[] }
```

Durable specialist roots normally produce typed Evidence and Move Candidate Objects. A CMO `rebuild-marketing-plan` task pins only the exact immutable brand-wide `strategy` Decision in its payload; it does not freeze the Intent portfolio while queued. During the run the CMO reads the current active Intents together with the graph and chooses which candidates and evidence to use. When the current graph is missing or insufficient, the same CMO task may use its read/consultation surface, call `record_evidence` for the observations it wants to preserve, and then call the typed `produce_object(move_candidate)` boundary before it writes the Plan. The CMO is the producing Actor for both writes; the candidate cites the exact duplicate-free same-brand Evidence Object ids that originated it and carries its own rationale. `Evidence.content.key` remains a human-readable search/display label: it is neither unique nor a reference and trusted code never resolves a candidate through it. No separate specialist task is a prerequisite. The ordered `moves` array is the Plan priority; rationale, dependencies, assumptions and exclusions are model judgment rather than outputs of a scoring formula. `moves` and `excluded_moves` are disjoint and classify only the candidates this Plan explicitly addresses. An absent candidate is neither included nor rejected: the Plan makes no claim that it exhaustively snapshotted or classified every candidate that happened to be active during a potentially long model run.

The Strategy and Plan are single brand-level heads even when several Intents are active. `originIntentId` on the Strategy is only the causal objective that triggered that human choice; it is not the portfolio. The Plan-producing Action therefore owns a canonical `planning_intent_snapshots[]` array containing each active Intent the CMO coordinated at publication: exact `intent_id`, `intent_revision`, statement, acceptance criteria and constraints. It deliberately excludes preauthorization facts and never becomes a task common origin. The immutable Plan content continues to pin only the Strategy and its Move/Evidence synthesis, avoiding a second copy of the portfolio.

The Evidence ids inside a Move Candidate and inside a Plan have related but distinct meanings. The candidate's ids preserve the immutable observations that originated that candidate. Each Plan move's `evidence_object_ids` records the exact observations the CMO used in that particular synthesis to include or prioritize it. Both sets contain exact same-brand Evidence Objects, but v1 does not require them to be equal: a later Plan may legitimately use newer Evidence while retaining the same immutable candidate.

Every `dependency_move_candidate_ids` entry is unique, same-brand, references a different Move included in the same `moves` array, and the complete dependency graph must be acyclic. This relation explains ordering and informs CMO judgment; it is not copied to `tasks`, translated into task status, or consulted by a claim query. A Move has no deterministic completion state because it may have zero or many routes, descendants, retries, commitments and canonical Objects produced before a later task failure.

`publishPlanAndRoute` derives brand, CMO Actor, rebuild task and Strategy from trusted context. Its model-authored input contains the closed Plan, a canonical ordered `planning_intent_refs[]` list of exact `{ intent_id, intent_revision }` values read during synthesis, and a bounded list of route requests; each request names one included Move Candidate plus one registered agent/automatic internal or preparatory task kind and that kind's typed payload. The target kind must declare `acceptsPlanRouteOrigin: true`. Intent refs are claims about planning inputs, not caller-authored task origin: the model supplies neither their content nor tenant, task Intent id/snapshot, Plan id, worker, execution mode, activation, subject identity, parent id or task id.

The route list is explicitly a **ready-now wave**, not a deterministic expansion of the dependency graph and not a promise to route every included Move. The CMO may route work for a dependent Move only when that particular work can start from currently available inputs; it omits work whose prerequisite Object or fact is absent. Trusted code validates the bounded route and provenance but does not second-guess this semantic readiness judgment.

The overall call first acquires the transaction-scoped advisory lock for its operation key, looks up the producing Action, and validates the canonical request hash. An exact hit returns that historical receipt even after the rebuild task or Plan became terminal; the same key with a different hash fails. Only on a receipt miss does the first-application transaction lock the exact authoritative rebuild task and require `status = 'running'`; a cancelled, failed, succeeded, or wrong-task caller writes nothing.

That first application then locks the exact Strategy row `FOR SHARE` and verifies that it remains the active head, followed by the current `marketing-plan` head `FOR UPDATE` and `expectedHeadId`. This fixed `rebuild task → Strategy → Plan` lock order prevents task terminalization or a concurrent `recordDecision` from interleaving with publication. It next performs one canonical ordered read of the brand's current active Intents. The submitted refs must be duplicate-free and equal that exact `{ id, revision }` set; otherwise the call returns typed `planning_inputs_changed` with no canonical write so the CMO can reload and deliberately retry within the same run. From those rows trusted code derives the full typed `planning_intent_snapshots` stored in the producing Action. V1 does not lock every Intent through Plan commit: an Intent change after that capture point may make the new Plan immediately require Rebuild, which is visible and safe rather than silently rewriting the Action's historical inputs.

Before writing, trusted code validates every Plan reference as same-brand and correctly typed, proves that each routed Move is included in that Plan, validates every target kind/payload through the registry and ordinary task-creation contract, derives the Plan-route subject as `plan-route:<move_candidate_id>:<registered-subject>`, rejects duplicate derived routes, and canonicalizes the route list by that stable identity. Every route result records `{ task_id, disposition, origin_root_routing_action_id?, origin_root_routing_task_id? }`: for `created`, root origin is this Action/rebuild task; for `observed`, trusted code preserves the earlier root origin only when a Plan/wave Action's `created` mapping originally materialized that immutable row, otherwise both fields are null. It then deduplicates exact root-route ids from non-null root origins in the previous Plan-producing Action and later `plan_wave_evaluated` mappings and conditionally locks/updates, in stable task-id order, those whose exact Move appears in `excluded_moves`. The complete predicate requires `agent/automatic + queued`, null Intent/snapshot, non-null Plan/Move, null retry/replacement/schedule lineage, `parent_task_id = origin_root_routing_task_id`, and a referenced origin Action whose `created` mapping names that row. Only rows returned by that guarded update change to terminal `superseded` with `finished_at` and `outcome_code = 'plan_move_excluded'`; session, staged completion, `next_*`, lease, and attempts remain absent. A dispatcher claim that first changes a candidate to `running` wins and leaves it untouched; if publication wins, the later claim sees no queued row. Omission from the new Plan is a no-op, and the predicate deliberately excludes direct work, human commitments, running work, rechecks, lateral descendants, retries, replacements, schedule occurrences, and terminal work even when they preserve the same Plan/Move pair. It allocates the new Plan id plus any new task ids, appends one producing Action containing the exact Strategy/Move Candidate/Evidence ids, the canonical `planning_intent_snapshots`, canonical route-request/result mapping, and the canonical per-Move list of task ids actually returned as superseded, supersedes the old Plan, inserts the immutable `marketing_plan`, and creates or observes every routed task through the same task service in that transaction. Newly inserted rows receive `intent_id = intent_snapshot = null`, `parent_task_id = rebuild_task_id`, and trusted same-brand `plan_object_id`/`move_candidate_id`. An equivalent active row is locked before it is accepted as `observed`; it must also be non-Intent-bound and carry the same Move reference, while its original Plan link, payload, parent and provenance remain immutable. This permits a later Plan to observe unfinished work for the same Move, with the new Plan association recorded in its own producing Action without claiming to have created it. If the candidate became terminal, normal insertion is retried. Any incompatible active conflict, invalid route or failed materialization rolls back the Action, task supersessions, Plan supersession, and every newly inserted task. A Strategy mismatch returns typed `obsolete` with no write; a Plan-head mismatch returns `stale_head`.

The successful tool result returns `plan_object_id`, the canonical planning Intent refs captured in the Action, every committed selected route with its `task_id`, `created | observed` disposition, and nullable immutable root-routing Action/task, plus `superseded_task_ids` for the queued root wave routes withdrawn by explicit exclusions. Exact operation replay returns this committed producing-Action receipt and never rescans current tasks or Intents. `TaskCompletion.result = { outcome: 'published', plan_object_id }` must reference that same Plan; it does not duplicate the planning snapshots or route mapping. Atomicity covers exactly the bounded route and explicit-exclusion lists submitted by the CMO; trusted code cannot infer whether the model selected every semantically desirable piece of work. The Plan, routed tasks, and exclusion settlements remain canonical if a later task/session failure occurs, consistently with other successful tool-level writes.

Later waves use `advancePlanAndRoute`, not `publishPlanAndRoute`. Its trusted context supplies the running `advance-marketing-plan` task and its pinned current Plan; it accepts the same bounded registered route shape but neither Plan content nor `expectedHeadId`. First application uses the same resource order—advancement task, pinned Strategy `FOR SHARE`, then active Plan head `FOR UPDATE`—and rejects a Plan whose Strategy or current active-Intent `{ id, revision }` set no longer matches its producing Action. Only a non-stale Plan proceeds to route validation/canonicalization and the subtype-unique same-task `plan_wave_evaluated` receipt before appending one non-producing wave Action and creating or observing the complete wave in one transaction. A same-task same-hash wave replays; a conflicting second wave is rejected. General evaluation may record `no_ready_moves`. A human-targeted evaluation accepts routes only for its exact Move and must create/observe at least one route; otherwise the task can end only with a typed hard `blocked` or `obsolete` result. Neither path mutates the Plan or dependency graph.

Goal and criteria/constraints remain on Intent. Budget/timeline/constraint Decision families remain deferred until they have closed schemas and an explicit CMO consumer; they need not be reducible to a deterministic formula. A Move Candidate write rejects duplicate, absent, cross-brand, or non-Evidence `evidence_object_ids`; an Evidence key is never accepted as a substitute. A `metric_observation` is the only valid baseline for ADR-020. `record_evidence` validates its provider-independent shape and derives brand/Actor/task/session attribution from trusted context, while value, source and interpretation remain explicitly agent-authored. A `decision_recommendation` is an ordinary immutable report Object; TaskCompletion references its Object id, and the human boundary reloads it rather than trusting duplicated UI/model JSON.

## Intent contract tests

The implementation is invalid if any of these are possible:

- `refineIntent` can update an Intent without the exact same-brand `expectedRevision`, append its Action outside the update transaction, increment more than once, or leave an `intent_refined` Action after a zero-row/stale compare-and-swap;
- an interactive refinement can execute outside the exact bound top-level CMO conversation and current non-viewer human turn; accept caller/model-authored Actor, Member role, branch, request identity, or causal locator; attribute its Action to the human instead of the CMO; change the Intent author; depend on a `session_events` row for authority; create an Approval Action, task, or second confirmation; or write from an ambiguous answer instead of asking again;
- exact replay or a second call id for one interactive `(conversation_id, session_id, turn_id, intent_id)` can create another Action or revision, while reuse with another canonical hash can succeed; a viewer, removed Member, wrong/cross-conversation session, task/autonomous CMO, durable root, self-copy, consultative subagent, or system Actor can reach the interactive refinement branch;
- `request_specialist_work` is callable outside a current authenticated top-level non-viewer CMO turn; an ambiguous human request creates work instead of asking which Intent; a task/autonomous/child/consultative/system path can choose a raw Intent; or a valid interactive request can bypass active/same-brand reload, Policy, capabilities, credit admission, or the external-commitment approval floor;
- an exact request such as “continue Intent X” cannot create work for an existing active X without another confirmation; a successfully declared/refined X cannot be used immediately from its exact receipt; two distinct task calls for X in one turn are incorrectly collapsed merely because they share turn and Intent; or the task result hides the exact Intent revision of the returned row;
- the UI automatically retries a submitted CMO `message`/`inputResponses`, represents a stale Eve response as the same-turn replay guarantee, or claims cross-turn exactly-once delivery without a separately designed delivery identity;
- concurrent refinement and settlement can both write against the same old revision, a settled/abandoned Intent can be refined, or a stale Verification can close the newer revision;
- a caller/model can choose an Intent's author or initial status; a human-explicit declaration is not `active` revision 1 with the current human Actor; an autonomous proposal is not `draft` revision 1 with its build-time agent Actor; or a consultative/system path can create either;
- any human-requested Intent creator/refinement/adoption/abandonment/settlement with a stable request can commit without its exact replay receipt, duplicate after a lost response, or accept the same operation key with another canonical hash;
- `adoptIntent` can target anything but an exact same-brand draft at `expectedRevision`, avoid incrementing the revision, change the original agent author, omit its human `intent_adopted` Action, or leave that Action after a stale/zero-row compare-and-swap;
- `abandonIntent` is caller/model-selectable, accepts a viewer, omits its revision guard/increment or `intent_abandoned` Action, deletes provenance, cancels accepted work, or allows later new Intent-bound work;
- human `settleIntent` omits current Member authorization, receipt-first replay, exact active revision, revision increment, or `intent_settled` Action; or automatic settlement lacks its exact task-bound Verification receipt and the same guarded transition;
- a draft can supply Policy structure, receive an exact-Intent preauthorization, become the origin of any new task/commitment/follow-up, or produce an Intent-acceptance settlement;
- criteria or constraints enter the canonical row, an Action, or a task snapshot without passing the shared typed schema; constraints can exist without criteria; a null/empty ambiguity can raise `structure_level`; or `structure_level` is persisted independently;
- refinement silently edits the statement or creates an `intent_versions` row;
- a task creator accepts a caller-authored snapshot, inserts Intent-bound work without one, or lets a later Intent edit mutate an existing task's input;
- creator replay or active-work dedup returns anything other than the original task and snapshot, while a genuinely inserted new task can miss the latest canonical revision;
- task-bound Policy reads current Intent structure instead of the pinned snapshot; `intent_acceptance` is non-null for a non-completed, non-Intent, or statement-only task; its closed judgment/Evidence schema is bypassed; trusted code accepts caller-supplied Intent identity; or anything but a same-revision `satisfied` Verification can settle the current Intent.
- a Plan-route request accepts caller-authored Intent/snapshot/Plan/parent/subject fields, targets a kind that does not explicitly support non-Intent work, inserts anything other than null Intent/snapshot plus same-brand Plan/Move references, or observes an Intent-bound task or a task for another Move;
- a Move Candidate cites Evidence by key, accepts duplicate, absent, cross-brand, or wrong-type Evidence Object ids, or loses the exact immutable evidence provenance that produced it; a Plan move's independently selected exact Evidence ids may differ from the candidate's origin set without either set being resolved through a key;
- a dependency names an absent, excluded, cross-brand or identical Move, appears twice, creates a cycle, is copied onto task rows, or changes dispatcher eligibility/status;
- a Plan-producing Action omits, duplicates or caller-authors an active Intent snapshot; its submitted refs can differ from the exact active `{ id, revision }` set at the capture query and still publish; preauthorization facts leak into those planning snapshots; a later Intent change mutates the Action or already accepted work; or draft Intent creation alone marks the Plan stale;
- an Intent mutation that commits after the publication/advancement input check is treated as retroactively invalidating or rolling back that canonical Plan/wave instead of leaving it intact and making `plan_needs_rebuild` immediately true;
- a Plan whose pinned Strategy or planning-Intent set/revisions drifted can create another wave through Advance, Ricontrolla or Avvia comunque instead of requiring an explicit Rebuild;
- either routing boundary treats dependencies as proof that all Moves are ready, requires a route for every included Move, or claims lossless automatic advancement; `advancePlanAndRoute` mutates/supersedes the Plan, a targeted override routes another Move or returns `no_ready_moves`, or a general no-route evaluation fabricates work;
- two different Moves coalesce, while the same Move/kind/registered subject cannot be observed across Plan rebuilds without mutating the existing row; or a Plan-routed task gains preauthorization, an Intent structure level, Intent-acceptance Verification, or authority to settle an Intent.
- omission from a new Plan withdraws any task; an explicit exclusion fails to supersede a matching queued root-wave `agent/automatic` route in the publication transaction; or it affects a direct, human, running, terminal, Intent-bound, retry, replacement, schedule, lateral descendant, different-Move, or other row that fails the complete origin-routing-Action/task predicate;
- claim and explicit-exclusion settlement can both win for one queued row, excluded-task locks are not acquired in stable id order, or a later publication failure preserves any task supersession without its producing Plan Action and Object.

## Onboarding data: context.dev

First-pass onboarding data comes from **context.dev** (The Web Context API): the Brand API resolves a domain into logos, colors, fonts, styleguides, socials, and industry codes, and the crawl/scrape APIs turn the site into markdown. V1 obtains that mechanical input synchronously in the onboarding flow through a server-side `apps/app` action. The action authenticates the Better Auth member, authorizes the brand's organization, persists the brand and a human-authored **active revision-1** onboarding Intent before leaving the database transaction, and calls context.dev with a server-held credential and an explicit deadline below the Function budget. It holds no database transaction during provider reads or Blob upload. After schema validation and deterministic normalization, each selected logo/icon variant is safely downloaded, validated, hashed, and uploaded idempotently to its brand-scoped content-addressed Vercel Blob key. Only then does one guarded, stable-key `packages/brain` transaction record the producing Action as the fixed `system:context-dev` Actor, create one Artifact Object per successful mirror, and create Brand Context v0 plus its size-capped extract and provider evidence with typed artifact-id references. Original URLs remain evidence only. A failed optional mirror omits that variant without blocking the structured baseline; a provider/bootstrap error leaves the brand incomplete and the same onboarding screen offers an explicit retry. No task, dispatcher, Eve session, LLM call, or autonomous-credit gate participates.

This deliberately differs from the [current CRM onboarding](https://github.com/trycompai/crm/blob/c56b3fd952b035c1b286d35c777e023527cc96bf/apps/api/src/workspace/workspace.service.ts#L143-L164), which persists onboarding and queues the full lookup for a background worker because its Context.dev path can use a [long provider deadline](https://github.com/trycompai/crm/blob/c56b3fd952b035c1b286d35c777e023527cc96bf/apps/agent/agent/lib/context-dev.ts#L121-L135) and [lease-based retryable delivery](https://github.com/trycompai/crm/blob/c56b3fd952b035c1b286d35c777e023527cc96bf/apps/agent/agent/lib/tasks.ts#L27-L78). Branderize v1 chooses the simpler synchronous UX and accepts that the user waits or presses Retry. If measured latency later makes that unacceptable, the operation may move to an **app-owned** durable background workflow; it still does not become agent work.

For assets, Branderize copies the CRM's current upload-before-database order and deterministic byte-hash key ([mirror flow](https://github.com/trycompai/crm/blob/c56b3fd952b035c1b286d35c777e023527cc96bf/apps/agent/agent/lib/brand.ts#L99-L137), [Blob helper](https://github.com/trycompai/crm/blob/c56b3fd952b035c1b286d35c777e023527cc96bf/packages/db/src/blob.ts#L25-L61)), but not its fallback that stores the remote URL as a canonical image. Branderize's remote URL remains evidence, while only a completed Blob upload can receive an Artifact Object. Both systems accept possible unreferenced Blob uploads after a later database failure; v1 adds no cleanup protocol.

The web cannot establish goals, taste, constraints, or which plausible claims the human is willing to adopt. That gap belongs to the persistent **CMO conversation**, the only HITL Eve surface. The CMO may call the local product-marketer declaration in task mode for read-only analysis; that `ConsultationReturn` ends and returns `open_questions` to the CMO. The specialist child never calls `ask_question`, never owns `session.waiting`, and never parks for a reply.

The CMO presents those questions through its own conversation. As the human answers, an explicit unambiguous reply authorizes the immediate typed criteria/constraint `refineIntent` write; a durable choice or preauthorization becomes canonical only through a separate explicit authenticated human `recordDecision` action. The CMO may prepare the typed recommendation but cannot record the active Decision or impersonate the human. The reply is the refinement authority, while only the successfully committed `intent_refined` Action and Intent revision are canonical state; chat text alone is not. Once the required answers are canonical, the same current human request may unambiguously identify that onboarding Intent for a separate `request_specialist_work` call, creating a new durable one-shot product-marketer task without another confirmation. If more than one Intent is plausible, the CMO asks which one and writes no task. The winning insertion snapshots the latest onboarding Intent revision and only applicable active exact-Intent preauthorizations with `content.authorized = true`. That root executes the pinned snapshot, may resolve those immutable Decision ids and current capabilities, and either produces or supersedes Brand Context. If information is still missing, it stages `TaskCompletion(partial | blocked)` with `open_questions` and terminates. The CMO may collect more answers, refine the canonical Intent, obtain explicit human Decisions, and create another task with the then-current revision, but the old task/session input is never rewritten, parked, resumed, or reused.

Context.dev bootstrap consumes no autonomous AI credit because it contains no inference. Any later product-marketer root task follows the ordinary agent-credit policy; this ADR does not decide the initial commercial grant.
